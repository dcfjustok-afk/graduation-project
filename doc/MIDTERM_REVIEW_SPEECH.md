## 开场：问题是什么（1 分钟）

老师好，我的课题是**基于区块链的可信任务日志审计系统**。

我先讲一下这个课题要解决的问题。在传统的运维和任务管理场景中，日志是事后追责和审计的核心依据。但传统日志系统有一个根本缺陷：**日志存储在数据库或文件系统中，拥有系统权限的人（管理员、攻击者）可以直接篡改日志内容，而且篡改之后无法被发现**。

这意味着：
- 审计结果不可信——因为审计的对象本身可能已经被改过了
- 无法事后证明"这条日志从生成到现在没有被动过"

我的思路是：**引入区块链作为独立于数据库之外的"可信证据源"**。日志入库的同时，把它的哈希写入区块链。之后审计时，重新算哈希和链上记录对比——哪怕数据库被改了，链上的记录改不了，所以篡改一定能被发现。

## 第一部分：架构设计与设计决策（3 分钟）

### 整体架构："链下存原文，链上存哈希"

这是本系统最核心的设计决策。我没有把日志原文直接存到区块链上，原因有两点：
1. **成本问题**：链上存储极其昂贵，一条日志可能几百字节，上千条日志不现实
2. **隐私问题**：日志可能包含敏感信息（IP、用户行为等），上链等于公开

所以我采取的方案是：
- **链下**（SQLite 数据库）保存日志原文，支持高效查询
- **链上**（以太坊智能合约）只保存日志的 SHA-256 哈希值，作为不可篡改的"指纹"
- **审计时**重新对链下原文计算哈希，与链上哈希比对，一致则说明未被篡改

这个方案兼顾了**存储效率**和**可信验证**。

### 模块划分："四层分离"

系统分为 4 个独立模块，各司其职：

```
┌──────────┐    HTTP     ┌──────────┐    Ethers.js   ┌──────────────┐
│  Agent   │ ──────────→ │  Server  │ ──────────────→ │ LogRegistry  │
│ 日志采集  │             │ 业务处理  │                 │  智能合约     │
└──────────┘             └────┬─────┘                 └──────────────┘
                              │ API
                         ┌────▼─────┐
                         │   Web    │
                         │ 可视化展示 │
                         └──────────┘
```

**为什么要单独做一个 Agent，而不是 Server 直接读文件？**

因为在实际场景中，日志文件和审计服务器往往不在同一台机器上。Agent 部署在产生日志的机器上，通过网络把日志推送给 Server。这样做的好处是：
- 采集端和处理端**解耦**，可以分别部署和扩展
- Agent 可以做到**增量采集**（只读新增内容，不重复读取），通过偏移量机制实现
- Agent 内置了**失败重试队列**（指数退避），网络中断时不丢数据，恢复后自动补发

**为什么用 SQLite 而不是 MySQL/PostgreSQL？**

这是毕设原型系统，SQLite 零配置、单文件，启动即用，降低部署复杂度。但代码中数据访问通过 Repository 层隔离，切换数据库只需改底层实现，不影响业务逻辑。

### 智能合约设计

合约 `LogRegistry` 基于 OpenZeppelin 的 `AccessControl` 做了**角色权限控制**：
- 只有被授予 `LOGGER_ROLE` 的地址才能写入日志哈希
- 任何人都可以查询链上记录

为什么要做权限控制？因为链上存证的可信度取决于"谁有权写入"。如果任何人都能写，攻击者可以写入虚假哈希来混淆审计结果。通过角色控制，确保只有授权的审计服务器能写入。

合约还记录了每条存证的**提交者地址和时间戳**，这为后续追责提供了链上证据。

### 审计机制："三方比对"

这是系统的核心逻辑。执行审计时做三件事：

1. **重新计算**日志原文的 SHA-256 哈希 → `actualHash`
2. **从数据库读取**入库时保存的哈希 → `expectedHash`
3. **从区块链读取**链上存证的哈希 → `onChainHash`

然后三方比对：
- 三者一致 → **通过**（日志未被篡改）
- `actualHash ≠ expectedHash` → **失败**（链下数据被篡改，库里的和重算的对不上）
- `actualHash ≠ onChainHash` → **失败**（即使有人同时改了数据库里的哈希，链上的也改不了）

这样设计的好处是：即使攻击者同时篡改了日志内容和数据库中的哈希记录，只要他改不了区块链，系统就一定能检测到。

## 第二部分：创新点（1.5 分钟）

### 创新点 1：链上链下协同的日志可信审计闭环

现有的区块链存证方案大多停留在"数据上链"这一步。我的系统打通了**从采集到存证到审计到告警的完整闭环**：

```
采集 → 入库 → 哈希上链 → 审计比对 → 异常告警 → 可视化
```

不是单纯地"往链上写东西"，而是**把链上记录用起来了**——用于审计时的可信比对，发现异常时自动生成告警。

### 创新点 2：三方哈希比对审计机制

不是简单的"链下 vs 链上"两方比对，而是**实时重算 vs 数据库存储 vs 链上存证**的三方比对。这样可以区分不同的攻击场景：
- 只改了日志内容 → `actualHash ≠ expectedHash`
- 同时改了日志和数据库哈希 → `actualHash = expectedHash`，但 `≠ onChainHash`
- 能精确定位问题出在哪一层

### 创新点 3：基于历史合约地址的回溯审计

合约可能会因为升级重新部署（地址变化）。系统在每条上链记录中保存了**当时使用的合约地址**，审计时按历史地址去查询对应合约上的数据，而不是只查当前合约。这保证了**合约升级后，历史日志的审计依然正确**。

### 创新点 4：Agent 端可靠采集设计

Agent 不是简单的文件读取工具，而是包含了：
- **偏移量持久化**：断电重启后从上次读到的位置继续，不遗漏也不重复
- **指数退避重试队列**：网络异常时自动退避重试，队列持久化到磁盘
- **状态上报机制**：Server 端可以实时监控 Agent 的健康状态

## 第三部分：实验验证（2 分钟）

### 核心实验：篡改检测

这个实验直接验证了系统的核心价值：

| 步骤 | 操作 |
|------|------|
| 1 | 正常提交一条日志，系统自动计算哈希并写入区块链 |
| 2 | 直接修改数据库中该日志的内容（模拟内部人员或攻击者篡改） |
| 3 | 触发审计 |
| 4 | **审计结果：failed，自动生成高危告警** |

结论：**即使拥有数据库访问权限的攻击者篡改了日志，系统也能检测到**。因为攻击者改不了区块链上的哈希记录。

这个实验证明了引入区块链存证的必要性——如果只用数据库，篡改后审计就发现不了了。

### 全链路联调

- 执行审计 → 正常日志通过 / 被篡改日志失败
- 整条链路数据一致、功能完整

## 导师可能追问及参考回答

**Q: 为什么用区块链，而不是数字签名或 HMAC？**
> 数字签名和 HMAC 都依赖密钥的安全性。如果系统管理员本身就是攻击者，他拥有密钥，可以篡改日志后重新签名。区块链的优势在于：哈希一旦上链，**任何单方（包括管理员）都无法篡改**，因为需要全网共识。这就把"可信"从"信任某个人"变成了"信任协议本身"。

**Q: 为什么不直接把日志原文上链？**
> 两个原因：一是**成本**，链上存储按字节计费，日志量大时完全不可接受；二是**隐私**，日志可能包含敏感信息，上链等于公开。所以只上链哈希——32 字节的哈希就能唯一标识任意长度的日志，存储成本极低，且不泄露原始内容。

**Q: SQLite 不是生产级数据库，实际怎么办？**
> 这是工程权衡。毕设目标是验证"区块链存证 + 审计检测"这套机制的可行性，SQLite 零配置、全内嵌，让系统启动即用，降低了实验环境搭建成本。代码中数据访问通过 Repository 模式隔离，切换到 MySQL 或 PostgreSQL 只需替换底层实现，业务逻辑不变。

**Q: 如果区块链节点挂了怎么办？**
> Agent 端有指数退避重试队列，提交失败会自动重试。Server 端对上链失败的记录标记为 `pending`，可以后续补写。区块链本身是多节点共识网络，单节点故障不影响已上链的数据安全。

**Q: 三方比对和两方比对有什么本质区别？**
> 两方比对（链下 vs 链上）在大多数场景够用，但有一个盲区：如果攻击者既改了日志内容，又改了数据库中保存的原始哈希，两方比对会以为"数据库里的哈希就是正确的"。三方比对多了一步"重新计算"——从日志原文重新算哈希，这样即使数据库里的哈希也被篡改了，重算结果和链上一比就暴露了。
