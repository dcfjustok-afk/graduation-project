## 开场（30 秒）

老师好，我的毕业设计课题是**基于区块链的可信任务日志审计系统**。这个系统要解决的核心问题是：传统日志存在被篡改的风险，审计结果不可信。我的方案是把日志哈希写入区块链，利用区块链不可篡改的特性来保障日志的真实性。

---

## 第一部分：系统架构（1 分钟）

系统采用了前后端分离 + 区块链的架构，一共有 **5 个模块**：

1. **日志采集 Agent** — 负责从日志文件中增量读取新日志，提交给后端
2. **后端 Server** — 接收日志、计算哈希、调用智能合约写入区块链、执行审计
3. **智能合约** — 部署在以太坊上，存储日志哈希，提供链上查询
4. **前端 Web** — 可视化展示日志、审计结果、告警信息
5. **共享类型库** — 保证前后端和 Agent 之间类型定义一致

整体数据流是：**Agent 采集 → Server 处理上链 → 审计时三方比对 → 异常自动告警 → 前端展示**。

### 核心实验：篡改检测
我做了一个关键实验来验证系统的核心能力：
1. 正常提交一条日志，系统自动计算哈希并写入区块链
2. 人为直接修改数据库中的日志内容（模拟篡改攻击）
3. 执行审计 → 重新计算哈希与链上哈希对比
4. **结果：系统成功检测到篡改，审计状态标记为 failed，并自动生成了告警**

这证明了区块链存证方案的有效性——即使数据库被入侵篡改，只要链上记录未被改变，审计就能发现异常。

## 如果导师提问

**Q: 为什么选区块链而不是传统数字签名？**
> 数字签名依赖可信的签名方，如果签名私钥被泄露或系统管理员本身就是攻击者，签名就失效了。区块链的优势在于去中心化——哈希一旦上链，任何单方都无法篡改，即便是系统管理员也不行。

**Q: 性能瓶颈在哪里？**
> 主要在链上写入，单次写入需要等待区块确认。目前在 Hardhat 本地链上平均 173ms，实际公链会更慢。可以通过批量上链、异步写入等方式优化。

**Q: 如果区块链节点挂了怎么办？**
> 系统设计了重试机制。Agent 有指数退避重试队列，Server 也可以将上链失败的记录标记为 pending 后续重试。且链上数据有多节点共识，单节点故障不影响已存数据。
