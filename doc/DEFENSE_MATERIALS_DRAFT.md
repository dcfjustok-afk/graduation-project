## 2. 每页建议展示内容

### 第 1 页：课题背景与研究意义

建议内容：

- 传统日志系统易被篡改，缺少可信存证能力
- 运维审计与任务执行追踪需要可验证证据
- 区块链具有不可篡改、可追溯、可验证的特点
- 本课题的目标是构建“基于区块链的可信任务日志审计系统”

建议口述要点：

本课题聚焦任务日志可信性问题，通过链上存证和链下审计相结合的方式，使日志既能高效存储，又能在事后证明是否被篡改。

### 第 2 页：系统建设目标与总体方案

建议内容：

- 自动采集日志
- 链下保存原文
- 链上保存哈希与元数据
- 支持审计比对与异常告警
- 提供前端可视化展示

建议配图：

- 一张简化的数据流图

建议内容：

- `Agent` 负责本地日志采集
- `Server` 负责业务处理与 API
- `SQLite` 负责链下数据存储
- `LogRegistry` 负责链上存证
- `Web` 负责可视化展示

建议口述顺序：

先从日志文件进入 Agent 开始讲，再讲后端、数据库、区块链，最后落到前端展示。

### 第 4 页：智能合约与可信存证设计

建议内容：

- 合约名称：`LogRegistry`
- 使用 `AccessControl` 实现权限控制
- 记录任务 ID、日志哈希、时间戳、提交者地址
- 支持按任务 ID 查询链上记录

答辩强调点：

- 为什么不上链保存原文而只保存哈希
- 为什么引入角色控制
- 区块链在本系统中的“可信证据”作用

4. 查询链上存证

6. 写入审计记录

- 本轮优化增加了“合约代码存在性校验”
- 审计时按历史 `contract_address` 查询，保证多次部署后的结果仍可追溯

不足建议：

3. 批量审计尚可继续优化并发性能

## 5. 常见答辩问题及参考回答

### 问题 1：为什么要用区块链，普通数据库不行吗？

参考回答：

普通数据库可以保存日志，但数据库管理员或攻击者仍可能篡改数据。区块链在本系统中不负责保存原文，而是保存日志哈希和元数据，作为独立于数据库之外的可信证据源。这样即使链下日志被修改，系统仍能通过重新计算哈希并与链上记录比对来发现异常。

### 问题 2：为什么不上链保存原始日志？

参考回答：

原始日志体积较大，而且可能包含隐私或敏感信息，直接上链会带来较高存储成本和隐私风险。因此本系统采用“链下保存原文、链上保存哈希”的方式，在兼顾效率的同时保留可验证性。

### 问题 3：系统如何判断日志被篡改？

参考回答：

系统会对链下日志原文重新计算哈希，然后读取数据库保存的期望哈希与链上存证哈希。若本地重算结果与数据库、链上记录存在不一致，系统就会写入失败审计记录，并自动生成告警。

### 问题 4：为什么需要 Agent？

参考回答：

Agent 负责自动监听本地日志文件并增量读取新增内容，使日志采集过程自动化。这样可以模拟真实业务环境中的日志接入场景，而不是依赖人工导入。

### 问题 5：如果本地链重启了，会不会影响结果？

参考回答：

本轮实现中已经增加了合约代码存在性校验。如果目标地址没有部署合约，后端会直接报错而不是误判成功。同时，审计时优先使用日志记录对应的历史合约地址读取链上数据，能够更准确地处理多次部署后的历史记录。

### 问题 6：系统目前还有哪些不足？

参考回答：

目前系统主要定位为毕业设计原型，链环境仍使用本地 Hardhat，数据库也选用了更易部署的 SQLite。后续如果继续扩展，可以接入测试网、引入更强的数据库方案，并对批量审计性能做更深层优化。

## 6. 演讲稿开场示例

各位老师好，我的毕业设计题目是“基于区块链的可信任务日志审计系统”。本课题主要解决传统日志系统中日志容易被篡改、事后难以证明真实性的问题。为此，我设计并实现了一套由日志采集 Agent、后端服务、SQLite、区块链存证合约以及前端可视化页面组成的完整系统，通过链上保存日志哈希、链下保存日志原文，并在审计阶段进行重算比对，从而实现日志可信性验证和异常告警。
