## 5.5 功能测试与闭环验证

为验证系统各模块是否能够按照设计目标协同运行，本节围绕智能合约、后端接口与审计闭环、Agent 采集与前端展示三个方面开展功能测试。功能测试的重点不是单纯验证某个函数是否能够运行，而是确认日志从采集、入库、哈希计算、链上存证、审计比对、告警生成到前端展示的闭环是否能够形成。测试过程中未引入论文事实之外的额外功能，主要依据项目中已有的合约测试、后端验证脚本、Agent 验证脚本和前端构建检查结论进行整理。

### 5.5.1 智能合约功能测试

智能合约功能测试主要面向 LogRegistry 合约展开，测试目标是确认合约能够稳定完成日志哈希存证、权限控制和查询操作。LogRegistry 合约负责保存 taskId、logHash、createdAt 和 submitter 四类核心字段，是系统链上可信存证的基础。如果合约写入或查询能力不可靠，则后续三方哈希比对将缺少可信的链上依据。

测试内容覆盖合约部署、LOGGER_ROLE 权限控制、日志哈希写入、按记录编号查询、按 taskId 查询、任务日志数量统计、合约总记录数量统计以及异常输入处理等场景。测试结果显示，智能合约测试 8 项全部通过，说明合约基础功能满足系统原型验证需要。其中，权限测试用于确认未授权地址不能随意写入日志哈希，写入测试用于确认授权地址能够通过 storeLog(taskId, logHash) 保存存证记录，查询测试用于确认 getLog、getLogsByTaskId、getRecordIdsByTaskId、getTaskLogCount 和 getLogCount 等方法能够返回预期结果。

从系统闭环角度看，合约测试通过说明链上存证模块能够为后端提供稳定接口。后端在日志提交阶段可以将计算得到的 logHash 写入合约，在审计阶段也能够根据 taskId 读取链上记录。该测试为后续后端接口验证和性能实验奠定了基础。

本节关键信息摘要：

1. LogRegistry 合约测试围绕权限、写入、查询和异常场景展开。
2. 合约测试 8 项全部通过，说明基础链上存证能力可用。
3. LOGGER_ROLE 权限控制验证了日志写入边界。
4. 查询方法为后续审计阶段读取 onChainHash 提供支持。

### 5.5.2 后端接口与审计闭环测试

后端接口与审计闭环测试主要验证 Server 能否正确完成日志接收、链下入库、哈希计算、链上写入、审计比对和异常告警。测试重点包括 POST /api/logs 日志提交接口、POST /api/audits/run 审计执行接口、GET /api/audits 审计记录查询接口和 GET /api/alerts 告警查询接口。通过这些接口，可以验证后端是否能够将第 3 章设计的可信日志审计机制落到实际运行流程中。

在链上写入验证中，系统通过后端服务接收日志内容，将日志原文写入 logs 表，并对 log_content 计算 SHA-256 哈希。随后，后端调用 LogRegistry 合约的 storeLog 方法写入链上存证，并在 log_hash_records 表中保存 log_id、task_id、log_hash、contract_address、transaction_hash、block_number 和 on_chain_status 等信息。验证结果表明，日志提交后能够形成链下日志记录和链上哈希记录，说明后端完成了从接口输入到可信存证的主要流程。

在 API 回归验证中，系统对日志提交、日志查询、审计触发、审计结果查询和告警查询等接口进行检查，确认接口能够返回结构化响应，并且前后端使用的数据字段保持一致。在审计闭环验证中，后端执行 runAuditForAllLogs 后，能够检测到 passed 与 failed 两类分支：当 expectedHash、actualHash 和 onChainHash 一致时，审计结果为 passed；当日志内容被修改或哈希比对不一致时，审计结果为 failed，并在 audit_records 表中写入 failed 记录，同时在 alerts 表中生成 hash_mismatch 类型告警。

该测试说明，后端不只是完成日志保存，还能够将链下数据库、链上合约和审计告警串联起来。passed 分支验证了正常日志的可信校验路径，failed 分支验证了异常日志的识别与告警路径，二者共同证明系统具备基本的审计闭环能力。

本节关键信息摘要：

1. 后端测试覆盖日志提交、API 回归、批量审计和告警查询。
2. POST /api/logs 能够触发日志入库、哈希计算和链上写入。
3. POST /api/audits/run 能够验证 passed 与 failed 两类审计分支。
4. failed 分支会写入 audit_records 并生成 hash_mismatch 告警。

### 5.5.3 Agent 采集与前端展示测试

Agent 采集测试主要验证日志采集端能否按照增量方式读取文件，并维护读取偏移量。测试中，Agent 首次读取日志文件时能够采集已有日志行；在日志文件没有新增内容时，不会重复读取历史记录；当文件追加新日志后，Agent 仅采集新增部分。同时，offsetStore 能够保存 lastOffset，使 Agent 在后续运行中继续从正确位置读取。该结果说明，Agent 的增量读取和偏移量持久化机制能够减少重复采集问题。

除基础采集外，Agent 还进行了真实提交链路验证。Agent 将采集到的日志封装为包含 taskId、sourceType、sourcePath、logContent、logLevel 和 collectedAt 等字段的数据，并提交给后端接口。后端接收后继续执行入库、哈希计算和上链流程。该测试说明，Agent 并非孤立的文件读取脚本，而是系统可信日志审计链路的输入端，能够为后端提供持续日志来源。

前端展示测试主要通过 TypeScript 类型检查与 Vite 构建验证完成。前端工程的 build 脚本包含 tsc --noEmit 与 vite build，分别用于检查 TypeScript 类型一致性和生产构建结果。验证结论表明，前端 TypeScript 检查与 Vite 构建通过，说明系统总览、日志中心、审计管理和告警管理页面能够在工程层面完成构建。结合后端接口验证结果，前端能够通过 GET /api/logs、GET /api/audits、GET /api/alerts 和 GET /api/overview 展示日志、审计和告警数据。

总体来看，Agent 采集、后端审计和前端展示能够形成连续路径：Agent 负责产生标准化日志输入，后端负责可信存证与审计判断，前端负责展示运行状态和异常结果。该功能验证说明系统闭环具备可运行性，为后续性能实验和篡改检测实验提供了基础。

本节关键信息摘要：

1. Agent 验证覆盖增量读取、偏移量持久化和真实提交。
2. 日志无新增时不会重复采集，追加日志后只读取新增内容。
3. 前端 TypeScript 检查与 Vite 构建通过。
4. Agent、后端和前端共同验证了系统闭环的可运行性。

### 5.6.1 日志批量提交实验

日志批量提交实验用于验证系统在连续接收日志并执行存证流程时的稳定性。实验通过脚本连续提交 100 条日志，每条日志经由后端接口进入系统，随后完成日志入库、SHA-256 哈希计算和链上存证记录写入。该实验能够反映 POST /api/logs 接口在批量场景下的可用性，也能够间接验证后端与 LogRegistry 合约之间的调用链路。

实验结果显示，日志批量提交共执行 100 次，成功 100 次，失败 0 次，成功率为 100%。平均响应时间约为 107.03 ms，吞吐量约为 9.33 条/秒。该结果说明，在本地实验环境和当前系统规模下，日志提交链路能够稳定完成连续请求处理，没有出现批量提交失败的情况。平均响应时间包含后端处理、数据库写入、哈希计算和链上交互等环节，因此该指标能够较综合地反映日志提交链路的运行开销。

从实验意义看，100 次连续提交成功表明系统具备基本的批量接入能力，能够支撑毕业设计原型系统的演示和验证需要。吞吐量为 9.33 条/秒，说明系统在本地链和 SQLite 条件下可以完成小规模任务日志的持续存证。但该结果并不代表系统已经适用于大规模生产环境，因为本实验使用的是本地开发链和原型数据库，后续若面向更高并发场景，还需要进一步优化数据库连接、合约交互方式和批量写入策略。

### 5.6.2 批量审计性能实验

批量审计性能实验用于观察系统在不同数据规模下执行审计任务的耗时情况。审计过程需要读取 logs 表中的日志原文，重新计算 actualHash，读取 log_hash_records 中的 expectedHash，并根据 taskId 和合约地址查询链上 onChainHash，最后完成三方比对并写入 audit_records。与日志提交相比，批量审计涉及更多记录遍历和链上查询，因此更能反映审计流程的整体处理开销。

实验分别针对 100 条、500 条和 1000 条数据集执行批量审计，每个规模重复 5 轮，5 轮均全部成功。实验结果显示，100 条数据集平均耗时约为 3067.77 ms，500 条数据集平均耗时约为 15659.44 ms，1000 条数据集平均耗时约为 35032.13 ms。随着数据规模增加，批量审计总耗时呈明显上升趋势，说明审计处理时间与待审计日志数量具有较强相关性。

从结果分析看，批量审计耗时由多个因素共同构成，包括数据库读取、哈希重算、链上记录查询、比对判断和审计结果写入。1000 条数据集平均耗时约 35032.13 ms，说明在本地实验环境下，系统能够完成千条级日志审计，但耗时已经较为明显。该结果符合原型系统特点：系统重点验证可信审计机制和闭环有效性，而不是追求极限性能。若后续需要提升批量审计效率，可以考虑减少重复链上查询、优化任务维度索引、批量处理数据库写入，或在合约与后端之间增加更高效的数据读取策略。

本节关键信息摘要：

1. 批量审计实验覆盖 100、500、1000 条三种数据规模。
2. 每种规模重复 5 轮，实验均全部成功。
3. 平均耗时分别为 3067.77 ms、15659.44 ms、35032.13 ms。
4. 审计耗时随数据规模增加而上升，符合批量哈希重算和链上查询特点。

### 5.6.3 篡改检测实验与结果分析

篡改检测实验用于验证系统能否识别日志内容被修改后的异常情况。实验思路是先通过正常流程提交日志，使日志原文写入 logs 表，日志哈希写入 log_hash_records 和 LogRegistry；随后修改链下日志内容，使日志原文与原始哈希不再匹配；最后触发审计流程，观察系统是否能够识别哈希不一致并生成告警。

实验结果显示，篡改检测实验中 auditStatus 为 failed，alertGenerated 为 true。该结果说明，当日志内容被修改后，审计阶段重新计算得到的 actualHash 与数据库中保存的 expectedHash 或链上 onChainHash 不一致，系统能够将审计状态判定为 failed。同时，系统在 failed 分支中生成 hash_mismatch 类型告警，并写入 alerts 表，使异常情况能够在前端告警页面中展示。

从机制角度分析，篡改检测成功依赖于链上链下混合存储和三方哈希比对。链下 logs 表保存日志原文，log_hash_records 保存提交时的 expectedHash，LogRegistry 保存链上 onChainHash。当日志原文被修改后，actualHash 会随之变化，而链上哈希保持为原始存证结果。三者不一致时，系统即可判断日志存在完整性异常。由于链上哈希不直接依赖当前数据库中的日志内容，因此能够为篡改检测提供独立比对依据。

该实验验证了系统设计目标中“发现日志被篡改并生成告警”的关键能力。需要说明的是，本实验验证的是内容篡改检测场景，即日志原文被修改后能否通过哈希不一致发现异常；对于更复杂的攻击行为，例如绕过 Agent 采集、破坏数据库文件或攻击区块链节点等情况，还需要结合权限控制、备份机制和运行环境安全策略进一步研究。就本毕业设计原型而言，篡改检测实验已经证明系统能够完成从异常发现到告警生成的基本闭环。

本节关键信息摘要：

1. 篡改检测实验通过修改链下日志内容触发哈希不一致。
2. 实验结果为 auditStatus=failed，alertGenerated=true。
3. failed 结果说明系统能够识别日志内容被修改后的完整性异常。
4. hash_mismatch 告警证明系统具备异常提示闭环。
