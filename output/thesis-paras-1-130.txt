[001] 摘要

[002] 随着信息系统在业务处理、自动化运维和任务执行场景中的广泛应用，日志数据已成为安全审计、故障排查和责任追溯的重要依据。传统中心化日志通常将日志原文、哈希记录和审计结果保存在同一管理域内，存在被篡改、删除或伪造后难以及时验证的问题。针对上述问题，本文设计并实现了一种基于区块链的可信任务日志审计系统。系统采用“链下保存日志原文、链上保存日志哈希摘要”的混合存储模型，由 Agent 完成日志增量采集，Server 负责日志入库、SHA-256 哈希计算和 LogRegistry 智能合约调用，SQLite 保存日志、存证、审计和告警记录，Web 前端展示日志、审计和告警结果。审计阶段，系统重新计算日志原文得到 actualHash，并与数据库中的 expectedHash、链上的 onChainHash 进行三方比对；当哈希不一致时，生成 failed 审计记录和 hash_mismatch 告警。系统还针对本地链重启和多次部署场景，引入合约代码存在性校验与历史合约地址回溯策略，以减少空地址和历史记录误判。实验结果表明，LogRegistry 合约测试 8 项全部通过；日志批量提交 100 次成功率为 100%，平均响应时间约 107.03 ms，吞吐量约 9.33 条/秒；批量审计 100、500、1000 条数据 5 轮均执行成功；篡改检测实验能够识别日志内容被修改并生成告警。

[003] 关键词：区块链；日志审计；智能合约；哈希校验；可信存证；异常告警

[004] Abstract

[005] With the widespread use of information systems in business processing, automated operation and maintenance, and task execution scenarios, log data has become an important basis for security auditing, fault diagnosis, and responsibility tracing. Traditional centralized log management usually stores original logs, hash records, and audit results within the same management domain. Once logs are tampered with, deleted, or forged, it is difficult to provide independent and reliable evidence for later verification. To address this problem, this thesis designs and implements a blockchain-based trusted task log auditing system. The system adopts a hybrid storage model in which original logs are stored off-chain and log hash digests are stored on-chain. The Agent performs incremental log collection, the Server stores logs in SQLite, calculates SHA-256 hashes, and calls the LogRegistry smart contract, while SQLite maintains log records, evidence records, audit records, and alert records. The Web frontend displays logs, audit results, and alert information. During auditing, actualHash is recalculated from the current log content and compared with expectedHash stored in the database and onChainHash queried from the smart contract. If the three hashes are consistent, the audit result is passed; otherwise, a failed audit record and a hash_mismatch alert are generated. The system also introduces contract code existence verification and historical contract address tracing for local chain restart and repeated deployment scenarios. Experimental results show that all 8 LogRegistry contract tests passed, 100 batch log submissions achieved a 100% success rate, the average response time was about 107.03 ms, and the throughput was about 9.33 records per second. Batch audits for 100, 500, and 1000 records were successfully completed in five rounds, and the tamper detection experiment showed that modified log content could be identified and alerted.

[006] Keywords: blockchain; log auditing; smart contract; hash verification; trusted evidence storage; anomaly alert

[007] 第 1 章 绪论

[008] 1.1 研究背景及意义

[009] 随着信息系统在政务服务、企业管理、在线交易、自动化运维和数据处理任务中的广泛应用，系统运行过程中会持续产生大量日志数据。日志记录了任务执行过程、接口调用结果、异常错误、用户操作和系统状态变化等信息，是安全审计、故障排查、责任追溯和运行分析的重要依据。当系统发生异常或安全事件时，日志往往是定位问题来源、还原操作过程和判断责任边界的重要证据。因此，日志数据的真实性、完整性和可追溯性直接影响后续审计结论的可信程度。传统日志管理方式多采用中心化存储模式，日志原文通常保存在服务器文件系统、数据库或集中日志平台中。

[010] 这种方式具有部署简单、查询方便、与业务系统集成成本较低等优点，但在可信审计场景下也存在明显不足。首先，中心化日志存储依赖管理权限和数据库安全策略，一旦攻击者获得较高权限，可能对日志内容进行修改、删除或伪造。在此背景下，如何增强日志数据的防篡改能力和审计可验证性，成为日志审计系统设计中的重要问题。本课题围绕“基于区块链的可信任务日志审计系统设计与实现”展开，目标是构建一个从日志采集、链下存储、链上存证、审计比对、异常告警到前端展示的完整原型系统。本课题具有一定的理论意义和工程意义。

[011] 从工程层面看，系统实现了 Agent 增量采集、Express 后端服务、SQLite 链下存储、LogRegistry 智能合约、审计告警和 React 前端展示等模块，能够验证可信日志审计闭环的可运行性。

[012] 1.2 国内外研究现状

[013] 近年来，围绕数据可信存证、日志审计和智能合约可信管理的研究不断发展。三类研究方向相互关联，共同为可信日志审计系统提供了理论与工程基础。已有研究通常认为，区块链适合保存数据摘要而非大规模原文，哈希函数适合用于校验链下数据是否被修改，智能合约适合将写入规则和查询接口固化在链上。这些研究为本课题采用“链下保存日志原文、链上保存日志哈希摘要”的设计提供了参考。

[014] 因此，本课题在已有研究基础上，面向任务日志审计场景，设计并实现包含 Agent 自动采集、Server 后端处理、SQLite 链下存储、LogRegistry 合约存证、三方哈希比对和 Web 前端展示的原型系统，重点验证可信日志审计机制在工程闭环中的可行性。

[015] 1.2.1 区块链存证技术研究现状

[016] 区块链存证技术是区块链在数据可信证明领域的重要应用方向。相关研究表明，区块链由于具备账本共享、记录可追溯和历史数据难以篡改等特点，可以用于保存电子证据、数据摘要、交易凭证和关键操作记录。在数据完整性保护场景中，区块链常被用作外部可信记录载体，为链下数据提供时间顺序和摘要校验依据。从存证方式看，常见方案主要包括完整数据上链和摘要数据上链两类。完整数据上链能够使数据直接成为链上记录，便于后续查询和验证，但在日志、文件、业务数据等规模较大的场景中，会带来较高的存储成本和处理开销，也可能导致敏感信息暴露。

[017] 摘要数据上链则将原始数据保存在链下，只将哈希摘要、业务标识、提交时间和提交者等元数据写入链上。链上保存摘要、链下保存原文的模式更适合日志审计场景。但是，摘要上链模式也存在一定局限。本课题正是在这一思路下，将 SQLite 链下存储与 LogRegistry 链上哈希存证结合起来，形成面向任务日志的可信存证方案。

[018] 1.2.2 日志审计与完整性校验研究现状

[019] 日志审计是信息系统安全管理和运行维护中的重要内容。已有研究和工程实践通常围绕日志采集、集中存储、查询分析、异常检测和审计追溯展开。通过统一收集服务器、应用程序和任务执行过程中的日志，系统可以在发生异常时定位故障原因，在发生安全事件时还原操作过程，并为责任追溯提供依据。因此，日志审计不仅关注日志是否能够被记录，还关注日志是否完整、可信和可追溯。传统日志审计系统通常采用集中式日志平台或数据库保存日志数据。该方式便于统一检索、聚合分析和可视化展示，但在完整性保护方面仍存在不足。

[020] 由于日志原文和审计依据往往保存在同一管理域内，当系统权限被滥用或数据库被攻击时，日志可能被修改、删除或伪造。在完整性校验方面，哈希摘要、数字签名、时间戳和访问控制等技术常被用于增强日志可信性。此外，传统日志审计在自动化和闭环能力方面也存在不足。本课题面向上述问题，设计 Agent 自动采集、三方哈希比对和 hash_mismatch 告警机制，以提高日志审计过程的完整性和可观察性。

[021] 1.2.3 智能合约在可信审计中的应用现状

[022] 智能合约能够将预先定义的业务规则部署到区块链网络中，并按照合约逻辑自动执行。由于合约状态和交易记录可以在链上追溯，智能合约在可信审计场景中常用于固化写入规则、限定操作权限、保存证据摘要、提供查询接口和记录事件信息。相比仅依靠链下程序执行审计逻辑，智能合约可以为关键存证行为提供更加稳定的链上规则约束。在数据存证与审计场景中，智能合约通常承担证据登记和查询功能。例如，系统可以通过合约方法写入数据哈希、业务标识、提交时间和提交者地址，并通过事件记录写入结果。

[023] 后续审计时，链下系统可以根据业务标识查询链上记录，与本地数据库和重新计算的哈希进行比对。通过这种方式，智能合约成为链下业务数据与链上可信证据之间的连接层。智能合约在可信审计中的优势主要体现在三个方面。本系统中的 LogRegistry 合约即采用 AccessControl 控制 LOGGER_ROLE，只有被授权地址才能调用 storeLog 写入日志哈希。同时，智能合约应用也存在一定限制。

[024] 1.3 本文主要研究内容

[025] 本文围绕基于区块链的可信任务日志审计系统展开研究，面向传统中心化日志易被篡改、删除或伪造且审计依据不足的问题，设计并实现包含日志采集、链下存储、链上存证、审计比对、异常告警和前端展示的原型系统。主要研究内容包括以下方面。

[026] 第一，设计链上链下混合存储模型。系统将日志原文保存在 SQLite 中，将 SHA-256 哈希摘要和任务标识写入 LogRegistry 合约，以兼顾隐私保护、存储成本和审计可信性。第二，设计 LogRegistry 智能合约，保存 taskId、logHash、createdAt 和 submitter，并通过 LOGGER_ROLE 控制写入权限，提供任务维度查询能力。

[027] 第三，设计三方哈希比对审计机制。系统在审计阶段重新计算 actualHash，并与数据库 expectedHash、链上 onChainHash 进行比对，形成 passed、failed 和 pending 状态。第四，实现 Agent 自动采集、后端服务、前端展示和告警联动，并通过合约测试、批量提交、批量审计和篡改检测实验验证系统闭环可运行。

[032] 2.1 区块链与链上存证技术

[033] 区块链是一种以区块为基本组织单位、通过密码学机制和共识机制维护数据一致性的分布式账本技术。与传统中心化数据库相比，区块链不依赖单一节点保存全部可信依据，而是由多个节点共同维护账本状态。交易被确认并写入区块后，会与区块时间、交易内容、前一区块哈希等信息形成关联，后续区块继续在此基础上扩展。若试图修改历史数据，相关哈希值和区块链接关系也会发生变化，因此历史记录具有较强的不可篡改性和可追溯性。在日志审计场景中，区块链可以为链下日志提供独立的可信证明。

[034] 链上存证的思路是将关键证据写入区块链，使后续校验不完全依赖中心化数据库自身的可信性。链上存证并不意味着将完整业务数据全部写入区块链。对于本系统而言，日志原文数量较多、长度不固定，且可能包含路径、任务状态、错误信息等敏感内容，直接写入区块链会增加存储成本和隐私风险。审计阶段，系统重新计算日志原文的 actualHash，并与数据库中的 expectedHash、链上的 onChainHash 进行三方比对。

[035] 2.2 智能合约与访问控制技术

[036] 智能合约是部署在区块链上的程序化规则，能够在满足条件时自动执行，并将调用记录保存在链上。与普通后端程序相比，智能合约的执行过程和状态变化更容易被追溯，适合承担证据登记、权限校验和链上查询等任务。但合约部署后修改成本较高，因此其数据结构和权限边界需要在设计阶段明确。

[037] 访问控制是智能合约安全设计的重要内容。在日志存证场景中，若任意地址都能写入日志哈希，攻击者可能提交伪造摘要，削弱链上证据的可信性。OpenZeppelin AccessControl 提供基于角色的授权机制，可通过 DEFAULT_ADMIN_ROLE 管理角色，通过 LOGGER_ROLE 限定日志写入主体。相比自定义布尔字段，该机制接口清晰、可复用性较好，适合 LogRegistry 合约的写入权限控制。

[038] 2.3 哈希摘要与日志完整性校验技术

[039] 哈希摘要技术是日志完整性校验的重要基础。哈希函数能够将任意长度的输入数据映射为固定长度的摘要值，该摘要值通常以十六进制字符串形式表示。对于同一份输入数据，使用相同哈希算法得到的结果应保持一致；安全哈希函数通常具有单向性、抗碰撞性和雪崩效应等特点。SHA-256 是安全哈希算法家族中的常用算法之一，其输出长度为 256 位，通常表示为固定长度的十六进制字符串。系统在日志首次提交时对日志正文计算哈希，并将该哈希作为提交时的 expectedHash；后续审计时，再对当前保存的日志正文重新计算 actualHash。

[040] 如果日志内容被修改，actualHash 通常会与 expectedHash 不同。日志进入 Server 后，后端对 log_content 字段计算 SHA-256 哈希，并生成以 0x 开头的十六进制哈希值。哈希摘要技术本身并不能说明日志内容是否真实产生，也不能判断日志语义是否正确，它主要解决的是“数据是否与存证时保持一致”的问题。

[041] 2.4 系统开发相关技术

[042] 本系统除区块链、智能合约和哈希摘要技术外，还需要前端展示、后端服务、链下存储和合约开发环境共同支撑。相关开发技术并非孤立存在，而是分别服务于日志采集后的业务处理、数据保存、审计执行和结果展示。

[043] 2.4.1 React 前端框架

[044] React 是一种组件化前端开发框架，适合构建状态变化较多、页面结构可复用的 Web 应用。其核心思想是将页面拆分为多个组件，通过状态变化驱动界面更新。对于本系统而言，前端需要展示系统总览、日志中心、审计管理和告警管理等页面，不同页面中存在统计卡片、数据表格、趋势图、分布图和状态标签等可复用界面元素，因此采用 React 有助于提高页面组织的清晰度。本系统前端结合 TypeScript 和 Ant Design 使用。

[045] 2.4.2 Express 后端服务框架

[046] Express 是基于 Node.js 的轻量级 Web 服务框架，常用于构建 REST API。它提供路由、中间件和请求响应处理能力，适合实现前后端分离系统中的后端接口层。本系统需要向 Agent、Web 前端和实验脚本提供统一接口，例如日志提交、日志查询、审计触发、审计记录查询和告警查询等，因此采用 Express 作为后端服务框架。Express 后端并不只是转发请求，而是承担日志入库、哈希计算、链上写入、审计比对和告警生成等业务编排职责。

[047] 2.4.3 SQLite 数据存储技术

[048] SQLite 是一种轻量级关系型数据库，具有部署简单、无需独立数据库服务、适合本地原型系统和实验验证等特点。对于本科毕业设计系统而言，SQLite 能够在较低配置复杂度下提供结构化数据保存能力，便于保存日志、存证记录、审计记录、告警记录和 Agent 状态等信息。本系统使用 SQLite 作为链下存储层。链下数据库提供业务数据管理能力，LogRegistry 合约提供可信哈希依据，二者共同构成链上链下协同机制。SQLite 的作用是支撑系统查询、展示和审计重算，而不是替代链上存证。

[049] 2.4.4 Hardhat 智能合约开发环境

[050] Hardhat 是以太坊智能合约开发和测试环境，支持 Solidity 编译、合约部署、本地链运行和自动化测试。对于需要开发 LogRegistry 合约的系统而言，Hardhat 能够提供较完整的本地开发工具，使合约编写、调试、测试和部署过程更加方便。本系统使用 Hardhat 管理 LogRegistry 合约工程，并结合 Solidity、OpenZeppelin AccessControl 和 Ethers 完成链上存证功能。

[051] 2.5 本章小结

[052] 本章围绕系统涉及的关键技术进行了说明，主要包括区块链存证、智能合约与访问控制、哈希完整性校验，以及 React、Express、SQLite、Hardhat 等开发技术。这些内容为后续链上链下混合存储、LogRegistry 合约设计和三方哈希审计机制提供了技术基础。

[053] 第 3 章 基于区块链的可信日志存证与审计机制设计

[054] 3.1.1 链下日志存储与链上哈希存证模型

[055] 日志数据是信息系统运行过程中形成的重要证据材料，通常用于安全审计、故障排查、责任追溯和运行状态分析。在传统日志管理方式中，日志原文通常直接保存在服务器文件系统、关系型数据库或集中式日志平台中。针对上述问题，本系统采用“链下保存日志原文、链上保存日志哈希摘要”的混合存储模型。该模型并不将完整日志内容直接写入区块链，而是在日志进入系统后，由后端服务对日志原文计算 SHA-256 哈希值，再将哈希摘要以及任务标识等必要元数据写入 LogRegistry 智能合约。该设计首先能够降低链上存储成本。

[056] 日志原文通常具有数量多、长度不固定、内容变化频繁等特点，如果将完整日志直接写入区块链，不仅会增加链上存储开销，也会降低系统处理效率。从审计可信性角度看，链上哈希存证为链下日志提供了独立校验依据。此外，链上链下混合存储模型兼顾了系统效率和工程实现复杂度。LogRegistry 合约用于保存关键哈希存证，保证核心审计依据不完全依赖链下数据库。

[058] 3.1.2 日志采集、存证、审计、告警闭环流程

[059] 可信日志审计不仅需要解决日志数据如何存储的问题，还需要形成从日志产生到异常反馈的完整业务闭环。本系统围绕任务日志可信性验证目标，将日志采集、链下存储、链上存证、审计核验、异常告警和前端展示整合为一条连续流程，使日志在进入系统后能够被持续追踪，并在后续审计阶段具备可验证依据。系统流程从日志文件开始。Server 接收到日志后，首先将日志原文及其元数据写入 SQLite 数据库中的 logs 表，以便后续查询、展示和审计重算。在审计阶段，用户或系统脚本可以触发单条日志审计或批量审计任务。

[060] Server 根据待审计日志的 log_id 读取 logs 表中的日志原文，并重新计算 actualHash。当审计结果为 failed 时，系统触发异常告警流程。告警记录写入 alerts 表，告警类型为 hash_mismatch，并与对应日志记录和审计记录建立关联。从整体上看，本系统形成了“采集—存储—存证—审计—告警—展示”的可信审计闭环。

[061] Agent 解决日志自动进入系统的问题，Server 负责链下持久化、哈希计算和业务编排，LogRegistry 提供链上可信存证能力，审计模块负责完整性核验，告警模块负责异常反馈，Web 前端负责结果呈现。

[062] 图 3-2 可信日志审计闭环流程

[063] 3.2.1 日志标准化封装与任务标识设计

[064] 日志原文通常来源于不同应用、不同任务或不同运行环境，其格式、级别、时间和路径信息可能存在差异。如果系统直接对原始文本进行存储和审计，后续在查询、归类、上链和比对时会缺少统一的数据依据。日志标准化封装主要包括 taskId、sourceType、sourcePath、logContent、logLevel 和 collectedAt 等字段。其中，taskId 用于表示日志所属的业务任务或审计对象，是连接链下日志、数据库记录和链上存证记录的关键字段。上述字段中，taskId 是最核心的业务关联字段。

[065] 任务标识还能够支持日志归集和审计回溯。对于多次部署或历史合约地址回溯场景，taskId 与 contract_address 等字段共同构成审计定位依据，有助于提高审计过程的准确性。在实际任务执行过程中，同一任务可能产生多条日志。如果每条日志缺少统一的任务标识，系统只能以单条日志为单位进行孤立处理，不利于任务维度的追踪和统计。

[067] 3.2.2 SHA-256 日志摘要生成方法

[068] 日志完整性校验的核心在于判断日志内容在存储和审计过程中是否发生变化。哈希函数能够将任意长度的数据映射为固定长度的摘要值，当输入内容发生变化时，输出摘要也会随之改变。在日志提交阶段，Server 接收到 Agent 上报的日志数据后，会读取其中的 logContent 或数据库字段 log_content，并以 UTF-8 编码方式输入 SHA-256 哈希函数。在审计阶段，系统再次读取 logs 表中的日志原文，并使用相同的 SHA-256 计算方式生成 actualHash。

[069] 若日志内容自提交后未发生改变，则审计阶段重新计算得到的 actualHash 应与提交阶段保存的 expectedHash 一致，也应与链上查询得到的 onChainHash 保持一致。需要注意的是，哈希摘要本身并不负责保存日志语义，也不能直接说明日志内容是否真实发生过某个业务事件。

[070] 3.2.3 链上存证字段与链下记录映射关系

[071] 本系统采用链下业务数据与链上摘要数据相互映射的方式组织日志证据。logs 表保存日志原文及采集来源，是审计时重新计算 actualHash 的基础；log_hash_records 表保存提交阶段生成的 log_hash、contract_address、transaction_hash、block_number 和 on_chain_status 等信息；LogRegistry 合约保存 taskId、logHash、createdAt 和 submitter，形成链上存证依据。

[072] 其中，logs.id 与 log_hash_records.log_id 对应，用于将日志原文和哈希记录关联起来；task_id 对应链上 taskId，用于按任务归集日志；log_hash 对应链上 logHash，用于后续完整性比对；contract_address 记录写入时使用的合约地址，支持历史合约地址回溯；transaction_hash 和 block_number 用于定位链上交易和区块；on_chain_status 表示上链结果。

[073] 通过上述映射关系，系统能够在审计阶段同时取得日志原文、数据库哈希和链上哈希。若 expectedHash、actualHash 和 onChainHash 一致，则说明链上链下证据匹配；若不一致，则可进一步结合交易哈希、区块号和合约地址定位异常来源。表 3-1 链上链下字段映射关系

[074] 3.3.1 合约数据结构设计

[075] LogRegistry 合约以 LogRecord 结构体保存链上日志存证信息，主要字段包括 taskId、logHash、createdAt 和 submitter。taskId 表示任务标识，用于将同一任务产生的多条日志归集；logHash 表示日志内容经 SHA-256 计算后的摘要，是后续完整性校验的核心字段；createdAt 记录链上写入时间；submitter 记录提交该日志哈希的账户地址。

[076] 合约内部通过 records 数组保存全部 LogRecord，并以数组下标或记录编号支持单条记录查询。为提高任务维度查询效率，合约还维护 taskIdToRecordIds 映射，将同一 taskId 对应的记录编号集中保存。审计时，系统既可以通过记录编号查询单条链上存证，也可以根据 taskId 获取某一任务下的全部链上记录。

[077] 该数据结构没有保存日志原文，只保存必要摘要和元数据，能够降低链上存储压力，也避免敏感日志内容直接暴露。records 数组保证全局记录可追溯，taskIdToRecordIds 映射支持任务维度审计，两者共同满足日志编号查询和任务回溯查询需求。

[078] 3.3.2 基于 AccessControl 的写入权限控制

[079] 日志存证合约不能允许任意地址写入。如果链上写入缺少权限限制，攻击者或无关账户可能提交伪造 taskId 和 logHash，导致链上记录与真实日志无关，从而影响审计依据的可信性。因此，LogRegistry 合约需要在写入入口设置安全边界，只允许受信任的日志提交主体调用 storeLog。

[080] 本系统基于 OpenZeppelin AccessControl 实现角色控制。DEFAULT_ADMIN_ROLE 用于管理角色授权，LOGGER_ROLE 用于控制日志哈希写入权限。后端服务使用具备 LOGGER_ROLE 的账户调用 storeLog，将日志哈希写入链上；未获得该角色的账户即使知道合约地址和方法，也不能完成有效写入。

[081] 与自定义权限字段相比，AccessControl 提供成熟的角色管理接口和事件记录，便于授权、撤销和审计。该设计将链下业务系统的提交行为与链上权限边界对应起来，使 LogRegistry 合约不仅保存证据摘要，也能够限制可信写入来源。

[082] 3.3.3 日志哈希写入与任务维度查询方法

[083] LogRegistry 合约在数据结构和权限控制的基础上，提供日志哈希写入与任务维度查询方法，用于支撑链上存证和后续审计读取。合约方法设计围绕两个目标展开：一是能够安全地将日志哈希写入链上，形成不可轻易篡改的存证记录；二是能够根据任务标识查询相关链上记录，使后端审计服务能够定位待审计日志对应的链上哈希。日志哈希写入主要通过 storeLog(taskId, logHash) 方法完成。该方法接收任务标识和日志哈希两个参数，并要求调用者具备 LOGGER_ROLE。在完成写入后，合约触发 LogStored 事件。

[084] 除写入方法外，LogRegistry 还提供多种查询方法。在审计阶段，任务维度查询方法具有直接作用。后端服务会根据待审计日志的 task_id 连接对应 LogRegistry 合约，并调用 getLogsByTaskId(taskId) 获取该任务下的链上记录。因此，storeLog 方法负责将日志哈希写入链上，查询方法负责在审计阶段提供链上证据读取能力，事件机制则增强链上写入过程的可追踪性。三者共同构成 LogRegistry 合约的核心操作接口，使系统能够围绕任务标识完成日志存证、查询和审计比对。

[086] 3.4.1 数据库哈希、链上哈希与重算哈希三方比对

[087] 三方哈希比对是本系统审计机制的核心。系统在日志提交阶段计算日志内容的 SHA-256 摘要，并将该值写入 log_hash_records，作为 expectedHash；同时将对应哈希写入 LogRegistry 合约，形成链上 onChainHash。审计阶段，系统再次读取 logs 表中的日志原文并重新计算 actualHash。

[088] 审计逻辑以 expectedHash、actualHash 和 onChainHash 的一致性为判断依据。若三者完全一致，说明当前日志原文、数据库存证记录和链上存证记录相互匹配，审计结果为 passed。若 actualHash 与 expectedHash 不一致，说明链下日志原文可能被修改；若 expectedHash 与 onChainHash 不一致，则说明数据库记录与链上存证存在差异，审计结果为 failed。

[089] 当链上记录缺失、合约地址不可用或链上查询结果不完整时，系统不直接判定日志被篡改，而是将结果置为 pending，并保留审计说明。该设计能够区分内容篡改、证据缺失和链上环境异常，避免单一数据库校验带来的可信性不足。

[091] 3.4.2 历史合约地址回溯审计策略

[092] 在区块链应用系统中，合约地址是定位链上数据的重要依据。对于生产环境中长期稳定运行的合约而言，系统通常可以通过固定配置读取合约地址。本系统在实验和开发过程中考虑了这一问题，并采用基于历史合约地址的回溯审计策略。日志哈希每次写入链上后，后端不仅保存 log_hash 和 transaction_hash，还会在 log_hash_records 表中保存本次写入实际使用的 contract_address。这种设计能够解决多次部署带来的历史记录审计问题。

[093] 例如，在本地 Hardhat 环境中，开发者可能重新启动节点或重新部署 LogRegistry 合约。历史合约地址回溯策略还能够增强实验结果的可复现性。将 contract_address 与每条哈希记录绑定后，审计过程可以明确说明该日志写入了哪个合约，审计时又查询了哪个合约，从而减少因环境变化导致的误判。需要说明的是，历史合约地址回溯并不改变链上存证本身的结构，而是在后端审计逻辑中增强链上读取策略。它属于工程实现层面的可靠性改进，主要用于解决多次部署、本地链重启和历史记录查询不一致等问题。

[094] 3.4.3 合约代码存在性校验机制

[095] 在本地 Hardhat 链和多次部署场景中，合约地址的有效性会直接影响审计结果。若本地链重启，原合约地址可能不再存在字节码；若系统仍按照旧地址执行写入或查询，可能造成空地址误判，使实验结果缺少可靠依据。因此，系统在链上读写前增加合约代码存在性校验，将地址有效性检查作为链上交互的前置步骤。

[096] 具体而言，系统通过 Ethers 的 provider.getCode(address) 读取目标地址上的合约字节码。若返回结果表明该地址不存在合约代码，系统不继续执行写入或查询，而是将相关链上记录视为不可用状态，并在审计中进入 pending 或异常说明流程。该机制能够避免本地链重启后仍使用历史地址造成误判，也使合约部署状态与审计结果之间的关系更加清晰。

[097] 合约代码存在性校验并不改变 LogRegistry 的业务逻辑，而是增强链上交互的健壮性。通过在写入和读取前确认目标地址确实部署了合约，系统能够降低错误配置、链重启和地址失效对实验结果的影响，从而提高可信日志审计闭环的可复现性和说明力。

[098] 3.5.1 审计状态判定规则

[099] 系统将审计结果划分为 passed、failed 和 pending 三种状态。passed 表示 expectedHash、actualHash 与 onChainHash 完全一致，说明日志原文、数据库哈希和链上哈希能够相互印证。该状态下，系统将审计记录写入 audit_records，并保留审计时间和说明信息。

[100] failed 表示审计过程中发现明确不一致。典型情况包括 actualHash 与 expectedHash 不一致，说明 logs 表中的日志内容可能被修改；或者 expectedHash 与 onChainHash 不一致，说明链下存证记录与链上记录不匹配。此时系统会生成 failed 审计记录，并触发 hash_mismatch 告警。

[101] pending 表示当前证据不足以得出最终结论，常见于链上记录缺失、合约地址不可用或合约代码不存在等情况。pending 不等同于审计通过，而是提示需要补充链上证据或检查部署环境。表 3-2 审计状态判定规则

[102] 3.5.2 哈希不一致告警生成流程

[103] 审计状态判定完成后，系统需要将发现的异常转化为可追踪、可展示的告警记录。为提高异常发现效率，本系统在审计结果为 failed 时自动生成 hash_mismatch 类型告警，将日志完整性异常从审计结果转化为告警事件，形成从检测到提示的闭环流程。哈希不一致告警的生成入口位于审计执行流程。

[104] 当系统完成 expectedHash、actualHash 和 onChainHash 的比对后，如果判定结果为 failed，后端服务会先创建一条审计记录，将 audit_status、expected_hash、actual_hash 和 audit_message 等信息写入 audit_records 表。在 alerts 表中，alert_type 用于标识告警类型。本系统当前使用 hash_mismatch 表示哈希不一致告警，说明该告警由日志哈希校验失败触发。告警标题和描述用于提高前端展示的可读性。

[105] 标题通常概括风险对象，例如提示某一任务存在篡改风险；哈希不一致告警生成流程体现了本系统从审计检测到风险提示的闭环。

[109] 4.2 系统需求分析

[110] 本系统面向任务日志可信审计场景，核心目标是使日志从产生、采集、存储、存证到审计和告警的全过程具备可追溯性和可验证性。传统日志系统通常能够完成日志保存和查询，但在日志被篡改、删除或伪造时，缺少独立可信的校验依据。因此，本系统的功能需求不仅包括一般日志系统中的采集、存储和展示能力，还需要围绕区块链可信存证、哈希完整性校验、异常告警和可视化审计构建完整能力。从用户使用角度看，系统需要支持日志自动进入审计流程，减少人工导入带来的遗漏和不一致；

[111] 4.2.1 日志自动采集需求

[112] 日志自动采集是系统可信审计流程的起点。若日志进入系统依赖人工复制或手动提交，不仅效率较低，也容易出现遗漏、重复或时间不一致等问题。为保证任务日志能够及时纳入审计范围，系统需要提供自动采集能力，使日志文件产生新增内容后能够被 Agent 识别并提交至后端服务。从功能角度看，Agent 需要能够读取指定日志文件，并基于偏移量记录方式识别新增日志内容，避免重复采集已处理的历史日志。为提高采集过程的可靠性，系统还需要支持失败重试和状态同步能力。日志自动采集需求直接支撑可信审计链路的完整性。

[113] 4.2.2 链上可信存证需求

[114] 链上可信存证是本系统区别于传统日志管理系统的重要需求。传统日志系统通常将日志原文和审计依据都保存在中心化数据库中，一旦数据库中的日志或哈希记录被修改，系统难以提供独立证据说明日志是否保持原始状态。从系统能力角度看，链上存证不要求直接保存完整日志原文，而是保存日志哈希、任务标识、写入时间和提交者地址等必要信息。后端服务在接收日志并计算 SHA-256 哈希后，应调用 LogRegistry 智能合约完成上链写入，并记录交易哈希、区块号、合约地址和链上状态。链上可信存证需求为后续审计比对提供了外部证据来源。

[115] 4.2.3 审计校验需求

[116] 审计校验是系统判断日志是否可信的核心功能。日志完成采集和存证后，系统需要在用户触发或系统执行审计任务时，对日志内容进行重新核验。从系统流程看，审计校验需要读取待审计日志原文，重新计算 actualHash；读取 log_hash_records 表中的 expectedHash；再根据任务标识和合约地址查询 LogRegistry 合约中的 onChainHash。审计校验需求要求系统不仅返回即时结果，还要将审计状态、期望哈希、实际哈希和审计说明写入 audit_records 表。

[117] 4.2.4 异常告警需求

[118] 日志审计系统不仅需要发现异常，还需要将异常以明确方式提示给用户。如果系统只在审计接口中返回 failed 状态，用户可能需要主动查看审计列表才能发现问题，异常响应不够直观。因此，本系统需要具备异常告警能力，在审计发现哈希不一致时自动生成告警记录，并通过前端页面进行展示。异常告警需求主要针对审计状态为 failed 的情况。当系统判断日志重算哈希与数据库或链上存证不一致时，应生成 hash_mismatch 类型告警，并将该告警与对应日志记录和审计记录关联。告警需求能够将底层哈希比对结果转化为面向用户的风险提示。

[119] 4.2.5 可视化展示需求

[120] 可信日志审计结果需要通过直观方式呈现给用户，才能支持日常查看、问题定位和答辩演示。系统后端虽然能够完成日志存储、链上写入和审计比对，但如果缺少前端展示，用户难以快速理解系统运行状态。因此，本系统需要提供 Web 可视化界面，集中展示日志、审计和告警相关信息。从功能需求看，前端需要提供系统总览页面，用于展示日志数量、审计通过情况、异常告警数量等统计指标；还需要提供告警管理页面，用于展示 hash_mismatch 告警及其处理状态。可视化展示需求不仅服务于用户交互，也有助于验证系统闭环是否完整。

[121] 4.3 非功能需求分析

[122] 除功能需求外，可信任务日志审计系统还需要满足数据可信性、系统可用性、可维护性与可扩展性等非功能需求。非功能需求决定系统在实际运行和后续扩展中的稳定性，也影响论文实验和答辩演示过程中的可复现性。

[123] 4.3.1 数据可信性需求

[124] 数据可信性是本系统最核心的非功能需求。在链下部分，SQLite 保存日志原文、存证记录、审计记录和告警记录，使系统能够查询和展示完整业务数据。在链上部分，LogRegistry 保存日志哈希和任务标识，为审计提供独立校验依据。审计阶段，系统通过 expectedHash、actualHash 和 onChainHash 的三方比对判断日志是否一致。因此，数据可信性需求不仅体现在区块链不可篡改特性上，也体现在链上链下字段映射、哈希生成规则、审计状态判定和异常告警记录等多个环节的协同设计中。

[125] 4.3.2 系统可用性需求

[126] 系统可用性要求用户能够稳定地完成日志提交、审计执行、告警查看和结果展示等操作。对于本系统而言，可用性不仅体现在前端页面能否访问，还体现在日志采集、后端接口、数据库读写和链上交互能否形成稳定闭环。若任一环节不可用，系统就难以完成可信日志审计目标。在日志采集侧，Agent 需要支持增量读取、失败重试和状态同步，以降低临时异常对日志提交的影响。在后端服务侧，系统需要提供日志提交、审计执行、告警查询和总览统计等接口，使前端能够稳定获取数据。此外，系统可用性还体现在验证和演示过程的可重复性上。

[127] 4.3.3 可维护性与可扩展性需求

[128] 可维护性要求系统结构清晰、模块职责明确，便于后续修改、调试和论文说明。本系统采用模块化 Monorepo 结构，将前端 Web、后端 Server、采集 Agent、智能合约和共享类型库放在同一仓库下统一管理。不同模块在目录和职责上独立，能够降低代码耦合度，也便于在论文中说明系统分层设计。后端服务采用 routes、controllers、services、repositories、db 和 blockchain 等分层结构。

[129] 可扩展性方面，当前系统虽然基于 SQLite 和本地 Hardhat 链实现，但整体结构为后续扩展预留了空间。
