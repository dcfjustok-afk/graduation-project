1: 摘要
2: 随着信息系统在业务处理和自动化任务中的广泛应用，日志数据已成为安全审计、故障排查和责任追溯的重要依据。传统中心化日志存储方式虽然便于查询和管理，但日志原文及审计依据集中保存，存在被篡改、删除或伪造后难以及时发现的问题。针对上述问题，本文设计并实现了一种基于区块链的可信任务日志审计系统。系统采用“链下保存日志原文、链上保存日志哈希摘要”的混合存储模型，由 Agent 完成日志增量采集，Server 负责日志入库、SHA-256 哈希计算和 LogRegistry 智能合约调用，SQLite 保存日志、存证、审计和告警记录，Web 前端展示日志、审计和告警结果。审计阶段，系统重新计算日志原文得到 actualHash，并与数据库中的 expectedHash、链上的 onChainHash 进行三方比对；当哈希不一致时，生成 failed 审计记录和 hash_mismatch 告警。实验结果表明，LogRegistry 合约测试 8 项全部通过；日志批量提交 100 次成功率为 100%，平均响应时间约 107.03 ms，吞吐量约 9.33 条/秒；批量审计 100、500、1000 条数据 5 轮均成功；篡改检测实验能够识别日志内容被修改并生成告警。结果说明，该系统能够形成从采集、存证、审计到告警展示的可信日志审计闭环。
3: 关键词：区块链；日志审计；智能合约；哈希校验；可信存证；异常告警
4: Abstract
5: With the widespread use of information systems in business processing and automated tasks, log data has become an important basis for security auditing, fault diagnosis, and responsibility tracing. Traditional centralized log storage is convenient for query and management, but log contents and audit evidence are usually maintained in the same trusted domain. Once logs are tampered with, deleted, or forged, it is difficult to provide independent and reliable evidence for subsequent auditing. To address this problem, this thesis designs and implements a trusted task log auditing system based on blockchain. The system adopts a hybrid storage model in which original logs are stored off-chain and log hash digests are stored on-chain. The Agent module performs incremental log collection, the Server module handles log persistence, SHA-256 hash calculation, and interaction with the LogRegistry smart contract, SQLite stores logs, evidence records, audit records, alerts, and agent states, and the Web frontend visualizes logs, audit results, and alert information. During the audit process, the system recalculates the hash of the current log content as actualHash, reads expectedHash from the database, and obtains onChainHash from the smart contract. A three-party hash comparison is then performed to determine whether the log remains consistent with its evidence record. If an inconsistency is detected, the system generates a failed audit record and a hash_mismatch alert. Experimental results show that all eight smart contract tests passed. In the log submission experiment, 100 submissions were completed successfully with an average response time of about 107.03 ms and a throughput of about 9.33 records per second. Batch audit experiments on 100, 500, and 1000 records were completed successfully in five rounds, and the tamper detection experiment identified modified log content and generated an alert. The results indicate that the proposed system can form a trusted audit loop covering log collection, evidence storage, audit verification, alert generation, and frontend visualization.
6: Keywords: blockchain; log auditing; smart contract; hash verification; trusted evidence storage; anomaly alert
7: 第 1 章 绪论
8: 1.1 研究背景及意义
9: 随着信息系统在政务服务、企业管理、在线交易、自动化运维和数据处理任务中的广泛应用，系统运行过程中会持续产生大量日志数据。日志记录了任务执行过程、接口调用结果、异常错误、用户操作和系统状态变化等信息，是安全审计、故障排查、责任追溯和运行分析的重要依据。当系统发生异常或安全事件时，日志往往是定位问题来源、还原操作过程和判断责任边界的重要证据。因此，日志数据的真实性、完整性和可追溯性直接影响后续审计结论的可信程度。
10: 传统日志管理方式多采用中心化存储模式，日志原文通常保存在服务器文件系统、数据库或集中日志平台中。这种方式具有部署简单、查询方便、与业务系统集成成本较低等优点，但在可信审计场景下也存在明显不足。首先，中心化日志存储依赖管理权限和数据库安全策略，一旦攻击者获得较高权限，可能对日志内容进行修改、删除或伪造。其次，内部人员误操作或恶意操作也可能导致关键日志缺失，使审计过程难以还原真实事件。再次，当日志原文、审计记录和校验依据都保存在同一中心化系统中时，一旦该系统被破坏，后续审计结论缺少独立可信依据。
11: 在此背景下，如何增强日志数据的防篡改能力和审计可验证性，成为日志审计系统设计中的重要问题。区块链具有不可篡改、可追溯和交易记录公开可验证等特点，适合保存关键数据摘要和存证元数据。哈希摘要技术能够将日志原文映射为固定长度的内容指纹，日志内容一旦被修改，重新计算得到的哈希值通常会发生变化。将区块链存证与哈希校验结合，可以为链下日志提供独立校验依据，使审计过程不完全依赖中心化数据库自身的可信性。
12: 本课题围绕“基于区块链的可信任务日志审计系统设计与实现”展开，目标是构建一个从日志采集、链下存储、链上存证、审计比对、异常告警到前端展示的完整原型系统。系统采用“链下保存日志原文、链上保存日志哈希摘要”的混合存储方式，在降低链上存储成本和保护日志内容隐私的同时，为日志完整性校验提供可信依据。审计阶段通过 expectedHash、actualHash 和 onChainHash 的三方比对，判断日志内容是否与存证时保持一致，并在发现异常时生成 hash_mismatch 告警。
13: 本课题具有一定的理论意义和工程意义。从理论层面看，课题将区块链存证、哈希摘要和日志完整性校验结合起来，围绕可信日志审计形成较清晰的机制设计。从工程层面看，系统实现了 Agent 增量采集、Express 后端服务、SQLite 链下存储、LogRegistry 智能合约、审计告警和 React 前端展示等模块，能够验证可信日志审计闭环的可运行性。该研究可为小规模任务日志审计、教学实验和可信存证原型设计提供参考。
14: 1.2 国内外研究现状
15: 近年来，围绕数据可信存证、日志审计和智能合约可信管理的研究不断发展。区块链存证研究主要关注如何利用链上不可篡改和可追溯特性保存关键证据，日志审计研究主要关注日志采集、集中存储、完整性校验和异常追溯，智能合约研究则为链上规则固化、权限控制和证据查询提供了可执行载体。三类研究方向相互关联，共同为可信日志审计系统提供了理论与工程基础。
16: 已有研究通常认为，区块链适合保存数据摘要而非大规模原文，哈希函数适合用于校验链下数据是否被修改，智能合约适合将写入规则和查询接口固化在链上。这些研究为本课题采用“链下保存日志原文、链上保存日志哈希摘要”的设计提供了参考。但从工程落地角度看，现有方案仍存在一些不足，例如完整数据上链可能导致存储成本较高，日志采集过程自动化不足，链上存证、链下存储、审计比对和异常告警之间缺少完整闭环，可视化展示与告警追踪能力也有待加强。
17: 因此，本课题在已有研究基础上，进一步面向任务日志审计场景，设计并实现包含 Agent 自动采集、Server 后端处理、SQLite 链下存储、LogRegistry 合约存证、三方哈希比对和 Web 前端展示的原型系统，重点验证可信日志审计机制在工程闭环中的可行性。
18: 1.2.1 区块链存证技术研究现状
19: 区块链存证技术是区块链在数据可信证明领域的重要应用方向。相关研究表明，区块链由于具备账本共享、记录可追溯和历史数据难以篡改等特点，可以用于保存电子证据、数据摘要、交易凭证和关键操作记录。在数据完整性保护场景中，区块链常被用作外部可信记录载体，为链下数据提供时间顺序和摘要校验依据。
20: 从存证方式看，常见方案主要包括完整数据上链和摘要数据上链两类。完整数据上链能够使数据直接成为链上记录，便于后续查询和验证，但在日志、文件、业务数据等规模较大的场景中，会带来较高的存储成本和处理开销，也可能导致敏感信息暴露。摘要数据上链则将原始数据保存在链下，只将哈希摘要、业务标识、提交时间和提交者等元数据写入链上。后续验证时，系统重新计算链下数据哈希，并与链上哈希进行比对，从而判断数据是否发生变化。
21: 链上保存摘要、链下保存原文的模式更适合日志审计场景。日志数据通常数量较多、内容变化频繁，并且可能包含路径、错误信息、任务状态等敏感内容。如果将日志原文全部写入区块链，不仅会增加链上存储压力，还可能影响隐私保护。采用摘要上链方式，可以在保留链下查询效率的同时，为日志内容提供不可随意修改的校验依据。
22: 但是，摘要上链模式也存在一定局限。区块链只能证明某个哈希值在某一时刻被写入链上，不能单独证明链下原文最初是否真实、采集过程是否完整。因此，可信日志审计系统还需要结合自动采集、链下数据库、权限控制和审计比对机制。本课题正是在这一思路下，将 SQLite 链下存储与 LogRegistry 链上哈希存证结合起来，形成面向任务日志的可信存证方案。
23: 1.2.2 日志审计与完整性校验研究现状
24: 日志审计是信息系统安全管理和运行维护中的重要内容。已有研究和工程实践通常围绕日志采集、集中存储、查询分析、异常检测和审计追溯展开。通过统一收集服务器、应用程序和任务执行过程中的日志，系统可以在发生异常时定位故障原因，在发生安全事件时还原操作过程，并为责任追溯提供依据。因此，日志审计不仅关注日志是否能够被记录，还关注日志是否完整、可信和可追溯。
25: 传统日志审计系统通常采用集中式日志平台或数据库保存日志数据。该方式便于统一检索、聚合分析和可视化展示，但在完整性保护方面仍存在不足。由于日志原文和审计依据往往保存在同一管理域内，当系统权限被滥用或数据库被攻击时，日志可能被修改、删除或伪造。若缺少独立校验机制，审计人员很难判断日志内容是否保持原始状态，审计结论的可信度也会受到影响。
26: 在完整性校验方面，哈希摘要、数字签名、时间戳和访问控制等技术常被用于增强日志可信性。哈希摘要可以将日志内容转换为固定长度指纹，数字签名可以证明数据来源，时间戳可以辅助确定事件发生顺序。然而，如果这些校验记录仍然只保存在中心化数据库中，一旦数据库被整体篡改，校验依据也可能同时失效。因此，如何为日志校验记录提供独立可信存储，是日志完整性保护中的关键问题。
27: 此外，传统日志审计在自动化和闭环能力方面也存在不足。一些方案重视日志集中存储和查询，但对日志采集过程中的增量读取、失败重试、审计结果写入、异常告警和前端展示关注不够。部分系统能够发现异常，但缺少与告警记录、审计记录和可视化页面的联动。本课题面向上述问题，设计 Agent 自动采集、三方哈希比对和 hash_mismatch 告警机制，以提高日志审计过程的完整性和可观察性。
28: 1.2.3 智能合约在可信审计中的应用现状
29: 智能合约能够将预先定义的业务规则部署到区块链网络中，并按照合约逻辑自动执行。由于合约状态和交易记录可以在链上追溯，智能合约在可信审计场景中常用于固化写入规则、限定操作权限、保存证据摘要、提供查询接口和记录事件信息。相比仅依靠链下程序执行审计逻辑，智能合约可以为关键存证行为提供更加稳定的链上规则约束。
30: 在数据存证与审计场景中，智能合约通常承担证据登记和查询功能。例如，系统可以通过合约方法写入数据哈希、业务标识、提交时间和提交者地址，并通过事件记录写入结果。后续审计时，链下系统可以根据业务标识查询链上记录，与本地数据库和重新计算的哈希进行比对。通过这种方式，智能合约成为链下业务数据与链上可信证据之间的连接层。
31: 智能合约在可信审计中的优势主要体现在三个方面。第一，合约规则公开可验证，便于审计人员理解数据如何写入链上。第二，权限控制可以限制关键写入行为，避免任意地址提交伪造记录。第三，链上记录和事件具有可追溯性，便于后续定位交易和提交者。本系统中的 LogRegistry 合约即采用 AccessControl 控制 LOGGER_ROLE，只有被授权地址才能调用 storeLog 写入日志哈希。
32: 与此同时，智能合约应用也存在一定限制。合约部署后修改成本较高，设计阶段需要谨慎确定数据结构和权限边界；链上交易存在一定性能开销，不适合承载大量日志原文；合约代码若存在安全缺陷，可能影响存证结果可信性。因此，本课题仅将日志哈希和必要元数据写入链上，并在后端加入合约代码存在性校验和历史合约地址回溯机制，以降低本地实验环境中合约地址变化带来的误判风险。
33: 1.3 本文主要研究内容
34: 本文围绕基于区块链的可信任务日志审计系统展开研究，重点面向传统中心化日志容易被篡改、删除或伪造，审计结果缺少可信依据的问题，设计并实现一个包含日志采集、链下存储、链上存证、审计比对、异常告警和前端展示的原型系统。研究过程既关注可信审计机制设计，也关注系统工程实现和实验验证之间的对应关系。本文主要研究内容包括以下几个方面。
35: 第一，设计链上链下混合存储模型。针对日志原文数量多、内容可能敏感、直接上链成本较高的问题，系统采用链下保存日志原文、链上保存日志哈希摘要的方式。SQLite 用于保存 logs、log_hash_records、audit_records、alerts 和 agent_states 等业务数据，LogRegistry 智能合约用于保存日志哈希和任务标识等摘要证据。该模型兼顾链下查询效率、链上可信校验和日志隐私保护。
36: 第二，设计并实现 LogRegistry 智能合约。合约保存 taskId、logHash、createdAt 和 submitter 等字段，通过 LOGGER_ROLE 控制日志哈希写入权限，并提供 storeLog、getLog、getRecordIdsByTaskId、getLogsByTaskId、getTaskLogCount 和 getLogCount 等方法。该合约为日志哈希存证和任务维度查询提供链上支撑。
37: 第三，设计三方哈希比对审计机制。系统在日志提交阶段生成 expectedHash 并写入数据库和链上；在审计阶段重新计算日志原文得到 actualHash，并读取链上 onChainHash。通过 expectedHash、actualHash 和 onChainHash 的比对，系统将审计结果判定为 passed、failed 或 pending。当发现哈希不一致时，系统生成 hash_mismatch 类型告警。
38: 第四，实现 Agent 自动采集与后端服务。Agent 模块支持日志文件增量读取、偏移量持久化、失败重试和状态同步；Server 后端负责日志接收、SQLite 入库、SHA-256 哈希计算、LogRegistry 合约调用、审计执行和告警生成。前端基于 React、TypeScript 和 Ant Design 展示系统总览、日志列表、审计结果和告警信息。
39: 第五，完成系统功能测试、性能实验和篡改检测验证。实验结果表明，LogRegistry 合约测试 8 项全部通过，日志批量提交 100 次全部成功，平均响应时间约 107.03 ms，吞吐量约 9.33 条/秒；批量审计 100、500、1000 条数据 5 轮全部成功，平均耗时约 3067.77 ms、15659.44 ms、35032.13 ms；篡改检测实验能够识别日志内容被修改并生成 failed 审计记录和告警。
40: 1.4 论文组织结构
41: 本文围绕基于区块链的可信任务日志审计系统设计与实现展开，共分为六章，各章内容安排如下。
42: 第 1 章为绪论。本章介绍课题研究背景及意义，分析日志审计在安全审计、故障排查和责任追溯中的作用，说明传统中心化日志在可信性方面存在的不足；同时概述区块链存证、日志审计与智能合约可信管理相关研究现状，明确本文主要研究内容和论文组织结构。
43: 第 2 章为相关理论与关键技术。本章介绍区块链与链上存证技术、智能合约与访问控制技术、哈希摘要与日志完整性校验技术，以及 React、Express、SQLite、Hardhat 等系统开发相关技术，为后续系统机制设计和工程实现提供技术基础。
44: 第 3 章为基于区块链的可信日志存证与审计机制设计。本章是全文核心章节，重点说明链上链下混合存储模型、日志标准化封装、SHA-256 日志摘要生成、LogRegistry 合约设计、三方哈希比对、历史合约地址回溯、合约代码存在性校验以及篡改检测与异常告警机制。

51: 2.1 区块链与链上存证技术
52: 区块链是一种以区块为基本组织单位、通过密码学机制和共识机制维护数据一致性的分布式账本技术。与传统中心化数据库相比，区块链不依赖单一节点保存全部可信依据，而是由多个节点共同维护账本状态。交易被确认并写入区块后，会与区块时间、交易内容、前一区块哈希等信息形成关联，后续区块继续在此基础上扩展。若试图修改历史数据，相关哈希值和区块链接关系也会发生变化，因此历史记录具有较强的不可篡改性和可追溯性。
53: 在日志审计场景中，区块链可以为链下日志提供独立的可信证明。传统日志通常保存在服务器文件系统或数据库中，如果日志原文、审计记录和校验依据都由同一中心化系统维护，一旦数据库被修改或日志文件被删除，审计过程可能缺少可信依据。链上存证的思路是将关键证据写入区块链，使后续校验不完全依赖中心化数据库自身的可信性。
54: 链上存证并不意味着将完整业务数据全部写入区块链。更常见的方式是将业务数据的哈希摘要、业务标识、提交者地址和时间信息等写入链上。当需要验证链下数据是否被修改时，系统重新计算链下数据哈希，并与链上保存的哈希进行比对。若两者一致，说明待验证数据与存证时内容保持一致；若不一致，则说明链下数据可能发生变化，需要进一步审计。
55: 对于本系统而言，日志原文数量较多、长度不固定，且可能包含路径、任务状态、错误信息等敏感内容，直接写入区块链会增加存储成本和隐私风险。因此，本系统采用“链下保存日志原文、链上保存日志哈希摘要”的方式。日志进入 Server 后，系统对日志正文计算 SHA-256 哈希，并将 taskId 与 logHash 写入 LogRegistry 智能合约。SQLite 保存日志原文、哈希记录、审计记录和告警信息，链上记录保存不可随意修改的摘要证据。
56: 审计阶段，系统重新计算日志原文的 actualHash，并与数据库中的 expectedHash、链上的 onChainHash 进行三方比对。通过这种设计，链下数据库提供查询效率和业务完整性，区块链提供可信校验依据。需要说明的是，区块链不能自动保证链下日志最初内容一定真实，它主要证明某一时刻写入链上的哈希记录后续不易被篡改。因此，在本系统中，区块链技术主要服务于日志哈希存证和审计追溯，为可信任务日志审计机制提供基础支撑。
57: 2.2 智能合约与访问控制技术
58: 智能合约是部署在区块链网络中的程序化合约，能够按照预先定义的规则自动执行，并将执行结果和状态变化记录在链上。与传统后端程序相比，智能合约具有公开可验证、执行过程可追溯、部署后难以随意修改等特点，适合用于实现规则明确且结果需要可信记录的业务逻辑。在链上存证场景中，智能合约不仅负责保存数据，还负责规定数据如何写入、由谁写入以及如何查询。
59: 日志哈希存证需要结构化的链上记录。如果仅依赖普通交易附带数据，系统在字段组织、权限控制和查询能力方面会受到限制。通过智能合约，可以将日志存证记录设计为包含 taskId、logHash、createdAt 和 submitter 的结构化数据，并提供按记录编号或任务标识查询的方法。这样，后端审计流程可以稳定读取链上存证信息，并将链上记录与数据库中的日志记录进行对应。
60: 访问控制是智能合约设计中的重要安全机制。由于区块链上的合约方法可能被不同地址调用，如果日志存证合约允许任意地址写入，攻击者或无关用户就可能提交伪造哈希，污染链上存证记录，进而影响审计结果。因此，日志哈希写入方法必须设置明确的权限边界，只有被授权的后端服务地址或系统账户才能执行写入操作。
61: OpenZeppelin AccessControl 是常用的角色权限控制组件。它通过角色标识与账户授权关系实现权限管理，典型角色包括 DEFAULT_ADMIN_ROLE 和自定义业务角色。DEFAULT_ADMIN_ROLE 通常用于管理角色授权和撤销，业务角色用于限定具体功能的调用权限。在本系统中，LogRegistry 合约通过 LOGGER_ROLE 控制日志写入权限，只有具备 LOGGER_ROLE 的地址才能调用 storeLog 写入日志哈希。
62: 与简单使用单个 owner 字段相比，AccessControl 的角色模型更清晰，也更便于扩展多个写入主体。LOGGER_ROLE 明确了可信写入边界，DEFAULT_ADMIN_ROLE 则负责管理该角色的授予关系。需要注意的是，访问控制的重点并不是阻止所有链上数据被查看，而是控制关键写入行为。通过将智能合约的自动执行、链上可验证性和 AccessControl 权限控制结合起来，本系统能够为 LogRegistry 合约设计和可信日志审计机制提供较清晰的理论基础。
63: 2.3 哈希摘要与日志完整性校验技术
64: 哈希摘要技术是日志完整性校验的重要基础。哈希函数能够将任意长度的输入数据映射为固定长度的摘要值，该摘要值通常以十六进制字符串形式表示。对于同一份输入数据，使用相同哈希算法得到的结果应保持一致；而当输入内容发生变化时，计算得到的摘要值也会随之变化。因此，哈希摘要可以作为数据内容的“指纹”，用于判断文件、消息或日志记录是否被修改。
65: 安全哈希函数通常具有单向性、抗碰撞性和雪崩效应等特点。单向性是指从输入数据计算哈希值较为容易，但难以根据哈希值反推出原始输入内容。抗碰撞性是指难以找到两份不同数据，使它们计算得到相同哈希结果。雪崩效应是指输入内容即使只发生很小变化，例如增加一个字符、修改一个时间戳或删除一个空格，输出哈希值也会发生显著变化。上述特性使哈希函数适合用于完整性校验，而不是用于还原原始数据。
66: SHA-256 是安全哈希算法家族中的常用算法之一，其输出长度为 256 位，通常表示为固定长度的十六进制字符串。在日志完整性校验场景中，SHA-256 的作用是将日志原文转换为稳定的摘要值。系统在日志首次提交时对日志正文计算哈希，并将该哈希作为提交时的 expectedHash；后续审计时，再对当前保存的日志正文重新计算 actualHash。如果日志内容没有变化，两次计算结果应保持一致；如果日志内容被修改，actualHash 通常会与 expectedHash 不同。
67: 在本系统中，日志进入 Server 后，后端对 log_content 字段计算 SHA-256 哈希，并生成以 0x 开头的十六进制哈希值。该哈希值一方面保存到 log_hash_records 表中，另一方面写入 LogRegistry 智能合约，形成链上存证。审计阶段，系统重新读取 logs 表中的日志原文并再次计算哈希，然后与数据库记录和链上记录进行比对。由于哈希函数对输入内容变化非常敏感，日志正文一旦被修改，即使修改幅度很小，重新计算得到的 actualHash 也会发生变化，从而暴露完整性异常。
68: 哈希摘要技术本身并不能说明日志内容是否真实产生，也不能判断日志语义是否正确，它主要解决的是“数据是否与存证时保持一致”的问题。因此，本系统将哈希摘要与链上存证、链下数据库和审计记录结合使用。SQLite 保存日志原文和 expectedHash，LogRegistry 保存 onChainHash，审计服务重新计算 actualHash。三者共同构成完整性校验依据，使系统能够在日志内容被篡改时生成 failed 审计结果和 hash_mismatch 告警。
69: 2.4 系统开发相关技术
70: 本系统除区块链、智能合约和哈希摘要技术外，还需要前端展示、后端服务、链下存储和合约开发环境共同支撑。相关开发技术并非孤立存在，而是分别服务于日志采集后的业务处理、数据保存、审计执行和结果展示。本节从 React、Express、SQLite 和 Hardhat 四个方面说明其在系统中的作用。
71: 2.4.1 React 前端框架
72: React 是一种组件化前端开发框架，适合构建状态变化较多、页面结构可复用的 Web 应用。其核心思想是将页面拆分为多个组件，通过状态变化驱动界面更新。对于本系统而言，前端需要展示系统总览、日志中心、审计管理和告警管理等页面，不同页面中存在统计卡片、数据表格、趋势图、分布图和状态标签等可复用界面元素，因此采用 React 有助于提高页面组织的清晰度。
73: 本系统前端结合 TypeScript 和 Ant Design 使用。TypeScript 用于约束日志记录、审计记录、告警记录和总览统计等数据结构，减少前后端字段不一致带来的问题；Ant Design 提供表格、卡片、按钮、标签和统计数值等基础组件，便于较快构建管理类界面。前端通过 API 客户端调用后端接口，将日志、审计和告警数据转换为可视化结果，从而支撑系统运行状态展示。
74: 2.4.2 Express 后端服务框架
75: Express 是基于 Node.js 的轻量级 Web 服务框架，常用于构建 REST API。它提供路由、中间件和请求响应处理能力，适合实现前后端分离系统中的后端接口层。本系统需要向 Agent、Web 前端和实验脚本提供统一接口，例如日志提交、日志查询、审计触发、审计记录查询和告警查询等，因此采用 Express 作为后端服务框架。
76: 在本系统中，Express 后端并不只是转发请求，而是承担日志入库、哈希计算、链上写入、审计比对和告警生成等业务编排职责。项目通过 routes、controllers、services、repositories、db 和 blockchain 等分层结构组织代码，使接口处理、业务逻辑、数据库访问和合约交互相互分离。该方式有助于提高后端代码的可维护性，也便于在论文实验中验证不同接口和审计分支。
77: 2.4.3 SQLite 数据存储技术
78: SQLite 是一种轻量级关系型数据库，具有部署简单、无需独立数据库服务、适合本地原型系统和实验验证等特点。对于本科毕业设计系统而言，SQLite 能够在较低配置复杂度下提供结构化数据保存能力，便于保存日志、存证记录、审计记录、告警记录和 Agent 状态等信息。
79: 本系统使用 SQLite 作为链下存储层。logs 表保存日志原文和来源信息，log_hash_records 表保存日志哈希和链上交易信息，audit_records 表保存审计结果，alerts 表保存异常告警，agent_states 表保存采集端运行状态。SQLite 的作用是支撑系统查询、展示和审计重算，而不是替代链上存证。链下数据库提供业务数据管理能力，LogRegistry 合约提供可信哈希依据，二者共同构成链上链下协同机制。
80: 2.4.4 Hardhat 智能合约开发环境
81: Hardhat 是以太坊智能合约开发和测试环境，支持 Solidity 编译、合约部署、本地链运行和自动化测试。对于需要开发 LogRegistry 合约的系统而言，Hardhat 能够提供较完整的本地开发工具，使合约编写、调试、测试和部署过程更加方便。
82: 本系统使用 Hardhat 管理 LogRegistry 合约工程，并结合 Solidity、OpenZeppelin AccessControl 和 Ethers 完成链上存证功能。Hardhat 本地链用于实验环境中的合约部署和交易验证，测试脚本用于验证合约写入权限、日志哈希存储和任务维度查询等功能。后端通过 Ethers 连接已部署的 LogRegistry 合约，调用 storeLog 写入哈希，并在审计阶段读取链上记录。由于本地链可能重启，系统还加入合约代码存在性校验和历史合约地址回溯，以提高实验过程的可靠性。

85: 随后，本章介绍了哈希摘要与日志完整性校验技术。SHA-256 能够将日志正文转换为固定长度摘要值，日志内容一旦被修改，重新计算得到的 actualHash 会发生变化，从而为日志篡改检测提供基础。最后，本章从 React、Express、SQLite 和 Hardhat 四个方面说明了系统开发相关技术，分别对应前端展示、后端服务、链下存储和智能合约开发环境。

87: 第 3 章 基于区块链的可信日志存证与审计机制设计
88: 3.1.1 链下日志存储与链上哈希存证模型
89: 日志数据是信息系统运行过程中形成的重要证据材料，通常用于安全审计、故障排查、责任追溯和运行状态分析。在传统日志管理方式中，日志原文通常直接保存在服务器文件系统、关系型数据库或集中式日志平台中。这种中心化存储方式具有实现简单、查询方便、维护成本较低等优点，但在可信审计场景下也存在明显不足。一旦具备较高权限的内部人员、系统管理员或攻击者能够访问日志存储位置，就可能对日志内容进行修改、删除或伪造。由于日志数据和审计依据都依赖同一中心化存储环境，系统在事后很难证明日志是否保持原始状态，审计结果也缺少独立可信的证据支撑。
90: 针对上述问题，本系统采用“链下保存日志原文、链上保存日志哈希摘要”的混合存储模型。该模型并不将完整日志内容直接写入区块链，而是在日志进入系统后，由后端服务对日志原文计算 SHA-256 哈希值，再将哈希摘要以及任务标识等必要元数据写入 LogRegistry 智能合约。日志原文仍保存在 SQLite 数据库中，用于后续查询、展示和审计重算。区块链负责保存日志摘要形式的存证记录，作为链下日志完整性的可信校验依据。其基本结构如图 3-1 所示。
91: 图 3-1 链上链下混合存储模型
92: 该设计首先能够降低链上存储成本。日志原文通常具有数量多、长度不固定、内容变化频繁等特点，如果将完整日志直接写入区块链，不仅会增加链上存储开销，也会降低系统处理效率。相比之下，哈希摘要长度固定，能够以较小的数据规模代表日志原文的完整性特征，更适合作为链上存证对象。其次，该设计能够降低敏感信息暴露风险。任务日志中可能包含路径、状态、错误信息或业务上下文，若直接上链，数据一旦公开将难以删除或修改。采用链下保存原文、链上保存摘要的方式，可以在保留可验证性的同时减少隐私泄露风险。
93: 从审计可信性角度看，链上哈希存证为链下日志提供了独立校验依据。日志首次提交时，系统将原始日志计算得到的哈希写入链上；后续审计时，系统重新读取链下日志原文并再次计算哈希。如果链下日志未被篡改，则重算哈希应与数据库中保存的哈希以及链上存证哈希保持一致。若日志原文被修改，即使修改幅度较小，重新计算得到的哈希值也会发生变化，从而在比对过程中暴露异常。因此，该模型能够在不改变日志链下存储和查询方式的基础上，为日志完整性提供可追溯、可验证的证明。
94: 此外，链上链下混合存储模型兼顾了系统效率和工程实现复杂度。SQLite 用于保存日志原文、审计记录、告警记录和 Agent 状态，便于系统进行快速查询和页面展示；LogRegistry 合约用于保存关键哈希存证，保证核心审计依据不完全依赖链下数据库。二者通过 taskId、log_id、log_hash 和 contract_address 等字段建立关联，使系统能够在日志采集、存储、存证和审计之间形成稳定的数据映射关系。由此可见，该模型既保留了传统数据库在数据管理方面的便利性，又利用区块链增强了日志审计结果的可信度，是本系统可信日志审计机制的基础。
95: 3.1.2 日志采集、存证、审计、告警闭环流程
96: 可信日志审计不仅需要解决日志数据如何存储的问题，还需要形成从日志产生到异常反馈的完整业务闭环。本系统围绕任务日志可信性验证目标，将日志采集、链下存储、链上存证、审计核验、异常告警和前端展示整合为一条连续流程，使日志在进入系统后能够被持续追踪，并在后续审计阶段具备可验证依据。
97: 系统流程从日志文件开始。应用系统或任务执行过程产生新的日志内容后，Agent 日志采集模块负责读取本地日志文件中的新增部分。为避免重复采集，Agent 通过偏移量记录方式维护上次读取位置，仅采集追加产生的新日志内容。采集到的日志会被封装为标准数据结构，其中包含任务标识、日志来源、日志级别、采集时间和日志原文等信息。随后，Agent 将封装后的日志提交给 Server 后端服务。
98: Server 接收到日志后，首先将日志原文及其元数据写入 SQLite 数据库中的 logs 表，以便后续查询、展示和审计重算。完成链下入库后，Server 对日志原文执行 SHA-256 哈希计算，生成能够代表日志内容完整性的哈希摘要。该哈希摘要随后被传入 LogRegistry 智能合约的 storeLog 方法，与任务标识一同写入链上。链上写入完成后，系统会在 log_hash_records 表中保存对应的链上存证信息，包括日志哈希、合约地址、交易哈希、区块号以及链上状态。至此，系统完成了从日志采集到链上存证的前半段流程。
99: 在审计阶段，用户或系统脚本可以触发单条日志审计或批量审计任务。Server 根据待审计日志的 log_id 读取 logs 表中的日志原文，并重新计算 actualHash。同时，系统从 log_hash_records 表中读取该日志提交时保存的 expectedHash 以及对应的 contract_address，再根据任务标识从 LogRegistry 合约中查询链上记录，获得 onChainHash。随后，系统对 actualHash、expectedHash 和 onChainHash 进行比对。当三者一致时，说明链下日志内容与原始存证记录保持一致，系统生成 passed 状态的审计记录；当重新计算的哈希与数据库或链上记录不一致时，说明日志可能被篡改，系统生成 failed 状态的审计记录。
100: 当审计结果为 failed 时，系统进一步触发异常告警流程。告警记录写入 alerts 表，告警类型为 hash_mismatch，并与对应日志记录和审计记录建立关联。告警信息包括告警标题、描述、严重程度和处理状态，用于提示用户该日志存在完整性风险。前端 Web 模块通过后端接口获取日志列表、审计结果和告警信息，并在总览页、日志中心、审计管理和告警管理页面进行展示。这样，用户不仅能够查看日志是否已经完成存证，还能够观察审计通过、失败或待定等状态，并及时发现潜在篡改风险。
101: 图 3-2 可信日志审计闭环流程
102: 从整体上看，本系统形成了“采集—存储—存证—审计—告警—展示”的可信审计闭环。Agent 解决日志自动进入系统的问题，Server 负责链下持久化、哈希计算和业务编排，LogRegistry 提供链上可信存证能力，审计模块负责完整性核验，告警模块负责异常反馈，Web 前端负责结果呈现。各模块围绕日志哈希这一核心证据建立关联，使日志在采集后能够被追溯，在被修改后能够被识别，在发现异常后能够被提示。该闭环流程是后续日志哈希模型、智能合约设计和链上链下协同审计机制展开的基础。
103: 3.2.1 日志标准化封装与任务标识设计
104: 日志原文通常来源于不同应用、不同任务或不同运行环境，其格式、级别、时间和路径信息可能存在差异。如果系统直接对原始文本进行存储和审计，后续在查询、归类、上链和比对时会缺少统一的数据依据。因此，在日志进入可信审计流程之前，需要对日志进行标准化封装，使其具备稳定的数据结构和明确的业务归属关系。本系统在 Agent 采集和 Server 接收阶段，将日志内容封装为包含任务标识、来源信息、日志内容、日志级别和采集时间等字段的标准数据对象。
105: 在本系统中，日志标准化封装主要包括 taskId、sourceType、sourcePath、logContent、logLevel 和 collectedAt 等字段。其中，taskId 用于表示日志所属的业务任务或审计对象，是连接链下日志、数据库记录和链上存证记录的关键字段。sourceType 用于描述日志来源类型，例如日志来自 Agent 采集或其他提交入口。sourcePath 用于记录日志文件路径或来源位置，便于后续定位日志产生环境。logContent 保存日志原文，是进行哈希计算和审计重算的基础。logLevel 用于表示日志级别，例如 INFO、WARN 或 ERROR，便于前端展示和筛选。collectedAt 用于记录日志采集时间，帮助系统分析日志产生和进入审计系统的时间关系。
106: 表 3-1 日志标准化封装字段说明
107: 上述字段中，taskId 是最核心的业务关联字段。在链下数据库中，logs 表通过 task_id 保存任务标识，log_hash_records 表也保存相同的 task_id，从而将日志原文记录与哈希存证记录对应起来。在链上合约中，LogRegistry 同样以 taskId 作为日志记录的重要字段，并通过任务标识建立从任务到链上记录编号的映射关系。这样，系统在审计阶段可以根据同一 taskId 查询某个任务下的全部链上存证记录，并进一步判断待审计日志是否存在对应的链上哈希。
108: 任务标识还能够支持日志归集和审计回溯。在实际任务执行过程中，同一任务可能产生多条日志。如果每条日志缺少统一的任务标识，系统只能以单条日志为单位进行孤立处理，不利于任务维度的追踪和统计。通过 taskId，系统可以将同一任务下的日志、哈希记录、审计记录和告警信息关联起来，使前端能够按任务查看日志状态，也使后端能够在审计时定位对应的链上记录。对于多次部署或历史合约地址回溯场景，taskId 与 contract_address 等字段共同构成审计定位依据，有助于提高审计过程的准确性。
109: 因此，日志标准化封装并不是简单的数据整理步骤，而是可信审计链路能够稳定运行的前提。通过统一字段结构，系统可以在日志采集、数据库存储、链上存证、审计比对和前端展示之间保持一致的数据语义，减少因日志格式差异导致的处理复杂度，为后续哈希生成和链上链下字段映射提供基础。
110: 3.2.2 SHA-256 日志摘要生成方法
111: 日志完整性校验的核心在于判断日志内容在存储和审计过程中是否发生变化。哈希函数能够将任意长度的数据映射为固定长度的摘要值，当输入内容发生变化时，输出摘要也会随之改变。因此，哈希摘要常用于文件完整性校验、数据存证和审计比对等场景。本系统采用 SHA-256 算法对日志原文进行摘要计算，将日志内容转换为固定长度的十六进制哈希值，并以该哈希值作为链上存证和后续审计比对的核心依据。
112: 在日志提交阶段，Server 接收到 Agent 上报的日志数据后，会读取其中的 logContent 或数据库字段 log_content，并以 UTF-8 编码方式输入 SHA-256 哈希函数。计算结果被转换为十六进制字符串，并添加 0x 前缀，以便与以太坊生态中常见的 bytes32 类型和十六进制表示方式保持一致。该哈希值随后被保存到 log_hash_records 表中，同时作为参数传入 LogRegistry.storeLog(taskId, logHash) 方法写入链上。由于链上仅保存哈希摘要而不保存日志原文，系统能够在减少链上数据量的同时保留日志完整性校验能力。
113: 在审计阶段，系统再次读取 logs 表中的日志原文，并使用相同的 SHA-256 计算方式生成 actualHash。若日志内容自提交后未发生改变，则审计阶段重新计算得到的 actualHash 应与提交阶段保存的 expectedHash 一致，也应与链上查询得到的 onChainHash 保持一致。若链下日志原文被人为修改，即使只改变一个字符，重新计算得到的哈希值也会与原始哈希产生明显差异，从而在三方比对过程中被识别出来。
114: 需要注意的是，哈希摘要本身并不负责保存日志语义，也不能直接说明日志内容是否真实发生过某个业务事件。它的作用是为某一时刻的日志内容生成唯一性较强的完整性标识。换言之，系统通过哈希值证明“当前链下日志是否与当时存证的日志内容一致”，而不是通过哈希值直接判断业务行为是否合法。因此，在本系统中，SHA-256 日志摘要主要承担完整性校验和链上存证索引作用，与 taskId、contract_address、audit_records 等字段共同支撑可信审计流程。
115: 采用 SHA-256 进行日志摘要生成还能够提高系统实现的一致性。日志提交和审计重算都使用同一计算规则，避免了不同模块采用不同摘要格式导致的比对误差。只要日志原文编码、哈希算法和输出格式保持一致，系统就能够稳定地在数据库、链上合约和审计逻辑之间传递哈希值，为后续三方哈希比对提供可靠基础。
116: 3.2.3 链上存证字段与链下记录映射关系
117: 链上存证机制要发挥作用，必须与链下数据库记录建立明确的映射关系。若链上哈希记录无法准确对应到链下日志原文，审计阶段就难以判断某一条日志是否存在有效存证。因此，本系统在数据库表设计和智能合约设计中同时保留任务标识、日志哈希和合约地址等关键字段，用于建立 logs、log_hash_records 与 LogRegistry 链上记录之间的对应关系。
118: 在链下数据库中，logs 表负责保存日志原文及其来源信息，是审计重算 actualHash 的数据来源。该表中的 id 字段是链下日志记录的唯一编号，task_id 表示日志所属任务，log_content 保存日志原文，source_type、source_path、log_level 和 collected_at 则用于描述日志来源、级别和采集时间。logs 表本身不直接保存链上交易信息，而是通过 id 与 log_hash_records 表中的 log_id 建立关联。
119: log_hash_records 表负责保存日志哈希及链上写入信息，是连接链下日志和链上存证的中间表。其中，log_id 对应 logs 表中的日志主键，说明该条哈希记录属于哪一条日志；task_id 与 logs 表中的 task_id 保持一致，用于任务维度查询；log_hash 保存提交阶段计算得到的日志哈希，也就是审计阶段的 expectedHash；contract_address 保存该哈希实际写入的 LogRegistry 合约地址；transaction_hash 记录链上写入交易；block_number 记录交易所在区块；on_chain_status 表示链上写入状态。通过这些字段，系统不仅能够知道某条日志的原始哈希，还能够追踪该哈希写入了哪个合约、对应哪笔交易以及写入是否成功。
120: 在链上合约中，LogRegistry 的 LogRecord 结构体保存 taskId、logHash、createdAt 和 submitter。taskId 与链下 task_id 对应，用于按任务查询链上日志记录；logHash 与 log_hash_records.log_hash 对应，是日志完整性校验的核心值；createdAt 记录链上写入时的区块时间戳，可作为存证时间参考；submitter 记录执行写入操作的钱包地址，用于确认链上记录的提交来源。合约还通过 taskIdToRecordIds 映射维护任务标识与链上记录编号之间的关系，使后端在审计时能够根据 taskId 查询同一任务下的链上哈希记录。
121: 表 3-1 链上链下字段映射关系
122: 这种字段映射关系使审计流程具备可追溯性。审计某条日志时，系统先根据 log_id 找到 logs 表中的日志原文，再根据 log_id 查询最新的 log_hash_records 记录，获得 expectedHash 和 contract_address。随后，系统使用 contract_address 连接对应的 LogRegistry 合约，并根据 task_id 查询链上记录，判断链上是否存在与 expectedHash 匹配的 logHash。若链下重算得到的 actualHash 与 expectedHash 和链上 logHash 均一致，则说明该日志在链下保存期间未发生内容变化。
123: 此外，contract_address 字段在历史审计场景中具有重要意义。本地链或测试环境中可能存在多次部署合约的情况，如果审计时只读取当前环境变量中的合约地址，可能无法正确查询旧日志对应的链上记录。通过在 log_hash_records 表中保存实际写入时的合约地址，系统可以在审计阶段回溯到对应历史合约，提高审计结果的准确性。因此，链上存证字段与链下记录映射不仅是数据关联设计，也是保证可信审计结果可复现的重要基础。
124: 3.3.1 合约数据结构设计
125: LogRegistry 智能合约是本系统链上存证机制的核心组成部分，其主要作用是保存日志哈希及相关元数据，为后续审计提供可追溯的链上证据。由于区块链存储成本较高，并且链上数据一旦写入后不宜修改，本系统在合约数据结构设计时遵循“字段必要、结构清晰、便于查询”的原则，只保存与日志可信审计直接相关的信息，不将日志原文写入链上。合约中的核心数据结构为 LogRecord，该结构体用于描述单条日志的链上存证记录。
126: LogRecord 结构体主要包含 taskId、logHash、createdAt 和 submitter 四个字段。taskId 表示日志所属的业务任务标识，是链上记录与链下日志记录之间建立业务关联的关键字段。在系统运行过程中，同一任务可能对应多条日志记录，因此 taskId 不仅用于说明日志来源于哪个任务，也用于支持后续按任务维度查询链上存证。通过该字段，后端审计服务能够根据某一任务标识读取该任务下的链上日志哈希记录，并与链下数据库中的日志记录进行匹配。
127: logHash 字段用于保存日志原文经过 SHA-256 计算后得到的哈希摘要，是链上存证记录中最核心的字段。系统不在链上保存 logContent 原文，而是保存 logHash，用较小的数据量代表日志内容的完整性特征。后续审计时，系统会对链下保存的日志原文重新计算哈希，并将重算结果与链上 logHash 进行比对。如果日志内容在链下被修改，则重新计算得到的哈希值会与链上存证记录不一致，从而暴露篡改风险。
128: createdAt 字段用于记录日志哈希写入链上时的区块时间戳。该字段并不表示日志实际产生时间，而是表示该条存证记录被写入区块链的时间。它可以为后续审计提供时间参考，使系统能够说明某条日志哈希在何时完成链上存证。submitter 字段用于记录执行链上写入操作的钱包地址。在本系统中，日志哈希通常由后端服务账户写入链上，submitter 能够帮助确认该条存证记录的提交来源，并配合权限控制机制说明写入行为是否来自授权角色。
129: 除 LogRecord 结构体外，LogRegistry 合约还通过 records 数组保存全部链上日志存证记录。每当 storeLog 方法成功写入一条日志哈希时，合约都会将新的 LogRecord 追加到 records 数组中，数组下标即可作为该条链上记录的 recordId。通过这种方式，合约能够支持基于记录编号的单条查询，后续可通过 getLog(recordId) 读取指定编号的链上记录。
130: 为了支持任务维度的查询，合约还设计了 taskIdToRecordIds 映射。该映射以 taskId 为键，以 recordId 列表为值，用于记录某一任务下所有链上日志记录的编号。当一条日志哈希写入合约时，系统不仅会将 LogRecord 添加到 records 数组中，还会把对应 recordId 加入 taskIdToRecordIds[taskId]。这样，后端服务在审计某个任务时，可以先通过任务标识获得该任务下所有链上记录编号，再进一步读取对应的日志哈希。该设计避免了遍历全部 records 数组，提高了按任务查询链上存证记录的便利性。
131: 总体而言，LogRegistry 的数据结构设计围绕日志可信审计需求展开。LogRecord 提供单条存证记录的基本信息，records 数组支持全局记录编号查询，taskIdToRecordIds 映射支持任务维度的链上记录定位。三者共同构成了系统链上存证的数据基础，为后续日志哈希写入、任务维度查询和三方哈希比对提供支撑。
132: 3.3.2 基于 AccessControl 的写入权限控制
133: 日志存证合约的可信性不仅取决于链上数据难以篡改，还取决于写入链上数据的主体是否可信。如果智能合约允许任意地址调用日志写入方法，攻击者或无关用户就可能向合约中写入伪造的 taskId 和 logHash，造成链上存证记录被污染。即使链上数据本身不可篡改，若写入入口没有权限约束，系统后续审计时也可能面对大量无效或恶意的存证记录，影响审计结果的可靠性。因此，LogRegistry 合约必须对日志哈希写入操作进行访问控制，确保只有被授权的账户能够执行存证写入。
134: 本系统采用 OpenZeppelin 提供的 AccessControl 机制实现合约权限管理。AccessControl 是 Solidity 智能合约开发中常用的角色访问控制组件，能够通过角色标识区分不同权限主体，并提供角色授予、撤销和权限校验能力。相比在合约中自行维护布尔类型权限字段，AccessControl 具有结构清晰、复用性强、接口成熟等优点，适合在毕业设计原型系统中实现可解释、可验证的权限边界。
135: 在 LogRegistry 合约中，LOGGER_ROLE 表示允许写入日志存证记录的角色。storeLog 方法被设计为只有具备 LOGGER_ROLE 的地址才能调用。该角色通常可以授予后端服务使用的钱包账户，由后端在接收日志、计算哈希后统一发起链上写入。这样，日志哈希上链行为由系统后端进行控制，避免任意外部地址直接向合约提交不可信数据。通过 LOGGER_ROLE，系统将链上写入入口限定在可信服务范围内，使链上记录更符合审计业务语义。
136: DEFAULT_ADMIN_ROLE 则用于管理角色授权。部署合约时，管理员地址获得 DEFAULT_ADMIN_ROLE，并具备授予或撤销 LOGGER_ROLE 的权限。该设计使系统能够区分“权限管理者”和“日志写入者”两类角色：管理员负责角色配置，日志写入账户负责执行实际存证操作。二者职责分离有助于提高合约权限模型的清晰性，也便于在论文中说明系统安全边界。
137: 采用 AccessControl 还能够提高合约行为的可测试性。合约测试可以分别验证授权账户是否能够成功调用 storeLog，未授权账户是否会被拒绝，以及角色授予后权限是否生效。这种测试方式比自定义权限字段更加规范，也更便于与 OpenZeppelin 的成熟实现保持一致。同时，由于 AccessControl 在智能合约生态中应用广泛，其权限语义相对明确，能够降低自定义实现中出现权限绕过或逻辑遗漏的风险。
138: 从系统整体角度看，基于 AccessControl 的权限控制是链上可信存证机制的重要组成部分。日志哈希写入链上后具有较强的不可篡改性，但只有写入来源可信，链上记录才具有审计价值。LOGGER_ROLE 限定了写入主体，DEFAULT_ADMIN_ROLE 管理角色授权，两者共同构成了 LogRegistry 的访问控制边界。通过该机制，系统能够在链上存证环节减少无效写入和恶意写入风险，为后续审计比对提供更可靠的链上数据来源。
139: 3.3.3 日志哈希写入与任务维度查询方法
140: LogRegistry 合约在数据结构和权限控制的基础上，进一步提供日志哈希写入与任务维度查询方法，用于支撑链上存证和后续审计读取。合约方法设计围绕两个目标展开：一是能够安全地将日志哈希写入链上，形成不可轻易篡改的存证记录；二是能够根据任务标识查询相关链上记录，使后端审计服务能够定位待审计日志对应的链上哈希。
141: 日志哈希写入主要通过 storeLog(taskId, logHash) 方法完成。该方法接收任务标识和日志哈希两个参数，并要求调用者具备 LOGGER_ROLE。写入前，合约需要对参数进行基本校验，确保 taskId 不为空，logHash 不为零值。这样的校验可以避免无效任务标识或空哈希被写入链上，减少无意义存证记录。参数校验通过后，合约以当前 records 数组长度作为新记录的 recordId，并将包含 taskId、logHash、createdAt 和 submitter 的 LogRecord 追加到 records 数组中。同时，合约会将该 recordId 加入 taskIdToRecordIds[taskId]，建立任务标识与链上记录编号之间的映射关系。
142: 在完成写入后，合约触发 LogStored 事件。事件中包含 recordId、taskId、logHash、submitter 和 createdAt 等信息，用于记录链上写入行为。虽然本系统当前主要通过后端接口和数据库记录进行展示，但事件机制仍具有重要意义。它能够为后续扩展链上事件监听、前端链上记录展示或审计追踪提供基础，也使日志存证行为在链上具备更清晰的可观察性。
143: 除写入方法外，LogRegistry 还提供多种查询方法。getLog(recordId) 用于根据记录编号读取单条链上存证记录，适合在已经知道 recordId 的情况下定位具体日志。getRecordIdsByTaskId(taskId) 用于返回某一任务标识下的全部记录编号，使后端能够先获取记录编号列表，再按需查询具体记录。getLogsByTaskId(taskId) 则直接返回某一任务下的完整 LogRecord 列表，便于后端审计服务一次性读取任务相关链上哈希。getTaskLogCount(taskId) 用于统计指定任务下的链上日志数量，getLogCount() 用于统计合约中全部存证记录数量。
144: 表 3-2 LogRegistry 合约方法说明
145: 在审计阶段，任务维度查询方法具有直接作用。后端服务会根据待审计日志的 task_id 连接对应 LogRegistry 合约，并调用 getLogsByTaskId(taskId) 获取该任务下的链上记录。随后，系统从返回结果中提取 logHash，并判断数据库中保存的 expectedHash 是否能够在链上记录中找到对应项。如果链上记录中存在匹配哈希，则说明该日志提交时确实完成了链上存证；若链上记录缺失或不匹配，则系统需要结合本地重算哈希进一步判断审计状态。
146: 因此，storeLog 方法负责将日志哈希写入链上，查询方法负责在审计阶段提供链上证据读取能力，事件机制则增强链上写入过程的可追踪性。三者共同构成 LogRegistry 合约的核心操作接口，使系统能够围绕任务标识完成日志存证、查询和审计比对。
147: 3.4.1 数据库哈希、链上哈希与重算哈希三方比对
148: 链上存证的最终目的在于为日志完整性审计提供可信依据。单独保存日志原文或单独保存链上哈希都不足以完成完整审计，系统需要在审计阶段将链下数据库记录、链上存证记录和当前日志内容重新计算结果进行联合比对。本系统将该过程设计为数据库哈希、链上哈希与重算哈希的三方比对机制，通过 expectedHash、actualHash 和 onChainHash 三个值判断日志是否保持一致。
149: expectedHash 表示系统在日志提交阶段计算并保存的期望哈希，来源于 log_hash_records 表中的 log_hash 字段。当日志首次进入系统时，Server 对日志原文计算 SHA-256 哈希，并将该值写入 log_hash_records 表。因此，expectedHash 可以理解为系统在日志入库和上链时保存的原始摘要记录。它位于链下数据库中，便于后端快速读取和审计记录关联。
150: actualHash 表示审计阶段对当前日志原文重新计算得到的实际哈希。审计服务会根据待审计日志的 log_id 读取 logs 表中的 log_content，并使用与提交阶段相同的 SHA-256 规则生成 actualHash。该值反映的是审计发生时链下日志原文的当前状态。如果日志原文自提交后未被修改，actualHash 应当与 expectedHash 保持一致；如果日志内容被篡改、删除后重写或被伪造，则 actualHash 会与原始 expectedHash 不一致。
151: onChainHash 表示从 LogRegistry 合约中读取到的链上哈希记录。系统会根据 log_hash_records 中保存的 contract_address 连接对应合约，并根据 task_id 查询该任务下的链上记录，从中提取 logHash 字段。由于链上记录写入后难以被随意修改，onChainHash 在审计中承担独立可信证据的作用。它用于证明某条日志在提交时是否已经将对应哈希写入链上。
152: 图 3-3 三方哈希比对流程
153: 三方比对的基本逻辑是：当 expectedHash、actualHash 和 onChainHash 三者一致时，说明链下日志当前内容、数据库保存的原始哈希记录以及链上存证记录相互匹配，系统可以判定审计通过，生成 passed 状态的审计记录。当 actualHash 与 expectedHash 不一致时，说明当前日志原文与提交阶段保存的哈希不匹配，存在链下日志被修改的风险。如果此时链上记录仍能匹配 expectedHash，则更能说明当前链下日志已经偏离原始存证内容，系统应判定为 failed。当 expectedHash 存在但链上记录暂不可用或未匹配到对应哈希时，系统可根据实际情况标记为 pending 或 failed，以区分链上证据缺失与日志内容异常。
154: 三方哈希比对机制的优势在于，它不是单纯依赖数据库自身进行校验，而是引入链上记录作为外部可信依据。即使链下 logs 表中的日志原文被篡改，只要 log_hash_records 或链上存证记录仍保留原始哈希，审计阶段就可以通过重新计算哈希发现异常。同时，如果链下数据库中的存证记录也出现不一致，链上 LogRegistry 中的记录仍可作为追溯依据。通过这种方式，系统在中心化存储之外增加了可信校验维度，提高了审计结果的可靠性。
155: 本系统在生成审计结果时，会将 expectedHash、actualHash、审计状态和审计说明写入 audit_records 表，并在失败情况下生成异常告警。这使三方比对不仅停留在计算层面，还能转化为可查询、可展示、可追踪的审计结果。由此，数据库哈希、链上哈希与重算哈希三方比对构成了本系统可信日志审计机制的核心判定方法。
156: 3.4.2 历史合约地址回溯审计策略
157: 在区块链应用系统中，合约地址是定位链上数据的重要依据。对于生产环境中长期稳定运行的合约而言，系统通常可以通过固定配置读取合约地址。但在毕业设计原型系统、本地 Hardhat 链环境或频繁部署测试场景中，合约地址可能随着部署过程发生变化。如果审计服务始终只读取当前环境变量中的最新合约地址，就可能无法正确查询历史日志对应的链上存证记录，从而影响审计结果的准确性。
158: 本系统在实验和开发过程中考虑了这一问题，并采用基于历史合约地址的回溯审计策略。日志哈希每次写入链上后，后端不仅保存 log_hash 和 transaction_hash，还会在 log_hash_records 表中保存本次写入实际使用的 contract_address。该字段记录的是日志存证发生时对应的 LogRegistry 合约地址，而不是审计时系统当前配置的合约地址。审计阶段，系统优先读取该日志哈希记录中的 contract_address，并使用该地址创建链上读取客户端，查询对应历史合约中的存证记录。
159: 这种设计能够解决多次部署带来的历史记录审计问题。例如，在本地 Hardhat 环境中，开发者可能重新启动节点或重新部署 LogRegistry 合约。此时，新的合约地址可能与旧日志写入时的地址不同。如果审计旧日志时只连接最新合约地址，系统可能无法查询到旧日志对应的 onChainHash，从而将原本已经完成存证的日志误判为链上记录缺失或审计待定。通过保存并使用 log_hash_records.contract_address，系统能够回到该日志实际写入时的合约地址进行查询，提高历史日志审计的可追溯性。
160: 历史合约地址回溯策略还能够增强实验结果的可复现性。毕业设计系统通常需要多次执行部署、验证和性能测试，如果不同轮次实验使用了不同合约实例，而系统没有记录每条日志对应的合约地址，就难以解释旧数据审计结果为何发生变化。将 contract_address 与每条哈希记录绑定后，审计过程可以明确说明该日志写入了哪个合约，审计时又查询了哪个合约，从而减少因环境变化导致的误判。
161: 从数据关系角度看，contract_address 是连接链下存证记录和链上合约实例的关键字段。task_id 能够定位任务维度的链上记录，log_hash 能够定位具体日志摘要，而 contract_address 则定位这些记录所在的合约实例。三者结合后，系统才能准确完成“哪条日志、属于哪个任务、写入哪个合约”的审计追溯过程。
162: 需要说明的是，历史合约地址回溯并不改变链上存证本身的结构，而是在后端审计逻辑中增强链上读取策略。它属于工程实现层面的可靠性改进，主要用于解决多次部署、本地链重启和历史记录查询不一致等问题。通过该策略，系统能够更准确地处理不同部署时期产生的日志记录，提升可信审计流程的稳定性。
163: 3.4.3 合约代码存在性校验机制
164: 区块链合约调用的前提是目标地址上确实部署了合约代码。在本地 Hardhat 链或测试环境中，节点重启、链状态重置或合约重新部署都可能导致原有合约地址不再包含有效字节码。如果系统仍然按照旧地址执行链上读写操作，就可能出现交易或查询过程表面执行，但实际并未与预期的 LogRegistry 合约交互的情况。对于可信日志审计系统而言，这类问题会影响链上存证和审计结果的真实性，因此需要在链上读写前增加合约代码存在性校验。
165: 本系统采用 provider.getCode(address) 对目标合约地址进行校验。该方法可以读取指定地址上的链上字节码。如果返回结果为空或仅为 0x，则说明该地址当前没有部署合约代码，不能作为有效的 LogRegistry 合约地址使用。此时，系统应停止后续链上写入或查询，并给出明确错误提示，而不是继续执行可能产生误导结果的操作。通过这种方式，系统能够在链上交互开始前发现合约地址失效问题。
166: 合约代码存在性校验首先用于日志哈希写入阶段。Server 在调用 LogRegistry.storeLog(taskId, logHash) 之前，会检查当前配置的合约地址是否存在字节码。如果合约地址无效，系统不会将该次写入误认为成功，而是记录链上写入失败状态。这样可以避免出现“数据库中已有哈希记录，但实际链上没有对应合约调用”的情况，保证 log_hash_records 中的 on_chain_status 更符合真实链上状态。
167: 该机制同样适用于审计阶段。审计服务在根据 contract_address 创建链上读取客户端后，需要确认目标地址仍存在合约代码。如果目标地址不存在字节码，则说明当前链环境无法提供该条记录的链上证据，系统应将链上记录不可用作为审计状态判断的重要依据。相比直接吞掉异常或返回空结果，合约代码存在性校验能够更清楚地区分“链上确实没有对应哈希”和“目标合约地址当前不可用”这两类情况。
168: 在实验环境中，该机制尤其重要。本地 Hardhat 链重启后，原有合约部署状态可能消失，但环境变量或数据库中仍可能保留旧合约地址。如果缺少代码存在性校验，系统可能在错误地址上执行查询，导致审计结果不稳定或难以解释。通过在链上读写前校验目标地址字节码，系统能够及时发现环境状态与数据库记录之间的不一致，从而提高实验过程的可复现性和审计结论的可信度。
169: 从系统健壮性角度看，合约代码存在性校验是对链上交互边界条件的补充处理。它不改变日志哈希存证和三方比对的基本逻辑，但能够避免由于合约地址失效造成的误判。结合历史合约地址回溯策略，系统既能够定位日志实际写入的合约地址，又能够验证该地址在当前链环境中是否仍然有效，从而使链上链下协同审计更加稳健。
170: 3.5.1 审计状态判定规则
171: 在可信日志审计过程中，系统需要将哈希比对结果转化为明确的审计状态，以便后端记录、前端展示和后续告警处理。本系统围绕数据库哈希、链上哈希与重算哈希三方比对结果，设计了 passed、failed 和 pending 三类审计状态。其中，passed 表示日志完整性校验通过，failed 表示日志存在篡改风险或存证记录不一致，pending 表示当前证据不完整或链上记录暂不可用，需要等待后续补充核验。
172: 审计状态判定首先依赖 expectedHash、actualHash 和 onChainHash 三个值。expectedHash 来源于 log_hash_records 表中的 log_hash 字段，代表日志提交阶段保存的原始哈希。actualHash 来源于审计阶段对 logs 表中 log_content 字段重新计算得到的哈希，代表当前链下日志内容的实际状态。onChainHash 来源于 LogRegistry 合约查询结果，代表链上存证记录中的日志哈希。三者分别对应数据库记录、当前日志内容和链上存证证据，是审计判定的核心依据。
173: 当 expectedHash、actualHash 与 onChainHash 三者完整存在且内容一致时，系统将审计状态判定为 passed。该状态说明链下日志当前内容与数据库中保存的原始哈希一致，同时也能在链上存证记录中找到匹配哈希。此时，日志从提交、存证到审计重算的完整链路能够相互印证，系统可以认为该条日志在链下保存期间未发生内容篡改。审计通过后，系统会在 audit_records 表中写入 passed 状态，并可将 logs 表中对应日志状态更新为 audit_passed，供前端展示和统计使用。
174: 当 actualHash 与 expectedHash 不一致时，系统通常将审计状态判定为 failed。该情况说明审计阶段重新计算得到的日志哈希与日志提交阶段保存的哈希不一致，表示链下日志原文可能已经被修改。即使链上记录仍然存在且与 expectedHash 匹配，也只能说明原始日志曾经完成存证，而当前链下日志已经偏离原始内容。因此，该情况应被视为篡改风险，并触发后续异常告警流程。若 expectedHash 与链上记录也不匹配，则说明链下数据库记录、当前日志内容或链上存证之间存在更复杂的不一致，同样应判定为 failed，以提示用户进行人工复核。
175: pending 状态主要用于处理证据不完整或链上记录暂不可用的情况。例如，数据库中存在 expectedHash，且 actualHash 与 expectedHash 一致，但由于链上服务暂时不可访问、合约地址不可用或链上记录尚未匹配到对应哈希，系统无法确认该日志是否具备完整链上存证。此时，日志内容本身未表现出被篡改迹象，但链上证据不足，系统可将审计状态标记为 pending。pending 并不表示审计失败，而是表示当前审计结论尚不完整，需要在链上记录恢复或补充后再次确认。
176: 表 3-3 审计状态判定规则
177: 审计状态判定规则的设计需要兼顾准确性和可解释性。passed 状态强调三方证据一致，failed 状态强调哈希不一致或存在篡改风险，pending 状态则用于区分链上证据缺失与日志内容异常。通过这种分类，系统能够避免将所有链上不可用情况简单归为失败，也能够在日志内容确实发生变化时及时给出风险提示。最终，审计状态将与 audit_message 一同写入 audit_records 表，为前端展示和后续追踪提供依据。
178: 3.5.2 哈希不一致告警生成流程
179: 审计状态判定完成后，系统需要将发现的异常转化为可追踪、可展示的告警记录。单纯生成 failed 审计结果只能说明某次审计未通过，但如果缺少告警机制，用户仍需要主动检查审计列表才能发现风险。为提高异常发现效率，本系统在审计结果为 failed 时自动生成 hash_mismatch 类型告警，将日志完整性异常从审计结果进一步转化为告警事件，形成从检测到提示的闭环流程。
180: 哈希不一致告警的生成入口位于审计执行流程。当系统完成 expectedHash、actualHash 和 onChainHash 的比对后，如果判定结果为 failed，后端服务会先创建一条审计记录，将 audit_status、expected_hash、actual_hash 和 audit_message 等信息写入 audit_records 表。随后，系统根据该审计记录生成对应的告警数据，并写入 alerts 表。这样，审计记录负责保存本次校验的技术结果，告警记录负责向用户表达该异常的风险含义，二者通过关联字段建立联系。
181: 在 alerts 表中，alert_type 用于标识告警类型。本系统当前使用 hash_mismatch 表示哈希不一致告警，说明该告警由日志哈希校验失败触发。severity 表示告警严重程度，哈希不一致通常意味着日志内容可能被篡改，因此可设置为较高风险级别。related_log_id 用于关联出现异常的日志记录，related_audit_id 用于关联触发该告警的审计记录。通过这两个字段，用户可以从告警追溯到具体日志，也可以从告警查看对应审计过程和哈希比对结果。
182: 告警标题和描述用于提高前端展示的可读性。标题通常概括风险对象，例如提示某一任务存在篡改风险；描述则进一步说明该日志的重新计算哈希与存证记录不一致，需要进行复核。相比只展示 failed 状态，标题和描述能够帮助用户快速理解异常原因，降低使用者阅读底层哈希字段的成本。status 字段用于表示告警处理状态，默认可设置为 open，表示该告警尚未处理。后续若系统扩展告警处置功能，可以根据处理过程将状态更新为 resolved 或其他状态。
183: 哈希不一致告警生成流程体现了本系统从审计检测到风险提示的闭环。系统并不是在发现哈希不一致后仅返回接口结果，而是将异常持久化为告警记录，使前端告警管理页面能够持续展示该风险。即使用户没有立即查看审计详情，也可以通过告警列表发现存在异常的日志记录。与此同时，告警与日志、审计记录之间的关联关系保证了异常事件可以被追溯，便于后续人工复核或进一步处理。
184: 从系统设计角度看，告警机制增强了可信日志审计系统的主动性和可用性。三方哈希比对负责发现问题，审计记录负责保存技术证据，告警记录负责提示风险并支持后续跟踪。三者结合后，系统能够将底层哈希不一致问题转化为面向用户的异常事件，从而提高日志审计结果的实际应用价值。

186: 本章围绕基于区块链的可信日志存证与审计机制展开，重点说明了系统核心技术方案。首先，本章提出链下保存日志原文、链上保存日志哈希的混合存储模型，通过 SQLite 保留日志查询和展示能力，通过 LogRegistry 智能合约保存哈希摘要和任务标识，从而兼顾存储效率、隐私保护和审计可信性。随后，本章说明了日志采集、存证、审计、告警和前端展示构成的完整闭环流程，明确了各模块在可信日志审计链路中的作用。
187: 在数据模型方面，本章介绍了日志标准化封装、任务标识设计、SHA-256 日志摘要生成方法，以及链上存证字段与链下记录之间的映射关系。通过 taskId、log_id、log_hash 和 contract_address 等字段，系统能够将链下日志原文、数据库存证记录和链上合约记录关联起来，为后续审计比对提供稳定的数据基础。
188: 在智能合约与审计机制方面，本章围绕 LogRegistry 合约的数据结构、AccessControl 权限控制、日志哈希写入和任务维度查询方法进行了说明，并进一步分析了数据库哈希、链上哈希与重算哈希的三方比对机制。针对本地链重启和多次部署可能带来的审计误判问题，本章还说明了历史合约地址回溯审计策略和合约代码存在性校验机制。最后，本章介绍了审计状态判定规则和哈希不一致告警生成流程，使系统能够在发现日志完整性异常后生成审计失败记录和异常告警。
189: 综上，本章完成了系统核心可信审计机制的设计说明，为后续系统需求分析、总体架构设计以及具体工程实现提供了技术基础。
190: 4.2 系统需求分析
191: 本系统面向任务日志可信审计场景，核心目标是使日志从产生、采集、存储、存证到审计和告警的全过程具备可追溯性和可验证性。传统日志系统通常能够完成日志保存和查询，但在日志被篡改、删除或伪造时，缺少独立可信的校验依据。因此，本系统的功能需求不仅包括一般日志系统中的采集、存储和展示能力，还需要围绕区块链可信存证、哈希完整性校验、异常告警和可视化审计构建完整能力。
192: 从用户使用角度看，系统需要支持日志自动进入审计流程，减少人工导入带来的遗漏和不一致；需要将日志摘要写入链上，形成独立于链下数据库的可信证据；需要在审计阶段对链下日志重新计算哈希，并与数据库记录、链上记录进行比对；需要在发现异常时及时生成告警；同时需要通过前端页面展示日志、审计结果和告警状态，使用户能够直观了解系统运行情况。上述需求共同支撑第 3 章提出的可信日志存证与审计机制。
193: 4.2.1 日志自动采集需求
194: 日志自动采集是系统可信审计流程的起点。若日志进入系统依赖人工复制或手动提交，不仅效率较低，也容易出现遗漏、重复或时间不一致等问题。为保证任务日志能够及时纳入审计范围，系统需要提供自动采集能力，使日志文件产生新增内容后能够被 Agent 识别并提交至后端服务。
195: 从功能角度看，Agent 需要能够读取指定日志文件，并基于偏移量记录方式识别新增日志内容，避免重复采集已处理的历史日志。对于已经采集的日志，Agent 应将其封装为统一数据格式，包含任务标识、日志来源、日志级别、日志内容和采集时间等字段，并提交给后端接口。为提高采集过程的可靠性，系统还需要支持失败重试和状态同步能力。当网络异常或后端暂时不可用时，采集端应能够保留待提交数据，并在后续恢复后继续上报。
196: 日志自动采集需求直接支撑可信审计链路的完整性。只有日志能够稳定进入系统，后续链下入库、哈希计算、链上存证和审计比对才具备数据基础。因此，Agent 模块不仅是日志获取工具，也是系统审计闭环的入口。
197: 4.2.2 链上可信存证需求
198: 链上可信存证是本系统区别于传统日志管理系统的重要需求。传统日志系统通常将日志原文和审计依据都保存在中心化数据库中，一旦数据库中的日志或哈希记录被修改，系统难以提供独立证据说明日志是否保持原始状态。因此，系统需要利用区块链的不可篡改和可追溯特性，将日志关键摘要信息写入链上，形成独立于链下数据库的可信存证。
199: 从系统能力角度看，链上存证不要求直接保存完整日志原文，而是保存日志哈希、任务标识、写入时间和提交者地址等必要信息。日志原文仍保存在 SQLite 中，便于查询和展示；链上只保存固定长度哈希摘要，用于完整性校验。后端服务在接收日志并计算 SHA-256 哈希后，应调用 LogRegistry 智能合约完成上链写入，并记录交易哈希、区块号、合约地址和链上状态。
200: 链上可信存证需求为后续审计比对提供了外部证据来源。审计阶段，系统能够根据任务标识和历史合约地址读取链上哈希记录，并与数据库哈希和重算哈希进行对比。通过该需求，系统能够避免完全依赖链下数据库，提高日志完整性验证的可信度。
201: 4.2.3 审计校验需求
202: 审计校验是系统判断日志是否可信的核心功能。日志完成采集和存证后，系统需要在用户触发或系统执行审计任务时，对日志内容进行重新核验。该需求的目标是发现链下日志是否在存储过程中被修改，并将审计结果持久化保存，供后续查询、展示和告警处理使用。
203: 从系统流程看，审计校验需要读取待审计日志原文，重新计算 actualHash；读取 log_hash_records 表中的 expectedHash；再根据任务标识和合约地址查询 LogRegistry 合约中的 onChainHash。系统应根据 expectedHash、actualHash 和 onChainHash 的比对结果生成审计状态。当三方一致时，审计状态为 passed；当重算哈希与数据库或链上记录不一致时，审计状态为 failed；当链上记录暂不可用或证据不完整时，可标记为 pending。
204: 审计校验需求要求系统不仅返回即时结果，还要将审计状态、期望哈希、实际哈希和审计说明写入 audit_records 表。这样可以保留每次审计的过程证据，使前端和后续分析能够追踪审计历史。该需求直接对应第 3 章提出的三方哈希比对机制，是系统实现可信日志审计的关键环节。
205: 4.2.4 异常告警需求
206: 日志审计系统不仅需要发现异常，还需要将异常以明确方式提示给用户。如果系统只在审计接口中返回 failed 状态，用户可能需要主动查看审计列表才能发现问题，异常响应不够直观。因此，本系统需要具备异常告警能力，在审计发现哈希不一致时自动生成告警记录，并通过前端页面进行展示。
207: 异常告警需求主要针对审计状态为 failed 的情况。当系统判断日志重算哈希与数据库或链上存证不一致时，应生成 hash_mismatch 类型告警，并将该告警与对应日志记录和审计记录关联。告警记录需要包含告警类型、严重程度、关联日志编号、关联审计编号、标题、描述和处理状态等信息。通过这些字段，用户可以从告警列表定位异常日志，也可以进一步查看相关审计记录和哈希比对结果。
208: 告警需求能够将底层哈希比对结果转化为面向用户的风险提示。它使系统从“被动审计查询”扩展为“主动异常提示”，有助于用户及时关注日志完整性风险。该需求与第 3 章中的篡改检测与异常告警机制相对应，是可信审计闭环中从检测到反馈的重要环节。
209: 4.2.5 可视化展示需求
210: 可信日志审计结果需要通过直观方式呈现给用户，才能支持日常查看、问题定位和答辩演示。系统后端虽然能够完成日志存储、链上写入和审计比对，但如果缺少前端展示，用户难以快速理解系统运行状态。因此，本系统需要提供 Web 可视化界面，集中展示日志、审计和告警相关信息。
211: 从功能需求看，前端需要提供系统总览页面，用于展示日志数量、审计通过情况、异常告警数量等统计指标；需要提供日志中心页面，用于查看日志列表、任务标识、日志级别和采集时间；需要提供审计管理页面，用于展示审计状态、哈希比对结果和审计说明；还需要提供告警管理页面，用于展示 hash_mismatch 告警及其处理状态。通过这些页面，用户能够从整体到局部了解系统可信审计情况。
212: 可视化展示需求不仅服务于用户交互，也有助于验证系统闭环是否完整。日志能否展示、审计结果能否查询、告警能否呈现，能够反映后端接口、数据库记录和前端数据映射是否正常。因此，前端可视化是系统可用性的重要组成部分，也是展示区块链可信日志审计效果的重要窗口。
213: 4.3 非功能需求分析
214: 除功能需求外，可信任务日志审计系统还需要满足数据可信性、系统可用性、可维护性与可扩展性等非功能需求。非功能需求决定系统在实际运行和后续扩展中的稳定性，也影响论文实验和答辩演示过程中的可复现性。本系统作为毕业设计原型，需要在工程复杂度可控的前提下，突出可信审计机制的有效性。
215: 4.3.1 数据可信性需求
216: 数据可信性是本系统最核心的非功能需求。系统需要保证日志从采集、入库、哈希生成、链上存证到审计比对的过程具有可追溯性，能够在日志内容被修改时发现异常。为满足该需求，系统采用链下原文存储与链上哈希存证相结合的方式，使日志原文和完整性证据不完全依赖同一中心化数据库。
217: 在链下部分，SQLite 保存日志原文、存证记录、审计记录和告警记录，使系统能够查询和展示完整业务数据。在链上部分，LogRegistry 保存日志哈希和任务标识，为审计提供独立校验依据。审计阶段，系统通过 expectedHash、actualHash 和 onChainHash 的三方比对判断日志是否一致。与此同时，历史合约地址回溯和合约代码存在性校验进一步增强了链上读取过程的可靠性，避免因合约地址变化或空地址导致误判。
218: 因此，数据可信性需求不仅体现在区块链不可篡改特性上，也体现在链上链下字段映射、哈希生成规则、审计状态判定和异常告警记录等多个环节的协同设计中。
219: 4.3.2 系统可用性需求
220: 系统可用性要求用户能够稳定地完成日志提交、审计执行、告警查看和结果展示等操作。对于本系统而言，可用性不仅体现在前端页面能否访问，还体现在日志采集、后端接口、数据库读写和链上交互能否形成稳定闭环。若任一环节不可用，系统就难以完成可信日志审计目标。
221: 在日志采集侧，Agent 需要支持增量读取、失败重试和状态同步，以降低临时异常对日志提交的影响。在后端服务侧，系统需要提供日志提交、审计执行、告警查询和总览统计等接口，使前端能够稳定获取数据。在数据存储侧，SQLite 作为原型系统数据库，需要支持日志、哈希记录、审计记录和告警记录的持久化。在区块链交互侧，系统需要能够识别合约地址不可用等异常情况，避免将失败操作误判为成功。
222: 此外，系统可用性还体现在验证和演示过程的可重复性上。项目提供脚本化验证入口和性能实验脚本，能够对合约、后端、Agent 和前端构建进行验证。这些脚本有助于在论文实验和答辩演示前确认系统主要功能处于可运行状态。
223: 4.3.3 可维护性与可扩展性需求
224: 可维护性要求系统结构清晰、模块职责明确，便于后续修改、调试和论文说明。本系统采用模块化 Monorepo 结构，将前端 Web、后端 Server、采集 Agent、智能合约和共享类型库放在同一仓库下统一管理。不同模块在目录和职责上相对独立，能够降低代码耦合度，也便于在论文中说明系统分层设计。
225: 后端服务采用 routes、controllers、services、repositories、db 和 blockchain 等分层结构。路由层负责接口定义，控制器负责请求处理，服务层负责编排业务逻辑，数据访问层负责 SQLite 读写，区块链封装层负责合约调用和哈希服务。这样的结构使日志提交、链上写入、审计执行和告警生成等逻辑能够分别维护，避免所有业务代码集中在单一文件中。
226: 可扩展性方面，当前系统虽然基于 SQLite 和本地 Hardhat 链实现，但整体结构为后续扩展预留了空间。例如，数据库层可以替换为更适合高并发场景的数据库，链上环境可以从本地链扩展到测试网或联盟链，审计执行方式也可以进一步扩展为异步队列或并发批量审计。前端页面和后端接口的分离也便于后续增加用户权限、日志筛选和风险分析等功能。
227: 4.4 系统总体架构设计
228: 本系统围绕可信任务日志审计目标，采用分层和模块化的总体架构。系统由 Agent、Server、SQLite、LogRegistry 和 Web 五类核心部分组成，分别对应日志采集、业务处理、链下存储、链上存证和前端展示等职责。各模块通过标准化数据结构和接口进行协作，共同形成从日志产生到审计告警的完整流程。
229: Agent 位于系统数据流的前端，主要负责从本地日志文件中读取新增日志内容。由于日志文件会随着任务运行不断追加内容，Agent 需要维护读取偏移量，确保每次只采集新增部分。采集到日志后，Agent 会将其封装为包含任务标识、来源路径、日志内容、日志级别和采集时间等字段的标准数据，并通过后端接口提交给 Server。同时，Agent 还负责同步自身状态，使系统能够了解采集端是否处于正常运行状态。
230: Server 是系统的业务处理中心，负责连接 Agent、SQLite、LogRegistry 和 Web。Server 接收 Agent 提交的日志后，先将日志原文和元数据写入 SQLite，再对日志内容计算 SHA-256 哈希。随后，Server 调用 LogRegistry 智能合约，将日志哈希和任务标识写入链上，并在数据库中保存交易哈希、区块号、合约地址和链上状态等信息。审计阶段，Server 读取日志原文、数据库哈希和链上哈希，执行三方比对，并根据结果写入审计记录和异常告警。
231: SQLite 是系统的链下数据存储部分，主要保存日志原文、哈希存证记录、审计记录、告警记录和 Agent 状态。相比将全部数据写入链上，SQLite 更适合保存结构化业务数据和日志原文，便于快速查询、前端展示和实验验证。链下数据库并不单独承担可信性证明责任，而是与链上 LogRegistry 合约共同构成完整审计依据。
232: LogRegistry 是系统的链上存证部分，负责保存日志哈希和任务标识等关键摘要信息。合约通过 LOGGER_ROLE 控制写入权限，避免任意地址写入无效数据。合约中的 LogRecord 记录 taskId、logHash、createdAt 和 submitter，records 数组和 taskIdToRecordIds 映射支持按编号和任务维度查询。审计阶段，Server 根据任务标识和合约地址读取链上哈希记录，用于与链下哈希进行比对。
233: Web 前端是系统面向用户的展示层。前端通过后端 API 获取日志、审计、告警和总览统计数据，并以页面形式展示系统运行状态。用户可以在总览页查看日志数量、审计状态和告警数量，在日志中心查看日志列表，在审计页面查看审计结果，在告警页面查看异常风险。通过前端展示，系统将底层哈希比对和链上存证结果转化为可理解的审计信息。
234: 图 4-1 系统总体架构图
235: 从数据流向看，系统首先由 Agent 采集日志并提交 Server；Server 将日志写入 SQLite，并计算哈希写入 LogRegistry；审计时，Server 从 SQLite 读取日志原文和数据库哈希，从 LogRegistry 读取链上哈希，完成三方比对；当发现异常时，Server 将审计失败记录和告警写入数据库；Web 前端再通过 API 查询并展示相关结果。该架构使每个模块职责清晰，数据流向明确，同时也使链上链下协同审计机制能够落地到具体工程实现中。
236: 总体来看，系统总体架构既满足毕业设计原型系统的可实现性，又能够突出区块链在日志可信审计中的作用。Agent 保证日志自动进入系统，Server 负责业务编排，SQLite 提供链下持久化能力，LogRegistry 提供可信存证依据，Web 提供可视化交互入口。各模块围绕日志哈希和任务标识建立连接，为后续功能模块设计、数据流设计和数据库设计奠定基础。
237: 4.5 系统功能模块设计
238: 本系统按照日志可信审计的业务流程划分功能模块，主要包括日志采集 Agent 模块、后端服务模块、区块链存证模块、审计告警模块和前端可视化模块。各模块围绕任务标识和日志哈希进行数据传递，分别承担采集、处理、存证、审计、告警和展示等职责。通过模块化设计，系统能够将不同功能边界清晰分离，降低实现复杂度，并便于后续测试和论文说明。
239: 4.5.1 日志采集 Agent 模块
240: 日志采集 Agent 模块负责从本地日志文件中获取新增日志内容，是系统数据进入可信审计流程的入口。该模块的输入主要是指定路径下的日志文件和本地保存的读取偏移量，输出则是封装后的日志提交数据和 Agent 运行状态。Agent 需要根据上次读取位置识别新增内容，避免重复采集已处理日志，并在采集后将日志内容、任务标识、来源路径、日志级别和采集时间等信息提交给后端服务。
241: 该模块与后端服务模块直接交互，通过日志提交接口将采集结果发送至 Server，并通过状态同步接口上报 Agent 当前运行状态、最后读取偏移量和同步时间。当后端服务暂时不可用或网络异常时，Agent 需要具备失败重试能力，以提高日志提交过程的可靠性。日志采集 Agent 模块的设计目标是降低人工导入日志的依赖，使任务日志能够持续、自动地进入后续存证与审计流程。
242: 4.5.2 后端服务模块
243: 后端服务模块是系统业务处理中心，负责连接日志采集、链下存储、链上存证、审计告警和前端展示等功能。该模块的输入包括 Agent 提交的日志数据、前端发起的查询请求和审计触发请求；输出包括日志列表、审计结果、告警信息、总览统计数据以及链上写入结果。后端服务需要完成日志入库、哈希计算、合约调用、审计执行、告警生成和数据查询等业务操作。
244: 从模块关系看，后端服务一方面接收 Agent 采集的日志，将日志原文保存到 SQLite，并调用哈希服务生成日志摘要；另一方面调用 LogRegistry 合约完成链上存证，并将交易哈希、区块号、合约地址等信息保存到 log_hash_records 表中。审计阶段，后端服务从 SQLite 读取日志和哈希记录，从区块链合约读取链上哈希，执行三方比对，并根据结果写入 audit_records 和 alerts 表。前端所有展示数据也主要通过后端 API 获取。
245: 4.5.3 区块链存证模块
246: 区块链存证模块负责将日志哈希写入链上，并在审计阶段提供链上记录查询能力。该模块的核心是 LogRegistry 智能合约，其输入主要包括任务标识 taskId 和日志哈希 logHash，输出则是链上存证记录、交易哈希、区块号和查询结果。合约记录 taskId、logHash、createdAt 和 submitter 等字段，用于描述每条链上存证记录。
247: 该模块与后端服务模块紧密关联。日志提交阶段，后端在完成日志入库和哈希计算后调用 storeLog 方法，将日志哈希写入链上。审计阶段，后端根据任务标识和合约地址调用 getLogsByTaskId 等查询方法，读取链上哈希记录。区块链存证模块不直接处理日志原文，而是保存摘要形式的完整性证据。通过 LOGGER_ROLE 权限控制，该模块能够限制链上写入主体，避免任意地址污染存证数据。
248: 4.5.4 审计告警模块
249: 审计告警模块负责执行日志完整性校验，并在发现异常时生成告警记录。该模块的输入包括待审计日志、数据库中的哈希记录和链上查询得到的哈希记录；输出包括审计状态、审计说明、审计记录和异常告警。其核心逻辑是重新计算日志原文的 actualHash，并与 expectedHash 和 onChainHash 进行三方比对。
250: 当三方哈希一致时，审计告警模块生成 passed 状态的审计记录；当哈希不一致时，生成 failed 状态的审计记录，并进一步写入 hash_mismatch 类型告警；当链上记录暂不可用或证据不完整时，可生成 pending 状态。该模块与数据库模块和区块链存证模块均存在交互，需要读取 logs、log_hash_records 和链上 LogRegistry 记录，同时将结果写入 audit_records 和 alerts 表。审计告警模块使系统能够从单纯记录日志扩展到主动识别日志篡改风险。
251: 4.5.5 前端可视化模块
252: 前端可视化模块负责将系统运行状态、日志数据、审计结果和告警信息展示给用户。该模块的输入主要来自后端 API 返回的数据，输出则是面向用户的页面视图。前端需要展示系统总览、日志中心、审计管理和告警管理等页面，使用户能够直观了解日志数量、审计状态、异常告警和趋势信息。
253: 该模块与后端服务模块交互，不直接访问数据库或区块链合约。前端通过统一接口获取日志列表、审计记录、告警记录和统计数据，并将后端返回的原始数据转换为适合页面展示的视图模型。系统总览页面用于展示总体指标，日志中心用于查看日志明细，审计管理页面用于查看审计状态和执行结果，告警管理页面用于查看哈希不一致等异常事件。前端可视化模块提高了系统的可用性，也为毕业设计演示提供了直观支撑。
254: 4.6 系统数据流与业务流程设计
255: 系统数据流围绕日志可信审计目标展开，主要包括两条核心业务流程：日志采集与存证流程、审计与告警流程。前者负责将任务日志从日志文件引入系统，并完成链下存储和链上存证；后者负责在审计阶段重新核验日志完整性，并在发现异常时生成告警。两条流程通过 logs、log_hash_records、audit_records、alerts 和 LogRegistry 链上记录建立关联，共同支撑系统可信日志审计闭环。
256: 第一条流程是日志采集与存证流程。任务执行过程中产生的日志首先保存在本地日志文件中。Agent 根据配置读取日志文件，并通过偏移量机制识别新增日志内容。读取到新增日志后，Agent 将日志封装为标准提交数据，包含 taskId、sourceType、sourcePath、logContent、logLevel 和 collectedAt 等字段，并通过后端接口提交给 Server。Server 接收到日志后，首先将日志原文和元数据写入 SQLite 的 logs 表，为后续查询、展示和审计重算提供链下数据基础。
257: 日志入库后，Server 对 logContent 执行 SHA-256 哈希计算，得到固定长度的日志哈希。该哈希值一方面写入 log_hash_records 表，作为数据库中的 expectedHash；另一方面作为参数提交给 LogRegistry 智能合约。Server 调用 storeLog(taskId, logHash) 方法，将任务标识和日志哈希写入链上。链上交易完成后，Server 将 transaction_hash、block_number、contract_address 和 on_chain_status 等信息保存到 log_hash_records 表中。至此，系统完成一条日志从采集、入库、哈希计算到链上存证的全过程。
258: 第二条流程是审计与告警流程。用户或系统脚本触发审计任务后，Server 根据待审计日志的 log_id 读取 logs 表中的日志原文，并使用相同的 SHA-256 规则重新计算 actualHash。随后，Server 从 log_hash_records 表中读取 expectedHash 和 contract_address，并根据 taskId 查询对应 LogRegistry 合约中的链上记录，获得 onChainHash。系统将 actualHash、expectedHash 和 onChainHash 进行比对，并根据比对结果生成 passed、failed 或 pending 状态的审计记录。
259: 当三方哈希一致时，系统将审计结果写入 audit_records 表，并更新日志状态为审计通过。若 actualHash 与 expectedHash 或 onChainHash 不一致，说明链下日志内容可能已经被修改，系统将审计状态判定为 failed，并生成 hash_mismatch 类型告警。告警记录写入 alerts 表，并通过 related_log_id 和 related_audit_id 分别关联异常日志和审计记录。前端 Web 模块通过后端 API 获取日志、审计和告警数据，并在系统总览、日志中心、审计管理和告警管理页面展示结果。
260: 图 4-2 系统数据流图
261: 从整体流程看，日志采集与存证流程负责生成可信证据，审计与告警流程负责使用可信证据验证当前日志状态。Agent、Server、SQLite、LogRegistry 和 Web 在两条流程中各自承担不同职责。Agent 保证日志进入系统，Server 负责业务编排和哈希计算，SQLite 保存链下业务数据，LogRegistry 保存链上存证记录，Web 展示审计和告警结果。通过这两条流程，系统实现了从日志产生到异常反馈的完整闭环。
262: 4.7 数据库设计
263: 数据库设计是系统链下数据管理的基础。本系统采用 SQLite 作为原型系统的数据存储方案，主要用于保存日志原文、链上存证记录、审计结果、异常告警和 Agent 运行状态。与链上 LogRegistry 合约相比，SQLite 更适合保存结构化业务数据和日志原文，便于后端查询和前端展示。系统通过 logs、log_hash_records、audit_records、alerts 和 agent_states 五张核心表支撑业务流程。
264: 4.7.1 日志数据表设计
265: logs 表用于保存日志原文及采集来源信息，是系统最基础的数据表。该表的核心字段包括 id、task_id、source_type、source_path、log_content、log_level、collected_at、created_at、updated_at 和 status。其中，id 是日志记录主键，用于唯一标识一条链下日志；task_id 表示日志所属任务，是连接链上存证记录和审计记录的重要业务字段；source_type 表示日志来源类型；source_path 记录日志文件路径；log_content 保存日志原文，是哈希计算和审计重算的基础。
266: log_level 用于记录日志级别，便于前端筛选和展示；collected_at 表示日志采集时间；created_at 和 updated_at 用于记录数据库写入和更新时间；status 用于标识日志当前状态，例如 collected、audit_passed、audit_failed 或 audit_pending。logs 表与 log_hash_records 表通过 id 和 log_id 建立关联，与 audit_records 表也可通过 log_id 建立关联。该表为系统提供链下日志原文和状态管理能力。
267: 4.7.2 存证记录表设计
268: log_hash_records 表用于保存日志哈希及其链上写入信息，是连接链下日志与链上存证的关键表。该表的核心字段包括 id、log_id、task_id、log_hash、chain_name、contract_address、transaction_hash、block_number、on_chain_status、created_at 和 updated_at。log_id 对应 logs 表中的日志主键，表示该条存证记录属于哪一条日志；task_id 与 logs 表中的任务标识保持一致，用于任务维度查询。
269: log_hash 字段保存日志提交阶段计算得到的 SHA-256 哈希，是审计阶段 expectedHash 的来源。chain_name 用于标识链环境，当前系统主要使用本地 Hardhat 链。contract_address 保存本次日志哈希实际写入的 LogRegistry 合约地址，是历史合约地址回溯审计的重要依据。transaction_hash 和 block_number 分别记录链上交易哈希和区块号，on_chain_status 表示链上写入状态或失败原因。该表使系统能够追踪每条日志哈希是否完成链上存证，以及对应的链上位置信息。
270: 4.7.3 审计记录与告警表设计
271: audit_records 表用于保存系统每次审计执行结果。其核心字段包括 id、log_id、log_hash_record_id、audit_status、expected_hash、actual_hash、audit_message、audited_at 和 created_at。log_id 关联被审计日志，log_hash_record_id 关联对应存证记录。audit_status 保存审计状态，包括 passed、failed 和 pending。expected_hash 保存数据库或链上存证中的期望哈希，actual_hash 保存审计阶段重新计算得到的实际哈希，audit_message 用于描述审计结果原因。该表能够保留审计过程证据，便于前端展示和后续追踪。
272: alerts 表用于保存异常告警记录，主要服务于哈希不一致等审计失败场景。其核心字段包括 id、alert_type、severity、related_log_id、related_audit_id、title、description、status、created_at 和 resolved_at。alert_type 当前主要为 hash_mismatch，表示哈希不一致告警；severity 表示告警严重程度；related_log_id 和 related_audit_id 分别关联异常日志和触发告警的审计记录；title 和 description 用于前端展示；status 表示告警处理状态。audit_records 与 alerts 表共同构成从审计结果到风险提示的数据链路。
273: 4.7.4 Agent 状态表设计
274: agent_states 表用于保存日志采集 Agent 的运行状态，帮助系统了解采集端是否正常工作。该表的核心字段包括 id、agent_name、source_path、last_offset、last_heartbeat_at、last_sync_at、status、error_message、created_at 和 updated_at。agent_name 用于标识采集 Agent；source_path 记录该 Agent 监听或读取的日志路径；last_offset 保存最后读取位置，是增量采集的重要依据。
275: last_heartbeat_at 用于记录 Agent 最近一次心跳时间，last_sync_at 用于记录状态同步时间，status 表示 Agent 当前运行状态，error_message 用于保存异常说明。通过 agent_states 表，后端可以记录采集端的运行情况，前端也可以在系统总览中展示 Agent 是否在线。该表虽然不直接参与链上存证，但对保证日志自动采集流程的可用性具有重要作用。
276: 表 4-1 数据库核心表结构说明
277: 总体来看，五张核心表之间形成了清晰关系：logs 保存日志原文，log_hash_records 保存对应哈希和链上写入信息，audit_records 保存审计结果，alerts 保存异常告警，agent_states 保存采集端状态。logs 是业务数据基础，log_hash_records 提供存证信息，audit_records 和 alerts 支撑审计反馈，agent_states 则保障采集流程可观察。通过该数据库设计，系统能够在链下完整记录可信审计过程，并与链上 LogRegistry 合约形成协同。

279: 本章围绕系统需求分析与总体设计展开，首先从功能需求角度说明了日志自动采集、链上可信存证、审计校验、异常告警和可视化展示等能力。这些功能需求共同支撑第 3 章提出的可信日志存证与审计机制，使系统能够完成从日志进入、哈希上链到审计告警的完整流程。

283: 5.1 系统开发环境与工程结构
284: 本系统以毕业设计原型实现和论文实验验证为目标，采用前后端分离、链上链下协同和多模块统一管理的工程组织方式。为便于同时管理前端页面、后端服务、日志采集 Agent、智能合约和公共类型，本项目采用 Monorepo 结构，将不同子系统放置在同一仓库中进行统一维护。该组织方式能够减少多仓库之间版本不一致的问题，也便于在实验和答辩过程中通过统一脚本完成构建、验证和演示。
285: 系统工程主要由 apps、packages、tests、scripts、storage 和 doc 等目录组成。其中，apps 目录用于存放可独立运行的应用模块，包括 apps/web、apps/server 和 apps/agent。apps/web 是前端审计系统，基于 React、TypeScript 和 Ant Design 实现，主要负责系统总览、日志中心、审计管理和告警管理等页面展示。apps/server 是后端服务模块，基于 Node.js、Express 和 TypeScript 实现，负责接收日志、写入 SQLite、计算日志哈希、调用智能合约、执行审计和生成告警。apps/agent 是日志采集模块，用于读取本地日志文件新增内容，并将日志提交给后端服务。
286: packages 目录用于存放可被多个模块复用或独立维护的公共工程。其中，packages/contracts 是智能合约工程，基于 Hardhat、Solidity 和 OpenZeppelin 实现 LogRegistry 合约，并提供合约部署和测试能力。packages/shared 用于沉淀前后端和 Agent 可复用的类型定义、数据结构和公共协议，减少不同模块之间字段不一致的问题。通过将合约工程和共享类型独立出来，系统能够在保持模块边界清晰的同时，提高整体工程的一致性。
287: tests/performance 目录用于保存性能测试脚本，包括日志批量提交实验和批量审计实验。scripts 目录用于存放仓库级验证脚本，便于统一执行合约测试、后端验证、Agent 验证和前端构建验证。storage/sqlite 目录用于保存 SQLite 数据文件和相关说明，支撑链下日志、哈希记录、审计记录、告警记录和 Agent 状态的持久化。doc 目录用于保存论文目录、技术说明、实验报告、答辩材料和写作 SOP 等文档资料，为论文撰写和答辩准备提供支撑。
288: 表 5-1 系统工程目录说明
289: 从技术栈角度看，系统前端采用 React 和 Ant Design 实现页面交互和可视化展示，后端采用 Express 提供 REST API，链下数据存储采用 SQLite，链上存证采用 Hardhat 本地链和 Solidity 智能合约实现，后端通过 Ethers 与 LogRegistry 合约交互。该技术组合既能够覆盖完整的软件系统开发流程，又能够突出区块链可信存证在日志审计中的作用。
290: 总体而言，Monorepo 工程结构使本系统能够在一个仓库内统一管理多个子模块，便于开发、测试、实验和论文说明。前端、后端、Agent、合约和共享类型之间职责相对独立，又通过统一接口和数据结构相互协作，为后续系统实现和实验验证奠定了工程基础。
291: 5.2 日志采集 Agent 实现
292: 日志采集 Agent 是系统实现自动化日志接入的关键模块。传统日志审计若依赖人工导入日志，容易出现遗漏、重复和时效性不足等问题。为使任务日志能够持续进入可信审计流程，本系统设计了独立的 Agent 模块，用于读取本地日志文件新增内容，并将标准化日志数据提交给后端服务。Agent 模块主要围绕日志读取、增量采集、偏移量持久化、失败重试和状态同步等功能展开，其中 logAgent 负责组织 Agent 主流程，协调 fileReader、logCollector、retryQueue 和 offsetStore 等功能单元共同完成采集与上报。
293: 5.2.1 增量读取与偏移量持久化实现
294: 增量读取是 Agent 模块的基础能力。日志文件通常会随着系统运行不断追加内容，如果每次采集都从文件开头读取，不仅会造成重复提交，也会增加不必要的处理开销。因此，Agent 需要记录每个日志文件上一次读取到的位置，并在下一次采集时从该偏移量继续读取新增内容。本系统通过 fileReader 和 offsetStore 等功能实现增量采集与偏移量持久化。
295: fileReader 负责根据指定文件路径和偏移量读取新增日志内容。当 Agent 启动或定时执行采集任务时，系统首先从 offsetStore 中读取上次保存的 lastOffset，再将该偏移量传入文件读取逻辑。fileReader 根据文件当前长度和 lastOffset 判断是否存在新增内容；若文件长度大于偏移量，则读取新增部分并按日志行进行处理；若文件没有新增内容，则本轮采集不产生提交数据。该方式能够避免重复读取历史日志，使 Agent 更适合持续运行场景。
296: logCollector 负责组织日志采集流程。它在 fileReader 读取新增内容后，将日志行封装为后端可接收的数据结构。封装内容通常包括 taskId、sourceType、sourcePath、logContent、logLevel 和 collectedAt 等字段。其中，taskId 用于标识日志所属任务，sourcePath 用于说明日志来源文件，logContent 是实际提交的日志内容，collectedAt 用于记录采集时间。通过标准化封装，Agent 输出的数据能够与后端日志入库、哈希计算和链上存证流程保持一致。
297: 偏移量持久化用于保证 Agent 重启后仍能继续从正确位置读取日志。如果 Agent 只在内存中保存偏移量，一旦进程退出或系统重启，下一次运行时可能重新读取整个文件，造成重复提交。offsetStore 将读取位置保存到本地状态文件中，使 Agent 在重新启动后能够恢复上次采集进度。当日志提交成功后，Agent 会更新对应文件的 lastOffset，确保后续采集从新的位置继续读取。
298: 在实现效果上，增量读取与偏移量持久化共同保证了日志采集过程的连续性和准确性。fileReader 解决“从哪里读”的问题，logCollector 解决“如何组织提交数据”的问题，offsetStore 解决“采集进度如何保存”的问题。三者配合后，Agent 能够以较低侵入方式接入本地日志文件，为后端可信存证和审计流程提供稳定输入。
299: 5.2.2 失败重试与状态同步实现
300: 在实际运行过程中，Agent 向后端提交日志时可能遇到网络异常、后端服务暂时不可用或接口调用失败等情况。如果失败后直接丢弃日志，将破坏日志采集链路的完整性；如果无限制地立即重试，又可能在后端不可用时造成额外压力。因此，本系统在 Agent 模块中设计了失败重试机制和状态同步机制，以提高日志采集过程的可靠性和可观察性。
301: 失败重试主要由 retryQueue 负责。当 Agent 提交日志失败时，系统不会立即丢弃该日志，而是将待提交数据加入重试队列。重试队列保存待发送日志、失败次数和下一次重试时间等信息，使 Agent 能够在后续轮询过程中继续尝试提交。为了避免频繁请求不可用服务，重试过程可以采用逐步延长间隔的策略，使系统在保证数据不丢失的同时降低异常期间的请求压力。
302: retryQueue 的持久化同样重要。如果待重试数据只保存在内存中，Agent 重启后未发送日志将丢失。通过将重试队列写入本地文件，Agent 可以在重新启动后恢复未提交任务，并继续向后端发送。该设计提高了日志采集过程的容错能力，使系统在短暂异常后仍能尽量保持日志提交完整性。
303: 状态同步用于向后端报告 Agent 当前运行情况。Agent 在运行过程中会定期将 agentName、sourcePath、lastOffset、lastHeartbeatAt、lastSyncAt、status 和 errorMessage 等信息提交给后端，由后端保存到 agent_states 表中。通过该表，系统可以了解 Agent 是否在线、当前读取到哪个位置、最近一次同步时间以及是否存在错误信息。前端总览页面也可以基于这些状态展示采集端运行情况。
304: 失败重试与状态同步分别解决日志提交可靠性和采集过程可观察性问题。前者保证在后端暂时不可用时日志不会轻易丢失，后者使系统能够掌握 Agent 的运行状态。二者结合后，Agent 不仅能够完成基本日志读取，还能够在异常场景下保持较好的恢复能力，并为后端和前端提供运行状态依据。这些能力为系统形成稳定的“采集—存储—存证—审计”链路提供了基础。
305: 5.3 后端服务与数据持久化实现
306: 后端服务是系统连接日志采集端、链下数据库、智能合约与前端页面的核心层。Agent 采集到日志后，需要经由后端完成接收、校验、入库、哈希计算和链上存证；审计阶段又需要由后端读取日志原文、查询数据库哈希和链上哈希，并将比对结果保存为审计记录或告警记录。因此，后端不仅承担数据转发功能，还负责可信日志审计流程的业务编排和数据一致性维护。
307: 本系统后端基于 Node.js、Express 和 TypeScript 实现，采用 routes、controllers、services、repositories、db、blockchain 等分层结构。routes 层声明接口路径，controllers 层处理请求参数和响应结果，services 层组织核心业务流程，repositories 层封装 SQLite 数据访问，db 层提供数据库连接和表结构初始化能力，blockchain 层封装 LogRegistry 合约交互、哈希处理和合约代码存在性校验。通过分层组织，日志接收、链下持久化、链上写入、审计执行和告警查询等职责被清晰拆分，降低了模块之间的耦合程度。
308: 5.3.1 后端分层架构与核心接口实现
309: 后端接口以 REST API 形式向 Agent、前端页面和实验脚本提供服务。routes 层负责将不同访问路径分发到对应控制器，例如日志路由、审计路由、告警路由和总览路由。controllers 层位于路由与业务服务之间，主要完成请求体读取、基础参数校验、异常捕获和统一响应封装。以 POST /api/logs 为例，控制器接收 taskId、sourceType、sourcePath、logContent、logLevel、collectedAt 等字段后，将日志提交请求交由服务层处理。
310: services 层是后端业务逻辑的主要承载位置。日志服务负责日志查询和 Agent 状态同步，区块链服务负责组织日志入库、SHA-256 哈希计算和 LogRegistry 写入，审计执行服务负责批量审计、单条审计和三方哈希比对，告警服务负责异常告警查询，总览服务负责聚合日志数量、审计数量和告警数量等指标。repositories 层则负责访问 logs、log_hash_records、audit_records、alerts、agent_states 等 SQLite 表，使上层服务无需直接处理 SQL 细节。
311: 核心接口围绕系统主流程展开。POST /api/logs 是日志进入系统的入口，用于接收 Agent 上报或前端模拟提交的日志；GET /api/logs 用于日志中心列表展示；POST /api/audits/run 用于触发批量审计；GET /api/audits 用于查看审计记录；GET /api/alerts 用于查询异常告警；GET /api/overview 用于提供总览统计数据。这些接口共同构成后端服务边界，使日志采集、审计执行和前端展示能够通过统一 API 协同运行。
312: 5.3.2 日志入库、哈希计算与上链流程实现
313: 日志入库、哈希计算与上链流程是后端实现可信存证的关键路径。当 POST /api/logs 接收到日志后，系统首先将日志原文及其来源信息保存到 logs 表，形成可查询、可展示、可重算的链下日志记录。logs 表中的 log_content 是后续审计阶段重新计算 actualHash 的基础，因此系统需要保持日志正文与 task_id、source_path、collected_at 等元数据之间的稳定关联。
314: 日志保存完成后，后端对 log_content 计算 SHA-256 摘要，生成以 0x 开头的十六进制哈希值。该哈希值代表日志提交时的内容指纹，用于后续完整性校验。随后，后端通过 blockchain 层连接 LogRegistry 合约，调用 storeLog(taskId, logHash) 将 taskId 与 logHash 写入链上。合约记录中的 taskId、logHash、createdAt、submitter 为审计阶段提供链上依据。
315: 链上写入成功后，系统将 log_id、task_id、log_hash、contract_address、transaction_hash、block_number 和 on_chain_status 等信息保存到 log_hash_records 表。该表承担链下日志与链上存证之间的映射作用：log_id 指向 logs 表中的日志原文，log_hash 保存数据库中的期望哈希 expectedHash，contract_address、transaction_hash 和 block_number 用于定位链上存证记录。审计时系统可以根据 log_id 找到对应存证记录，再结合合约查询获得 onChainHash。
316: 考虑到本系统使用 Hardhat 本地链进行实验，链重启或合约多次部署可能导致历史合约地址失效。为降低误判风险，后端在链上读写前通过 provider.getCode(address) 校验合约地址是否存在字节码，并在审计时优先使用 log_hash_records.contract_address 回溯当时写入的合约地址。该处理使日志存证流程不仅能够完成正常上链，也能在实验环境变化时保留更明确的审计依据。
317: 5.3.3 审计记录与告警数据表实现
318: 审计记录与告警数据表用于保存日志可信性判断结果，是后端形成审计闭环的重要支撑。当前端或脚本调用 POST /api/audits/run 后，审计执行服务会读取待审计日志及其存证记录，重新计算日志原文哈希，并查询链上 LogRegistry 记录。比对完成后，系统将审计结果写入 audit_records 表；若发现哈希不一致，则进一步生成 alerts 表中的异常告警。
319: audit_records 表主要记录每次审计的执行结果，关键字段包括 log_id、log_hash_record_id、audit_status、expected_hash、actual_hash、on_chain_hash、audit_message 和 audited_at 等。其中，expected_hash 来自 log_hash_records，actual_hash 来自审计阶段对 logs.log_content 的重新计算，on_chain_hash 来自 LogRegistry 查询结果。三者一致时 audit_status 写为 passed；若数据库哈希、重算哈希或链上哈希存在不一致，则写为 failed；若链上记录缺失或暂不可用，则可写为 pending，以表示证据尚不完整。
320: alerts 表用于保存审计失败后的异常提示。当审计状态为 failed 时，系统生成 hash_mismatch 类型告警，并记录 related_log_id、related_audit_id、title、description、severity、status 等字段。related_log_id 用于定位异常日志，related_audit_id 用于追溯触发告警的审计记录，severity 和 status 用于支持前端展示风险等级和处理状态。通过审计记录与告警记录的关联，系统能够从“发现异常”进一步延伸到“提示异常并支持追踪”。
321: 从页面展示角度看，GET /api/audits 为审计管理页面提供历史结果，GET /api/alerts 为告警管理页面提供异常列表，GET /api/overview 则基于日志、审计和告警表生成统计指标。审计记录回答日志是否可信，告警记录回答异常如何提示和追踪，二者共同支撑篡改检测实验中的 failed 审计记录和 hash_mismatch 告警展示。
322: 5.4 前端可视化模块实现
323: 前端可视化模块用于向系统使用者展示日志、审计和告警信息。可信日志审计涉及日志采集状态、链下存储状态、链上存证结果、审计执行结果和异常告警等多类数据，如果只通过接口或数据库查看，难以直观体现系统运行效果。本系统基于 React、TypeScript 和 Ant Design 实现 Web 前端，通过系统总览、日志中心、审计管理和告警管理等页面，将后端数据转换为可浏览、可检索和可对比的界面信息。
324: 前端不直接访问数据库或区块链，而是通过 API 客户端调用后端 REST 接口。页面加载时，系统调用 GET /api/overview 获取总览统计，调用 GET /api/logs 获取日志列表，调用 GET /api/audits 获取审计记录，调用 GET /api/alerts 获取异常告警。用户触发审计操作时，前端调用 POST /api/audits/run，并在审计完成后刷新页面状态。该交互方式保持了前端展示层与后端可信逻辑之间的职责边界。

334: 5.5 功能测试与闭环验证
335: 为验证系统各模块是否能够按照设计目标协同运行，本节围绕智能合约、后端接口与审计闭环、Agent 采集与前端展示三个方面开展功能测试。功能测试的重点不是单纯验证某个函数是否能够运行，而是确认日志从采集、入库、哈希计算、链上存证、审计比对、告警生成到前端展示的闭环是否能够形成。测试过程中未引入论文事实之外的额外功能，主要依据项目中已有的合约测试、后端验证脚本、Agent 验证脚本和前端构建检查结论进行整理。
336: 5.5.1 智能合约功能测试
337: 智能合约功能测试主要面向 LogRegistry 合约展开，测试目标是确认合约能够稳定完成日志哈希存证、权限控制和查询操作。LogRegistry 合约负责保存 taskId、logHash、createdAt 和 submitter 四类核心字段，是系统链上可信存证的基础。如果合约写入或查询能力不可靠，则后续三方哈希比对将缺少可信的链上依据。
338: 测试内容覆盖合约部署、LOGGER_ROLE 权限控制、日志哈希写入、按记录编号查询、按 taskId 查询、任务日志数量统计、合约总记录数量统计以及异常输入处理等场景。测试结果显示，智能合约测试 8 项全部通过，说明合约基础功能满足系统原型验证需要。其中，权限测试用于确认未授权地址不能随意写入日志哈希，写入测试用于确认授权地址能够通过 storeLog(taskId, logHash) 保存存证记录，查询测试用于确认 getLog、getLogsByTaskId、getRecordIdsByTaskId、getTaskLogCount 和 getLogCount 等方法能够返回预期结果。
339: 从系统闭环角度看，合约测试通过说明链上存证模块能够为后端提供稳定接口。后端在日志提交阶段可以将计算得到的 logHash 写入合约，在审计阶段也能够根据 taskId 读取链上记录。该测试为后续后端接口验证和性能实验奠定了基础。
340: 5.5.2 后端接口与审计闭环测试
341: 后端接口与审计闭环测试主要验证 Server 能否正确完成日志接收、链下入库、哈希计算、链上写入、审计比对和异常告警。测试重点包括 POST /api/logs 日志提交接口、POST /api/audits/run 审计执行接口、GET /api/audits 审计记录查询接口和 GET /api/alerts 告警查询接口。通过这些接口，可以验证后端是否能够将第 3 章设计的可信日志审计机制落到实际运行流程中。
342: 在链上写入验证中，系统通过后端服务接收日志内容，将日志原文写入 logs 表，并对 log_content 计算 SHA-256 哈希。随后，后端调用 LogRegistry 合约的 storeLog 方法写入链上存证，并在 log_hash_records 表中保存 log_id、task_id、log_hash、contract_address、transaction_hash、block_number 和 on_chain_status 等信息。验证结果表明，日志提交后能够形成链下日志记录和链上哈希记录，说明后端完成了从接口输入到可信存证的主要流程。
343: 在 API 回归验证中，系统对日志提交、日志查询、审计触发、审计结果查询和告警查询等接口进行检查，确认接口能够返回结构化响应，并且前后端使用的数据字段保持一致。在审计闭环验证中，后端执行 runAuditForAllLogs 后，能够检测到 passed 与 failed 两类分支：当 expectedHash、actualHash 和 onChainHash 一致时，审计结果为 passed；当日志内容被修改或哈希比对不一致时，审计结果为 failed，并在 audit_records 表中写入 failed 记录，同时在 alerts 表中生成 hash_mismatch 类型告警。
344: 该测试说明，后端不只是完成日志保存，还能够将链下数据库、链上合约和审计告警串联起来。passed 分支验证了正常日志的可信校验路径，failed 分支验证了异常日志的识别与告警路径，二者共同证明系统具备基本的审计闭环能力。
345: 5.5.3 Agent 采集与前端展示测试
346: Agent 采集测试主要验证日志采集端能否按照增量方式读取文件，并维护读取偏移量。测试中，Agent 首次读取日志文件时能够采集已有日志行；在日志文件没有新增内容时，不会重复读取历史记录；当文件追加新日志后，Agent 仅采集新增部分。同时，offsetStore 能够保存 lastOffset，使 Agent 在后续运行中继续从正确位置读取。该结果说明，Agent 的增量读取和偏移量持久化机制能够减少重复采集问题。
347: 除基础采集外，Agent 还进行了真实提交链路验证。Agent 将采集到的日志封装为包含 taskId、sourceType、sourcePath、logContent、logLevel 和 collectedAt 等字段的数据，并提交给后端接口。后端接收后继续执行入库、哈希计算和上链流程。该测试说明，Agent 并非孤立的文件读取脚本，而是系统可信日志审计链路的输入端，能够为后端提供持续日志来源。
348: 前端展示测试主要通过 TypeScript 类型检查与 Vite 构建验证完成。前端工程的 build 脚本包含 tsc --noEmit 与 vite build，分别用于检查 TypeScript 类型一致性和生产构建结果。验证结论表明，前端 TypeScript 检查与 Vite 构建通过，说明系统总览、日志中心、审计管理和告警管理页面能够在工程层面完成构建。结合后端接口验证结果，前端能够通过 GET /api/logs、GET /api/audits、GET /api/alerts 和 GET /api/overview 展示日志、审计和告警数据。
349: 总体来看，Agent 采集、后端审计和前端展示能够形成连续路径：Agent 负责产生标准化日志输入，后端负责可信存证与审计判断，前端负责展示运行状态和异常结果。该功能验证说明系统闭环具备可运行性，为后续性能实验和篡改检测实验提供了基础。

353: 5.6.1 日志批量提交实验
354: 日志批量提交实验用于验证系统在连续接收日志并执行存证流程时的稳定性。实验通过脚本连续提交 100 条日志，每条日志经由后端接口进入系统，随后完成日志入库、SHA-256 哈希计算和链上存证记录写入。该实验能够反映 POST /api/logs 接口在批量场景下的可用性，也能够间接验证后端与 LogRegistry 合约之间的调用链路。
355: 实验结果显示，日志批量提交共执行 100 次，成功 100 次，失败 0 次，成功率为 100%。平均响应时间约为 107.03 ms，吞吐量约为 9.33 条/秒。该结果说明，在本地实验环境和当前系统规模下，日志提交链路能够稳定完成连续请求处理，没有出现批量提交失败的情况。平均响应时间包含后端处理、数据库写入、哈希计算和链上交互等环节，因此该指标能够较综合地反映日志提交链路的运行开销。
356: 从实验意义看，100 次连续提交成功表明系统具备基本的批量接入能力，能够支撑毕业设计原型系统的演示和验证需要。吞吐量为 9.33 条/秒，说明系统在本地链和 SQLite 条件下可以完成小规模任务日志的持续存证。但该结果并不代表系统已经适用于大规模生产环境，因为本实验使用的是本地开发链和原型数据库，后续若面向更高并发场景，还需要进一步优化数据库连接、合约交互方式和批量写入策略。
357: 5.6.2 批量审计性能实验
358: 批量审计性能实验用于观察系统在不同数据规模下执行审计任务的耗时情况。审计过程需要读取 logs 表中的日志原文，重新计算 actualHash，读取 log_hash_records 中的 expectedHash，并根据 taskId 和合约地址查询链上 onChainHash，最后完成三方比对并写入 audit_records。与日志提交相比，批量审计涉及更多记录遍历和链上查询，因此更能反映审计流程的整体处理开销。
359: 实验分别针对 100 条、500 条和 1000 条数据集执行批量审计，每个规模重复 5 轮，5 轮均全部成功。实验结果显示，100 条数据集平均耗时约为 3067.77 ms，500 条数据集平均耗时约为 15659.44 ms，1000 条数据集平均耗时约为 35032.13 ms。随着数据规模增加，批量审计总耗时呈明显上升趋势，说明审计处理时间与待审计日志数量具有较强相关性。
360: 从结果分析看，批量审计耗时由多个因素共同构成，包括数据库读取、哈希重算、链上记录查询、比对判断和审计结果写入。1000 条数据集平均耗时约 35032.13 ms，说明在本地实验环境下，系统能够完成千条级日志审计，但耗时已经较为明显。该结果符合原型系统特点：系统重点验证可信审计机制和闭环有效性，而不是追求极限性能。若后续需要提升批量审计效率，可以考虑减少重复链上查询、优化任务维度索引、批量处理数据库写入，或在合约与后端之间增加更高效的数据读取策略。
361: 5.6.3 篡改检测实验与结果分析
362: 篡改检测实验用于验证系统能否识别日志内容被修改后的异常情况。实验思路是先通过正常流程提交日志，使日志原文写入 logs 表，日志哈希写入 log_hash_records 和 LogRegistry；随后修改链下日志内容，使日志原文与原始哈希不再匹配；最后触发审计流程，观察系统是否能够识别哈希不一致并生成告警。
363: 实验结果显示，篡改检测实验中 auditStatus 为 failed，alertGenerated 为 true。该结果说明，当日志内容被修改后，审计阶段重新计算得到的 actualHash 与数据库中保存的 expectedHash 或链上 onChainHash 不一致，系统能够将审计状态判定为 failed。同时，系统在 failed 分支中生成 hash_mismatch 类型告警，并写入 alerts 表，使异常情况能够在前端告警页面中展示。
364: 从机制角度分析，篡改检测成功依赖于链上链下混合存储和三方哈希比对。链下 logs 表保存日志原文，log_hash_records 保存提交时的 expectedHash，LogRegistry 保存链上 onChainHash。当日志原文被修改后，actualHash 会随之变化，而链上哈希保持为原始存证结果。三者不一致时，系统即可判断日志存在完整性异常。由于链上哈希不直接依赖当前数据库中的日志内容，因此能够为篡改检测提供独立比对依据。
365: 该实验验证了系统设计目标中“发现日志被篡改并生成告警”的关键能力。需要说明的是，本实验验证的是内容篡改检测场景，即日志原文被修改后能否通过哈希不一致发现异常；对于更复杂的攻击行为，例如绕过 Agent 采集、破坏数据库文件或攻击区块链节点等情况，还需要结合权限控制、备份机制和运行环境安全策略进一步研究。就本毕业设计原型而言，篡改检测实验已经证明系统能够完成从异常发现到告警生成的基本闭环。
366: 5.7 本章小结
367: 本章围绕系统实现与实验验证展开，首先说明了系统开发环境和 Monorepo 工程结构，随后分别介绍了日志采集 Agent、后端服务与数据持久化、前端可视化模块的实现方式。在实现层面，Agent 负责增量读取日志并提交后端，Server 负责日志入库、哈希计算、链上存证、审计比对和告警生成，Web 前端负责展示日志、审计和告警结果，各模块共同构成可信任务日志审计系统的运行闭环。
368: 在测试与实验层面，本章完成了智能合约功能测试、后端接口与审计闭环测试、Agent 采集与前端展示测试。测试结果表明，LogRegistry 合约 8 项测试全部通过，后端能够验证链上写入、API 回归以及 passed/failed 审计分支，Agent 能够完成增量读取、偏移量持久化和真实提交，前端 TypeScript 检查与 Vite 构建通过。性能实验中，日志批量提交 100 次成功率为 100%，批量审计在 100、500、1000 条数据规模下 5 轮均成功。篡改检测实验中，系统能够将被修改日志判定为 failed，并生成告警。上述结果说明，本系统的核心闭环具备可运行性，篡改检测机制具有有效性，为后续全文总结和改进分析提供了实验依据。
369: 第 6 章 总结与展望
370: 6.1 研究工作总结
371: 本文围绕基于区块链的可信任务日志审计系统开展研究与实现，针对传统中心化日志在存储和审计过程中可能存在的篡改、删除、伪造以及审计证据可信性不足等问题，设计并实现了一个包含日志采集、链下存储、链上存证、审计比对、异常告警和前端展示的原型系统。系统以任务日志为对象，将区块链存证技术、哈希完整性校验和常规 Web 系统工程实现相结合，形成了较完整的可信日志审计流程。
372: 在系统架构方面，本文设计了由 Agent、Server、SQLite、LogRegistry 智能合约和 Web 前端组成的整体架构。Agent 模块负责对日志文件进行增量采集，并通过偏移量持久化、失败重试和状态同步机制提高采集过程的连续性。Server 后端负责接收日志、写入 SQLite、计算 SHA-256 日志哈希、调用智能合约进行链上存证，并在审计阶段组织哈希重算、链上查询和结果判定。SQLite 作为链下存储层，用于保存日志原文、存证记录、审计记录、告警记录和 Agent 状态。Web 前端用于展示系统总览、日志列表、审计结果和异常告警。
373: 在可信存证机制方面，本文采用链下保存日志原文、链上保存日志哈希摘要的混合存储模型。该模型避免将完整日志直接写入区块链所带来的存储成本和隐私风险，同时利用链上哈希记录为链下日志提供独立校验依据。LogRegistry 智能合约保存 taskId、logHash、createdAt 和 submitter 等字段，并通过 LOGGER_ROLE 控制日志写入权限，使链上存证记录具有明确的写入边界和查询接口。
374: 在审计机制方面，本文设计了 expectedHash、actualHash 和 onChainHash 三方哈希比对流程。expectedHash 来源于数据库存证记录，actualHash 来源于审计阶段对日志原文的重新计算，onChainHash 来源于 LogRegistry 合约查询结果。当三者一致时，审计结果为 passed；当存在哈希不一致时，审计结果为 failed，并生成 hash_mismatch 类型告警；当链上记录不可用或证据不完整时，可标记为 pending。该机制使系统能够识别日志内容被修改后的完整性异常。
375: 在工程实现与实验验证方面，本文完成了前后端分离、智能合约、数据库和日志采集端的实现，并进行了功能测试、性能实验和篡改检测实验。实验结果表明，LogRegistry 合约测试 8 项全部通过；日志批量提交 100 次全部成功，平均响应时间约 107.03 ms，吞吐量约 9.33 条/秒；批量审计 100、500、1000 条数据 5 轮全部成功；篡改检测实验能够生成 failed 审计记录和告警。上述结果说明，系统核心闭环具备可运行性，能够完成基本的可信日志审计任务。
376: 6.2 系统创新点
377: 本文的工作重点在于将区块链存证、哈希完整性校验和任务日志审计流程结合起来，形成一个可运行的毕业设计原型系统。系统创新点主要体现在工程设计和机制整合方面，不属于理论层面的突破，但对于解决中心化日志审计缺少可信依据的问题具有一定实践价值。
378: 第一，设计了链下原文与链上哈希结合的轻量化存证模型。传统日志审计系统通常将日志原文和审计依据集中保存在数据库或日志平台中，若中心化存储被破坏，日志可信性容易受到影响。本文没有将完整日志原文直接写入区块链，而是将日志原文保存在 SQLite 中，将 SHA-256 哈希摘要写入 LogRegistry 智能合约。该设计在降低链上存储成本和减少敏感日志暴露风险的同时，为链下日志提供了独立的链上校验依据。
379: 第二，构建了数据库哈希、链上哈希和重算哈希的三方比对机制。系统在日志提交阶段生成 expectedHash，并将哈希记录同时关联链下数据库和链上合约；在审计阶段重新计算日志原文得到 actualHash，并读取链上的 onChainHash。通过三方比对，系统能够区分正常日志、哈希不一致日志和链上证据不完整的情况，并将审计状态标记为 passed、failed 或 pending。相比只比较本地日志和数据库记录，该机制增加了链上独立证据维度。
380: 第三，引入了历史合约地址回溯与合约代码存在性校验。在本地 Hardhat 链或多次部署场景中，如果审计时只读取当前环境变量中的合约地址，可能导致历史日志被错误地关联到新合约或空地址。本文在 log_hash_records 中记录当时写入的 contract_address，并在审计时优先使用该地址进行回溯。同时，系统在链上读写前通过 provider.getCode(address) 校验目标地址是否存在合约字节码，避免本地链重启后空地址造成误判。这是面向工程实验可靠性的改进。
381: 第四，实现了采集、存证、审计、告警和展示的完整闭环。系统不仅包含智能合约存证模块，还实现了 Agent 增量采集、Server 后端服务、SQLite 持久化、审计告警和 React 前端展示。日志从文件产生后，可以经过采集端提交到后端，经由链下入库和链上存证形成校验依据，审计阶段发现异常后生成告警，并在前端页面展示结果。该闭环使可信日志审计机制具备可观察、可验证和可演示的工程形态。
382: 6.3 存在不足
383: 虽然本文完成了可信任务日志审计系统的设计与实现，并通过测试和实验验证了系统核心闭环的可运行性，但受毕业设计周期、实验环境和系统规模限制，当前系统仍存在一些不足，需要在后续研究和工程实践中进一步完善。
384: 首先，当前区块链环境主要基于本地 Hardhat 链。Hardhat 本地链便于开发、部署和测试智能合约，能够满足毕业设计原型系统的验证需求，但其网络环境、节点数量、共识机制和运行稳定性与公开测试网或联盟链仍存在差异。因此，当前实验结果更多反映本地开发环境下的可行性，尚不能完全代表真实多节点区块链环境中的运行效果。
385: 其次，链下数据库采用 SQLite，更适合原型验证和本地实验。SQLite 具有部署简单、便于维护和适合小规模系统的特点，但在高并发写入、多用户访问和大规模日志存储场景下扩展能力有限。随着日志数量增加，单机文件型数据库可能在并发处理、备份恢复和权限管理方面暴露不足。如果系统需要面向更复杂的生产环境，还需要考虑更适合服务端部署的数据库方案。
386: 再次，批量审计流程仍以串行处理为主，性能优化空间较大。当前系统能够完成 100、500、1000 条数据规模的批量审计实验，但审计过程涉及日志读取、哈希重算、链上查询和审计记录写入等多个环节。随着数据规模扩大，串行审计方式可能导致整体耗时增加。后续需要进一步优化链上查询策略、数据库批量写入方式和任务调度方式。
387: 此外，系统权限体系仍相对简单。当前权限控制重点集中在 LogRegistry 合约的 LOGGER_ROLE 写入权限，能够避免任意地址向合约写入日志哈希，但 Web 前端和后端业务层尚未形成完善的多角色用户权限体系。例如，不同用户在日志查看、审计触发、告警处理和系统配置方面的权限划分仍可进一步细化。
388: 最后，当前系统主要关注日志完整性校验，对日志语义分析和风险分级支持不足。系统能够通过哈希不一致识别日志内容被修改的情况，但尚未深入分析日志内容本身是否存在异常行为、攻击特征或业务风险。告警类型也主要围绕 hash_mismatch 展开，距离更全面的智能化日志审计仍有进一步提升空间。
389: 6.4 后续优化方向
390: 针对当前系统存在的不足，后续可以从区块链环境、权限体系、审计性能、日志分析能力和前端可视化等方面继续优化，使系统从毕业设计原型逐步向更完整的可信日志审计平台演进。
391: 首先，可以将区块链环境从本地 Hardhat 链扩展到联盟链或公开测试网。联盟链更适合组织内部或多方协作审计场景，能够在节点准入、性能控制和隐私保护之间取得平衡；公开测试网则有助于验证系统在更接近真实链上环境中的交易确认、合约调用和异常处理能力。接入更真实的区块链网络后，需要进一步完善合约部署、地址管理、链上交易确认和异常重试机制。
392: 其次，可以完善多角色用户权限体系。当前系统主要通过 LOGGER_ROLE 控制合约写入权限，后续可以在后端和前端增加管理员、审计员、普通查看用户等角色划分。不同角色可以分别拥有日志查看、审计触发、告警处理、Agent 管理和系统配置等权限。通过更细粒度的权限设计，可以提高系统在实际使用场景中的安全性和可管理性。
393: 再次，可以引入异步审计队列和并发处理机制。当前批量审计以同步和串行处理为主，后续可以将审计任务放入异步队列，由后台工作线程或任务调度模块逐步处理。对于日志哈希重算、数据库写入和链上查询等环节，可以结合批量哈希计算、并发审计和缓存策略进行优化，减少重复查询和阻塞等待，提高大规模日志审计效率。
394: 此外，可以增强日志语义分析与风险分级能力。当前系统主要基于哈希一致性判断日志是否被篡改，后续可以结合日志级别、关键词、异常模式、任务类型和历史告警情况，对日志内容进行更细致的语义分析。系统可以在 hash_mismatch 告警之外增加更多告警类型，并根据风险程度进行分级，使审计结果不仅反映完整性异常，也能反映潜在运行风险。
395: 最后，可以进一步完善可视化分析能力。现有前端已经能够展示系统总览、日志列表、审计结果和告警信息，后续可以增加审计趋势分析、任务维度统计、链上交易追踪、告警处理流程和多维筛选能力。通过更丰富的可视化方式，审计人员能够更直观地理解系统运行状态和风险变化，提高可信日志审计系统的可用性。
396: 6.5 本章小结
397: 本章对全文研究工作进行了总结，并对系统创新点、存在不足和后续优化方向进行了归纳。本文围绕可信任务日志审计问题，设计并实现了包含 Agent 采集、Server 后端处理、SQLite 链下存储、LogRegistry 链上存证、三方哈希比对、异常告警和 Web 前端展示的原型系统。通过功能测试、性能实验和篡改检测实验，系统验证了可信日志审计闭环的可运行性，以及日志内容被修改后生成 failed 审计记录和告警的有效性。
398: 同时，当前系统仍存在本地链实验环境有限、SQLite 高并发能力不足、批量审计性能仍可优化、权限体系和日志语义分析不够完善等问题。后续可从联盟链或测试网接入、多角色权限控制、异步审计队列、并发审计优化、风险分级和可视化分析等方面继续改进。总体而言，本文完成了可信任务日志审计系统原型，为区块链存证技术在日志完整性审计中的应用提供了工程实践参考。
