# 阶段 0：论文写作准备资料

论文题目：基于区块链的可信任务日志审计系统设计与实现

说明：本文档用于沉淀论文写作前的事实资料、统一术语和写作规范，不作为正式论文正文。后续正式论文正文仍应单独写入论文主文件。

## 一、论文写作事实资料包

### 1. 课题背景

在信息系统运行过程中，服务器、应用服务、数据库和任务执行程序会持续产生日志数据。日志通常用于安全审计、故障定位、责任追溯和运行状态分析，是系统可信运行的重要依据。

传统日志系统多采用中心化存储方式，日志原文通常保存在数据库或文件系统中。当系统管理员、攻击者或内部人员具备较高权限时，日志存在被篡改、删除或伪造的风险，导致后续审计结果缺少独立可信证据。

区块链具有不可篡改、可追溯和公开可验证等特性，适合保存关键数据摘要和存证元数据。本课题将区块链存证能力与日志完整性校验结合，用于提升任务日志审计过程的可信性。

### 2. 系统目标

本系统目标是构建一个基于区块链的可信任务日志审计系统，形成从日志采集、链下存储、链上存证、审计核验、异常告警到前端展示的完整闭环。

系统采用“链下保存日志原文、链上保存日志哈希”的混合存储方式，在避免日志原文直接上链带来存储成本和隐私风险的同时，为日志完整性校验提供可信依据。

系统通过审计阶段重新计算日志哈希，并与数据库记录和链上记录进行比对，识别链下日志是否被修改。

### 3. 系统模块

- Agent 日志采集模块：负责监听或读取本地日志文件，支持增量读取、偏移量持久化、失败重试和运行状态同步。
- Server 后端服务模块：负责接收日志、写入 SQLite、计算哈希、调用智能合约、执行审计、生成告警，并向前端提供 API。
- SQLite 链下存储模块：负责保存日志原文、存证记录、审计记录、告警记录和 Agent 状态等数据。
- LogRegistry 智能合约模块：负责将日志哈希、任务标识、提交时间和提交者地址写入链上，并提供按任务标识查询的能力。
- 审计告警模块：负责重新计算日志哈希，与数据库和链上记录进行比对，并在发现异常时生成告警。
- Web 前端可视化模块：负责展示系统总览、日志列表、审计结果、告警信息和趋势图表。

### 4. 技术栈

- 前端采用 React、TypeScript 和 Ant Design，用于构建系统总览、日志中心、审计管理和告警管理页面。
- 后端采用 Node.js、Express 和 TypeScript，实现 REST API、业务服务、数据访问和链上交互。
- 数据库采用 SQLite，适合作为毕业设计原型系统的数据持久化方案。
- 区块链相关部分采用 Hardhat、Solidity、OpenZeppelin AccessControl 和 Ethers，用于合约开发、部署、测试和后端调用。

### 5. 系统数据流

日志文件产生新日志后，Agent 根据偏移量读取新增内容，并将日志封装为标准提交数据。Server 接收日志后写入 SQLite 的 logs 表，并对 log_content 计算 SHA-256 哈希。随后，Server 调用 LogRegistry.storeLog(taskId, logHash) 将日志哈希写入链上，并在 log_hash_records 表中记录合约地址、交易哈希、区块号和链上状态。

审计阶段，Server 读取日志原文重新计算 actualHash，读取数据库 expectedHash，并从 LogRegistry 查询 onChainHash，完成三方哈希比对。当比对结果不一致时，系统生成 failed 审计记录，并写入 hash_mismatch 类型告警。前端负责展示日志、审计和告警结果。

### 6. 数据库表设计概览

- logs 表用于保存日志原文与采集来源信息，关键字段包括 task_id、source_type、source_path、log_content、log_level、collected_at 和 status。
- log_hash_records 表用于保存日志哈希及链上写入信息，关键字段包括 log_id、task_id、log_hash、chain_name、contract_address、transaction_hash、block_number 和 on_chain_status。
- audit_records 表用于保存审计执行结果，关键字段包括 log_id、log_hash_record_id、audit_status、expected_hash、actual_hash、audit_message 和 audited_at。
- alerts 表用于保存异常告警，关键字段包括 alert_type、severity、related_log_id、related_audit_id、title、description 和 status。
- agent_states 表用于保存 Agent 运行状态，关键字段包括 agent_name、source_path、last_offset、last_heartbeat_at、last_sync_at、status 和 error_message。

### 7. 智能合约设计

LogRegistry 合约负责保存日志哈希存证记录，其 LogRecord 结构体包含 taskId、logHash、createdAt 和 submitter。合约通过 LOGGER_ROLE 控制日志写入权限，避免任意地址向链上写入不可信数据。DEFAULT_ADMIN_ROLE 用于角色管理。

合约支持 storeLog、getLog、getRecordIdsByTaskId、getLogsByTaskId、getTaskLogCount、getLogCount 等方法，满足写入、单条查询和任务维度查询需求。系统只将日志哈希写入链上，不直接保存日志原文，从而降低链上存储成本并减少敏感信息暴露风险。

### 8. 审计机制

审计阶段，系统读取日志原文并重新计算 actualHash，从 log_hash_records 表读取 expectedHash，并根据 contract_address 查询对应 LogRegistry 合约中的 onChainHash。

当 expectedHash、actualHash 和 onChainHash 一致时，审计状态为 passed；当本地重算结果与存证记录不一致时，审计状态为 failed；当链上记录暂不可用或记录不完整时，可根据情况标记为 pending。对于 failed 审计结果，系统生成 hash_mismatch 类型告警，并关联对应日志记录和审计记录。

### 9. 实验数据

- 合约测试 8 项全部通过，覆盖角色授权、日志写入、非法调用拦截、按任务查询和空参数拒绝等核心逻辑。
- 日志批量提交实验中，100 次请求全部成功，成功率为 100%，平均响应时间约 107.03 ms，吞吐量约 9.33 条/秒。
- 批量审计实验中，100、500、1000 条数据规模分别执行 5 轮，全部成功，平均耗时约 3067.77 ms、15659.44 ms、35032.13 ms。
- 篡改检测实验中，系统能够识别链下日志内容被修改的情况，并生成 failed 审计记录和异常告警。

### 10. 系统创新点

- 采用链下日志原文存储与链上日志哈希存证相结合的轻量化可信存证模型，兼顾存储效率、隐私保护和可验证性。
- 设计数据库哈希、链上哈希与审计重算哈希的三方比对机制，用于识别链下日志内容是否被篡改。
- 引入历史合约地址回溯审计策略，审计时优先使用 log_hash_records.contract_address 读取对应合约，提高多次部署场景下历史记录审计的准确性。
- 加入合约代码存在性校验机制，避免本地链重启后空地址导致的误判，提高实验结果可信度。
- 实现从日志采集、链上存证、审计核验、异常告警到前端展示的完整工程闭环。

### 11. 系统局限性

- 当前区块链环境基于本地 Hardhat 节点，尚未扩展到公开测试网或联盟链环境。
- SQLite 适合作为毕业设计原型系统的数据存储方案，但在高并发和大规模生产环境中扩展能力有限。
- 批量审计当前以正确性和可复现性为主要目标，性能仍有进一步并发优化空间。
- 系统权限体系主要围绕合约写入权限展开，尚未形成完整的多角色用户管理体系。
- 当前审计重点是日志完整性校验，尚未深入进行日志语义分析和风险分级。

## 三、章节写作风格规范

### 1. 全文通用写作规范

1. 全文语言应正式、客观、连贯，避免口语化表达，不使用“我”“我们”等第一人称。
2. 技术描述应以系统事实为依据，不编造不存在的功能、实验数据、参考文献或代码。
3. 每个章节应围绕该章标题展开，避免跨章节提前展开过多内容。
4. 涉及实验结果时必须使用已验证数据，保持数值、单位和结论一致。
5. 涉及创新点时应保持适度表达，强调工程设计与实现价值，避免夸大为理论突破。

### 2. 各章节写作重点

- 第 1 章 绪论：重点说明研究背景、国内外研究现状、当前问题、本文主要研究内容和论文结构。该章应从可信日志审计需求自然引出区块链存证方案。
- 第 2 章 相关理论与关键技术：重点介绍区块链、智能合约、哈希完整性校验和系统开发技术。该章不应写成技术百科，应服务于后续系统设计。
- 第 3 章 基于区块链的可信日志存证与审计机制设计：全文核心章节，应突出链上链下混合存储、LogRegistry 合约、三方哈希比对、历史合约地址回溯、合约代码存在性校验、篡改检测与告警机制。
- 第 4 章 系统需求分析与总体设计：重点说明业务场景、功能需求、非功能需求、总体架构、功能模块、数据流和数据库设计，为系统实现提供结构支撑。
- 第 5 章 系统实现与实验验证：重点结合真实模块、真实接口和真实实验结果，说明系统如何实现并验证可信日志审计闭环。
- 第 6 章 总结与展望：总结全文工作、系统创新点、存在不足和后续优化方向，语言应收束自然。

2. LogRegistry 智能合约：说明 taskId、logHash、createdAt、submitter 等字段，以及 LOGGER_ROLE 权限控制的必要性。
3. 三方哈希比对机制：说明 expectedHash、actualHash、onChainHash 的来源和审计判定逻辑。
