# 第 6 章 总结与展望

## 6.1 研究工作总结

本文围绕基于区块链的可信任务日志审计系统开展研究与实现，针对传统中心化日志在存储和审计过程中可能存在的篡改、删除、伪造以及审计证据可信性不足等问题，设计并实现了一个包含日志采集、链下存储、链上存证、审计比对、异常告警和前端展示的原型系统。系统以任务日志为对象，将区块链存证技术、哈希完整性校验和常规 Web 系统工程实现相结合，形成了较完整的可信日志审计流程。

在系统架构方面，本文设计了由 Agent、Server、SQLite、LogRegistry 智能合约和 Web 前端组成的整体架构。Agent 模块负责对日志文件进行增量采集，并通过偏移量持久化、失败重试和状态同步机制提高采集过程的连续性。Server 后端负责接收日志、写入 SQLite、计算 SHA-256 日志哈希、调用智能合约进行链上存证，并在审计阶段组织哈希重算、链上查询和结果判定。SQLite 作为链下存储层，用于保存日志原文、存证记录、审计记录、告警记录和 Agent 状态。Web 前端用于展示系统总览、日志列表、审计结果和异常告警。

在可信存证机制方面，本文采用链下保存日志原文、链上保存日志哈希摘要的混合存储模型。该模型避免将完整日志直接写入区块链所带来的存储成本和隐私风险，同时利用链上哈希记录为链下日志提供独立校验依据。LogRegistry 智能合约保存 taskId、logHash、createdAt 和 submitter 等字段，并通过 LOGGER_ROLE 控制日志写入权限，使链上存证记录具有明确的写入边界和查询接口。

在审计机制方面，本文设计了 expectedHash、actualHash 和 onChainHash 三方哈希比对流程。expectedHash 来源于数据库存证记录，actualHash 来源于审计阶段对日志原文的重新计算，onChainHash 来源于 LogRegistry 合约查询结果。当三者一致时，审计结果为 passed；当存在哈希不一致时，审计结果为 failed，并生成 hash_mismatch 类型告警；当链上记录不可用或证据不完整时，可标记为 pending。该机制使系统能够识别日志内容被修改后的完整性异常。

在工程实现与实验验证方面，本文完成了前后端分离、智能合约、数据库和日志采集端的实现，并进行了功能测试、性能实验和篡改检测实验。实验结果表明，LogRegistry 合约测试 8 项全部通过；日志批量提交 100 次全部成功，平均响应时间约 107.03 ms，吞吐量约 9.33 条/秒；批量审计 100、500、1000 条数据 5 轮全部成功；篡改检测实验能够生成 failed 审计记录和告警。上述结果说明，系统核心闭环具备可运行性，能够完成基本的可信日志审计任务。

本节关键信息摘要：

1. 本文完成了可信任务日志审计系统的架构设计、模块实现和实验验证。
2. 系统采用 Agent、Server、SQLite、LogRegistry 和 Web 前端协同架构。
3. 链上链下混合存储模型兼顾日志查询效率、存储成本和可信校验。
4. 三方哈希比对机制能够支撑日志完整性审计和异常告警。
5. 功能测试、性能实验和篡改检测实验验证了系统闭环可运行性。

## 6.2 系统创新点

本文的工作重点在于将区块链存证、哈希完整性校验和任务日志审计流程结合起来，形成一个可运行的毕业设计原型系统。系统创新点主要体现在工程设计和机制整合方面，不属于理论层面的突破，但对于解决中心化日志审计缺少可信依据的问题具有一定实践价值。

第一，设计了链下原文与链上哈希结合的轻量化存证模型。传统日志审计系统通常将日志原文和审计依据集中保存在数据库或日志平台中，若中心化存储被破坏，日志可信性容易受到影响。本文没有将完整日志原文直接写入区块链，而是将日志原文保存在 SQLite 中，将 SHA-256 哈希摘要写入 LogRegistry 智能合约。该设计在降低链上存储成本和减少敏感日志暴露风险的同时，为链下日志提供了独立的链上校验依据。

第二，构建了数据库哈希、链上哈希和重算哈希的三方比对机制。系统在日志提交阶段生成 expectedHash，并将哈希记录同时关联链下数据库和链上合约；在审计阶段重新计算日志原文得到 actualHash，并读取链上的 onChainHash。通过三方比对，系统能够区分正常日志、哈希不一致日志和链上证据不完整的情况，并将审计状态标记为 passed、failed 或 pending。相比只比较本地日志和数据库记录，该机制增加了链上独立证据维度。

第三，引入了历史合约地址回溯与合约代码存在性校验。在本地 Hardhat 链或多次部署场景中，如果审计时只读取当前环境变量中的合约地址，可能导致历史日志被错误地关联到新合约或空地址。本文在 log_hash_records 中记录当时写入的 contract_address，并在审计时优先使用该地址进行回溯。同时，系统在链上读写前通过 provider.getCode(address) 校验目标地址是否存在合约字节码，避免本地链重启后空地址造成误判。这是面向工程实验可靠性的改进。

第四，实现了采集、存证、审计、告警和展示的完整闭环。系统不仅包含智能合约存证模块，还实现了 Agent 增量采集、Server 后端服务、SQLite 持久化、审计告警和 React 前端展示。日志从文件产生后，可以经过采集端提交到后端，经由链下入库和链上存证形成校验依据，审计阶段发现异常后生成告警，并在前端页面展示结果。该闭环使可信日志审计机制具备可观察、可验证和可演示的工程形态。

本节关键信息摘要：

1. 系统创新主要体现在工程机制整合和原型实现方面，不夸大为理论突破。
2. 链下原文与链上哈希结合形成轻量化可信存证模型。
3. 三方哈希比对机制引入链上独立证据维度。
4. 历史合约地址回溯和合约代码存在性校验提升了实验可靠性。
5. 系统实现了采集、存证、审计、告警和展示的完整闭环。

## 6.3 存在不足

虽然本文完成了可信任务日志审计系统的设计与实现，并通过测试和实验验证了系统核心闭环的可运行性，但受毕业设计周期、实验环境和系统规模限制，当前系统仍存在一些不足，需要在后续研究和工程实践中进一步完善。

首先，当前区块链环境主要基于本地 Hardhat 链。Hardhat 本地链便于开发、部署和测试智能合约，能够满足毕业设计原型系统的验证需求，但其网络环境、节点数量、共识机制和运行稳定性与公开测试网或联盟链仍存在差异。因此，当前实验结果更多反映本地开发环境下的可行性，尚不能完全代表真实多节点区块链环境中的运行效果。

其次，链下数据库采用 SQLite，更适合原型验证和本地实验。SQLite 具有部署简单、便于维护和适合小规模系统的特点，但在高并发写入、多用户访问和大规模日志存储场景下扩展能力有限。随着日志数量增加，单机文件型数据库可能在并发处理、备份恢复和权限管理方面暴露不足。如果系统需要面向更复杂的生产环境，还需要考虑更适合服务端部署的数据库方案。

再次，批量审计流程仍以串行处理为主，性能优化空间较大。当前系统能够完成 100、500、1000 条数据规模的批量审计实验，但审计过程涉及日志读取、哈希重算、链上查询和审计记录写入等多个环节。随着数据规模扩大，串行审计方式可能导致整体耗时增加。后续需要进一步优化链上查询策略、数据库批量写入方式和任务调度方式。

此外，系统权限体系仍相对简单。当前权限控制重点集中在 LogRegistry 合约的 LOGGER_ROLE 写入权限，能够避免任意地址向合约写入日志哈希，但 Web 前端和后端业务层尚未形成完善的多角色用户权限体系。例如，不同用户在日志查看、审计触发、告警处理和系统配置方面的权限划分仍可进一步细化。

最后，当前系统主要关注日志完整性校验，对日志语义分析和风险分级支持不足。系统能够通过哈希不一致识别日志内容被修改的情况，但尚未深入分析日志内容本身是否存在异常行为、攻击特征或业务风险。告警类型也主要围绕 hash_mismatch 展开，距离更全面的智能化日志审计仍有进一步提升空间。

本节关键信息摘要：

1. 当前区块链环境基于本地 Hardhat 链，尚未接入公开测试网或联盟链。
2. SQLite 适合原型验证，但高并发和大规模存储能力有限。
3. 批量审计以串行为主，链上查询和审计写入仍可优化。
4. 系统权限体系主要集中在合约写入控制，业务角色划分不够完善。
5. 当前审计重点是完整性校验，日志语义分析和风险分级仍不足。

## 6.4 后续优化方向

针对当前系统存在的不足，后续可以从区块链环境、权限体系、审计性能、日志分析能力和前端可视化等方面继续优化，使系统从毕业设计原型逐步向更完整的可信日志审计平台演进。

首先，可以将区块链环境从本地 Hardhat 链扩展到联盟链或公开测试网。联盟链更适合组织内部或多方协作审计场景，能够在节点准入、性能控制和隐私保护之间取得平衡；公开测试网则有助于验证系统在更接近真实链上环境中的交易确认、合约调用和异常处理能力。接入更真实的区块链网络后，需要进一步完善合约部署、地址管理、链上交易确认和异常重试机制。

其次，可以完善多角色用户权限体系。当前系统主要通过 LOGGER_ROLE 控制合约写入权限，后续可以在后端和前端增加管理员、审计员、普通查看用户等角色划分。不同角色可以分别拥有日志查看、审计触发、告警处理、Agent 管理和系统配置等权限。通过更细粒度的权限设计，可以提高系统在实际使用场景中的安全性和可管理性。

再次，可以引入异步审计队列和并发处理机制。当前批量审计以同步和串行处理为主，后续可以将审计任务放入异步队列，由后台工作线程或任务调度模块逐步处理。对于日志哈希重算、数据库写入和链上查询等环节，可以结合批量哈希计算、并发审计和缓存策略进行优化，减少重复查询和阻塞等待，提高大规模日志审计效率。

此外，可以增强日志语义分析与风险分级能力。当前系统主要基于哈希一致性判断日志是否被篡改，后续可以结合日志级别、关键词、异常模式、任务类型和历史告警情况，对日志内容进行更细致的语义分析。系统可以在 hash_mismatch 告警之外增加更多告警类型，并根据风险程度进行分级，使审计结果不仅反映完整性异常，也能反映潜在运行风险。

最后，可以进一步完善可视化分析能力。现有前端已经能够展示系统总览、日志列表、审计结果和告警信息，后续可以增加审计趋势分析、任务维度统计、链上交易追踪、告警处理流程和多维筛选能力。通过更丰富的可视化方式，审计人员能够更直观地理解系统运行状态和风险变化，提高可信日志审计系统的可用性。

本节关键信息摘要：

1. 后续可接入联盟链或公开测试网，以验证更真实链上环境。
2. 可扩展管理员、审计员和普通用户等多角色权限体系。
3. 可通过异步审计队列、批量哈希和并发审计提升性能。
4. 可增强日志语义分析、风险分级和多类型告警能力。
5. 可进一步完善审计趋势、交易追踪和告警处理等可视化分析。

## 6.5 本章小结

本章对全文研究工作进行了总结，并对系统创新点、存在不足和后续优化方向进行了归纳。本文围绕可信任务日志审计问题，设计并实现了包含 Agent 采集、Server 后端处理、SQLite 链下存储、LogRegistry 链上存证、三方哈希比对、异常告警和 Web 前端展示的原型系统。通过功能测试、性能实验和篡改检测实验，系统验证了可信日志审计闭环的可运行性，以及日志内容被修改后生成 failed 审计记录和告警的有效性。

同时，当前系统仍存在本地链实验环境有限、SQLite 高并发能力不足、批量审计性能仍可优化、权限体系和日志语义分析不够完善等问题。后续可从联盟链或测试网接入、多角色权限控制、异步审计队列、并发审计优化、风险分级和可视化分析等方面继续改进。总体而言，本文完成了可信任务日志审计系统原型，为区块链存证技术在日志完整性审计中的应用提供了工程实践参考。

本节关键信息摘要：

1. 本章总结了全文研究成果、系统创新点、存在不足和优化方向。
2. 系统实现了从日志采集到前端展示的可信审计闭环。
3. 实验验证了系统闭环可运行性和篡改检测有效性。
4. 后续工作可围绕真实链环境、权限体系、审计性能和风险分析继续完善。
