## 4.2 系统需求分析

本系统面向任务日志可信审计场景，核心目标是使日志从产生、采集、存储、存证到审计和告警的全过程具备可追溯性和可验证性。传统日志系统通常能够完成日志保存和查询，但在日志被篡改、删除或伪造时，缺少独立可信的校验依据。因此，本系统的功能需求不仅包括一般日志系统中的采集、存储和展示能力，还需要围绕区块链可信存证、哈希完整性校验、异常告警和可视化审计构建完整能力。

从用户使用角度看，系统需要支持日志自动进入审计流程，减少人工导入带来的遗漏和不一致；需要将日志摘要写入链上，形成独立于链下数据库的可信证据；需要在审计阶段对链下日志重新计算哈希，并与数据库记录、链上记录进行比对；需要在发现异常时及时生成告警；同时需要通过前端页面展示日志、审计结果和告警状态，使用户能够直观了解系统运行情况。上述需求共同支撑第 3 章提出的可信日志存证与审计机制。

### 4.2.1 日志自动采集需求

日志自动采集是系统可信审计流程的起点。若日志进入系统依赖人工复制或手动提交，不仅效率较低，也容易出现遗漏、重复或时间不一致等问题。为保证任务日志能够及时纳入审计范围，系统需要提供自动采集能力，使日志文件产生新增内容后能够被 Agent 识别并提交至后端服务。

从功能角度看，Agent 需要能够读取指定日志文件，并基于偏移量记录方式识别新增日志内容，避免重复采集已处理的历史日志。对于已经采集的日志，Agent 应将其封装为统一数据格式，包含任务标识、日志来源、日志级别、日志内容和采集时间等字段，并提交给后端接口。为提高采集过程的可靠性，系统还需要支持失败重试和状态同步能力。当网络异常或后端暂时不可用时，采集端应能够保留待提交数据，并在后续恢复后继续上报。

日志自动采集需求直接支撑可信审计链路的完整性。只有日志能够稳定进入系统，后续链下入库、哈希计算、链上存证和审计比对才具备数据基础。因此，Agent 模块不仅是日志获取工具，也是系统审计闭环的入口。

本节关键信息摘要：

1. 日志自动采集用于减少人工导入造成的遗漏、重复和时间不一致问题。
2. Agent 需要支持增量读取、日志封装、失败重试和状态同步。
3. 采集数据应包含任务标识、来源、级别、内容和采集时间等字段。
4. 稳定采集能力是链下入库、链上存证和审计比对的前提。

### 4.2.2 链上可信存证需求

链上可信存证是本系统区别于传统日志管理系统的重要需求。传统日志系统通常将日志原文和审计依据都保存在中心化数据库中，一旦数据库中的日志或哈希记录被修改，系统难以提供独立证据说明日志是否保持原始状态。因此，系统需要利用区块链的不可篡改和可追溯特性，将日志关键摘要信息写入链上，形成独立于链下数据库的可信存证。

从系统能力角度看，链上存证不要求直接保存完整日志原文，而是保存日志哈希、任务标识、写入时间和提交者地址等必要信息。日志原文仍保存在 SQLite 中，便于查询和展示；链上只保存固定长度哈希摘要，用于完整性校验。后端服务在接收日志并计算 SHA-256 哈希后，应调用 LogRegistry 智能合约完成上链写入，并记录交易哈希、区块号、合约地址和链上状态。

链上可信存证需求为后续审计比对提供了外部证据来源。审计阶段，系统能够根据任务标识和历史合约地址读取链上哈希记录，并与数据库哈希和重算哈希进行对比。通过该需求，系统能够避免完全依赖链下数据库，提高日志完整性验证的可信度。

本节关键信息摘要：

1. 链上可信存证用于为日志完整性校验提供独立证据来源。
2. 系统链上保存日志哈希和必要元数据，不直接保存日志原文。
3. 后端需要记录交易哈希、区块号、合约地址和链上状态。
4. 链上存证是三方哈希比对机制的重要基础。

### 4.2.3 审计校验需求

审计校验是系统判断日志是否可信的核心功能。日志完成采集和存证后，系统需要在用户触发或系统执行审计任务时，对日志内容进行重新核验。该需求的目标是发现链下日志是否在存储过程中被修改，并将审计结果持久化保存，供后续查询、展示和告警处理使用。

从系统流程看，审计校验需要读取待审计日志原文，重新计算 actualHash；读取 log_hash_records 表中的 expectedHash；再根据任务标识和合约地址查询 LogRegistry 合约中的 onChainHash。系统应根据 expectedHash、actualHash 和 onChainHash 的比对结果生成审计状态。当三方一致时，审计状态为 passed；当重算哈希与数据库或链上记录不一致时，审计状态为 failed；当链上记录暂不可用或证据不完整时，可标记为 pending。

审计校验需求要求系统不仅返回即时结果，还要将审计状态、期望哈希、实际哈希和审计说明写入 audit_records 表。这样可以保留每次审计的过程证据，使前端和后续分析能够追踪审计历史。该需求直接对应第 3 章提出的三方哈希比对机制，是系统实现可信日志审计的关键环节。

本节关键信息摘要：

1. 审计校验用于判断链下日志内容是否与原始存证保持一致。
2. 审计过程需要比对 expectedHash、actualHash 和 onChainHash。
3. 审计状态包括 passed、failed 和 pending。
4. 审计结果需要写入 audit_records 表，便于追踪和展示。

### 4.2.4 异常告警需求

日志审计系统不仅需要发现异常，还需要将异常以明确方式提示给用户。如果系统只在审计接口中返回 failed 状态，用户可能需要主动查看审计列表才能发现问题，异常响应不够直观。因此，本系统需要具备异常告警能力，在审计发现哈希不一致时自动生成告警记录，并通过前端页面进行展示。

异常告警需求主要针对审计状态为 failed 的情况。当系统判断日志重算哈希与数据库或链上存证不一致时，应生成 hash_mismatch 类型告警，并将该告警与对应日志记录和审计记录关联。告警记录需要包含告警类型、严重程度、关联日志编号、关联审计编号、标题、描述和处理状态等信息。通过这些字段，用户可以从告警列表定位异常日志，也可以进一步查看相关审计记录和哈希比对结果。

告警需求能够将底层哈希比对结果转化为面向用户的风险提示。它使系统从“被动审计查询”扩展为“主动异常提示”，有助于用户及时关注日志完整性风险。该需求与第 3 章中的篡改检测与异常告警机制相对应，是可信审计闭环中从检测到反馈的重要环节。

本节关键信息摘要：

1. 异常告警用于将审计失败结果转化为可追踪风险事件。
2. failed 审计结果会触发 hash_mismatch 类型告警。
3. 告警需要关联日志记录和审计记录，便于后续追溯。
4. 告警展示提高了系统对日志篡改风险的提示能力。

### 4.2.5 可视化展示需求

可信日志审计结果需要通过直观方式呈现给用户，才能支持日常查看、问题定位和答辩演示。系统后端虽然能够完成日志存储、链上写入和审计比对，但如果缺少前端展示，用户难以快速理解系统运行状态。因此，本系统需要提供 Web 可视化界面，集中展示日志、审计和告警相关信息。

从功能需求看，前端需要提供系统总览页面，用于展示日志数量、审计通过情况、异常告警数量等统计指标；需要提供日志中心页面，用于查看日志列表、任务标识、日志级别和采集时间；需要提供审计管理页面，用于展示审计状态、哈希比对结果和审计说明；还需要提供告警管理页面，用于展示 hash_mismatch 告警及其处理状态。通过这些页面，用户能够从整体到局部了解系统可信审计情况。

可视化展示需求不仅服务于用户交互，也有助于验证系统闭环是否完整。日志能否展示、审计结果能否查询、告警能否呈现，能够反映后端接口、数据库记录和前端数据映射是否正常。因此，前端可视化是系统可用性的重要组成部分，也是展示区块链可信日志审计效果的重要窗口。

本节关键信息摘要：

1. 可视化展示用于呈现日志、审计结果、告警和统计信息。
2. 前端页面包括系统总览、日志中心、审计管理和告警管理。
3. 可视化能力使用户能够直观理解可信审计结果。
4. 前端展示也是验证系统闭环是否完整的重要方式。

## 4.3 非功能需求分析

除功能需求外，可信任务日志审计系统还需要满足数据可信性、系统可用性、可维护性与可扩展性等非功能需求。非功能需求决定系统在实际运行和后续扩展中的稳定性，也影响论文实验和答辩演示过程中的可复现性。本系统作为毕业设计原型，需要在工程复杂度可控的前提下，突出可信审计机制的有效性。

### 4.3.1 数据可信性需求

数据可信性是本系统最核心的非功能需求。系统需要保证日志从采集、入库、哈希生成、链上存证到审计比对的过程具有可追溯性，能够在日志内容被修改时发现异常。为满足该需求，系统采用链下原文存储与链上哈希存证相结合的方式，使日志原文和完整性证据不完全依赖同一中心化数据库。

在链下部分，SQLite 保存日志原文、存证记录、审计记录和告警记录，使系统能够查询和展示完整业务数据。在链上部分，LogRegistry 保存日志哈希和任务标识，为审计提供独立校验依据。审计阶段，系统通过 expectedHash、actualHash 和 onChainHash 的三方比对判断日志是否一致。与此同时，历史合约地址回溯和合约代码存在性校验进一步增强了链上读取过程的可靠性，避免因合约地址变化或空地址导致误判。

因此，数据可信性需求不仅体现在区块链不可篡改特性上，也体现在链上链下字段映射、哈希生成规则、审计状态判定和异常告警记录等多个环节的协同设计中。

本节关键信息摘要：

1. 数据可信性要求日志采集、存储、存证和审计过程可追溯。
2. 系统通过链下原文存储和链上哈希存证提高完整性校验可信度。
3. 三方哈希比对是数据可信性验证的核心机制。
4. 历史合约地址回溯和合约代码存在性校验增强链上证据可靠性。

### 4.3.2 系统可用性需求

系统可用性要求用户能够稳定地完成日志提交、审计执行、告警查看和结果展示等操作。对于本系统而言，可用性不仅体现在前端页面能否访问，还体现在日志采集、后端接口、数据库读写和链上交互能否形成稳定闭环。若任一环节不可用，系统就难以完成可信日志审计目标。

在日志采集侧，Agent 需要支持增量读取、失败重试和状态同步，以降低临时异常对日志提交的影响。在后端服务侧，系统需要提供日志提交、审计执行、告警查询和总览统计等接口，使前端能够稳定获取数据。在数据存储侧，SQLite 作为原型系统数据库，需要支持日志、哈希记录、审计记录和告警记录的持久化。在区块链交互侧，系统需要能够识别合约地址不可用等异常情况，避免将失败操作误判为成功。

此外，系统可用性还体现在验证和演示过程的可重复性上。项目提供脚本化验证入口和性能实验脚本，能够对合约、后端、Agent 和前端构建进行验证。这些脚本有助于在论文实验和答辩演示前确认系统主要功能处于可运行状态。

本节关键信息摘要：

1. 系统可用性要求日志采集、后端接口、数据库和链上交互稳定协同。
2. Agent 的重试和状态同步能力有助于降低采集过程异常影响。
3. 后端接口需要支撑日志、审计、告警和总览等主要业务操作。
4. 脚本化验证提高了系统实验和演示过程的可重复性。

### 4.3.3 可维护性与可扩展性需求

可维护性要求系统结构清晰、模块职责明确，便于后续修改、调试和论文说明。本系统采用模块化 Monorepo 结构，将前端 Web、后端 Server、采集 Agent、智能合约和共享类型库放在同一仓库下统一管理。不同模块在目录和职责上相对独立，能够降低代码耦合度，也便于在论文中说明系统分层设计。

后端服务采用 routes、controllers、services、repositories、db 和 blockchain 等分层结构。路由层负责接口定义，控制器负责请求处理，服务层负责编排业务逻辑，数据访问层负责 SQLite 读写，区块链封装层负责合约调用和哈希服务。这样的结构使日志提交、链上写入、审计执行和告警生成等逻辑能够分别维护，避免所有业务代码集中在单一文件中。

可扩展性方面，当前系统虽然基于 SQLite 和本地 Hardhat 链实现，但整体结构为后续扩展预留了空间。例如，数据库层可以替换为更适合高并发场景的数据库，链上环境可以从本地链扩展到测试网或联盟链，审计执行方式也可以进一步扩展为异步队列或并发批量审计。前端页面和后端接口的分离也便于后续增加用户权限、日志筛选和风险分析等功能。

本节关键信息摘要：

1. Monorepo 结构有助于统一管理前端、后端、Agent、合约和共享类型。
2. 后端分层设计提高了业务逻辑的可维护性。
3. SQLite 和本地 Hardhat 链适合原型验证，但后续可替换和扩展。
4. 系统结构为多角色权限、异步审计和更复杂可视化功能预留了空间。

## 4.4 系统总体架构设计

本系统围绕可信任务日志审计目标，采用分层和模块化的总体架构。系统由 Agent、Server、SQLite、LogRegistry 和 Web 五类核心部分组成，分别对应日志采集、业务处理、链下存储、链上存证和前端展示等职责。各模块通过标准化数据结构和接口进行协作，共同形成从日志产生到审计告警的完整流程。

Agent 位于系统数据流的前端，主要负责从本地日志文件中读取新增日志内容。由于日志文件会随着任务运行不断追加内容，Agent 需要维护读取偏移量，确保每次只采集新增部分。采集到日志后，Agent 会将其封装为包含任务标识、来源路径、日志内容、日志级别和采集时间等字段的标准数据，并通过后端接口提交给 Server。同时，Agent 还负责同步自身状态，使系统能够了解采集端是否处于正常运行状态。

Server 是系统的业务处理中心，负责连接 Agent、SQLite、LogRegistry 和 Web。Server 接收 Agent 提交的日志后，先将日志原文和元数据写入 SQLite，再对日志内容计算 SHA-256 哈希。随后，Server 调用 LogRegistry 智能合约，将日志哈希和任务标识写入链上，并在数据库中保存交易哈希、区块号、合约地址和链上状态等信息。审计阶段，Server 读取日志原文、数据库哈希和链上哈希，执行三方比对，并根据结果写入审计记录和异常告警。

SQLite 是系统的链下数据存储部分，主要保存日志原文、哈希存证记录、审计记录、告警记录和 Agent 状态。相比将全部数据写入链上，SQLite 更适合保存结构化业务数据和日志原文，便于快速查询、前端展示和实验验证。链下数据库并不单独承担可信性证明责任，而是与链上 LogRegistry 合约共同构成完整审计依据。

LogRegistry 是系统的链上存证部分，负责保存日志哈希和任务标识等关键摘要信息。合约通过 LOGGER_ROLE 控制写入权限，避免任意地址写入无效数据。合约中的 LogRecord 记录 taskId、logHash、createdAt 和 submitter，records 数组和 taskIdToRecordIds 映射支持按编号和任务维度查询。审计阶段，Server 根据任务标识和合约地址读取链上哈希记录，用于与链下哈希进行比对。

Web 前端是系统面向用户的展示层。前端通过后端 API 获取日志、审计、告警和总览统计数据，并以页面形式展示系统运行状态。用户可以在总览页查看日志数量、审计状态和告警数量，在日志中心查看日志列表，在审计页面查看审计结果，在告警页面查看异常风险。通过前端展示，系统将底层哈希比对和链上存证结果转化为可理解的审计信息。

图 4-1 系统总体架构图

从数据流向看，系统首先由 Agent 采集日志并提交 Server；Server 将日志写入 SQLite，并计算哈希写入 LogRegistry；审计时，Server 从 SQLite 读取日志原文和数据库哈希，从 LogRegistry 读取链上哈希，完成三方比对；当发现异常时，Server 将审计失败记录和告警写入数据库；Web 前端再通过 API 查询并展示相关结果。该架构使每个模块职责清晰，数据流向明确，同时也使链上链下协同审计机制能够落地到具体工程实现中。

总体来看，系统总体架构既满足毕业设计原型系统的可实现性，又能够突出区块链在日志可信审计中的作用。Agent 保证日志自动进入系统，Server 负责业务编排，SQLite 提供链下持久化能力，LogRegistry 提供可信存证依据，Web 提供可视化交互入口。各模块围绕日志哈希和任务标识建立连接，为后续功能模块设计、数据流设计和数据库设计奠定基础。

本节关键信息摘要：

1. 系统由 Agent、Server、SQLite、LogRegistry 和 Web 五类核心部分组成。
2. Agent 负责日志增量采集，Server 负责业务处理、哈希计算、上链和审计。
3. SQLite 保存链下业务数据，LogRegistry 保存链上哈希存证记录。
4. Web 前端展示日志、审计、告警和系统总览信息。
5. 总体架构围绕任务标识和日志哈希连接各模块，支撑链上链下协同审计。
