# 第 3 章 基于区块链的可信日志存证与审计机制设计

## 3.1.1 链下日志存储与链上哈希存证模型

日志数据是信息系统运行过程中形成的重要证据材料，通常用于安全审计、故障排查、责任追溯和运行状态分析。在传统日志管理方式中，日志原文通常直接保存在服务器文件系统、关系型数据库或集中式日志平台中。这种中心化存储方式具有实现简单、查询方便、维护成本较低等优点，但在可信审计场景下也存在明显不足。一旦具备较高权限的内部人员、系统管理员或攻击者能够访问日志存储位置，就可能对日志内容进行修改、删除或伪造。由于日志数据和审计依据都依赖同一中心化存储环境，系统在事后很难证明日志是否保持原始状态，审计结果也缺少独立可信的证据支撑。

针对上述问题，本系统采用“链下保存日志原文、链上保存日志哈希摘要”的混合存储模型。该模型并不将完整日志内容直接写入区块链，而是在日志进入系统后，由后端服务对日志原文计算 SHA-256 哈希值，再将哈希摘要以及任务标识等必要元数据写入 LogRegistry 智能合约。日志原文仍保存在 SQLite 数据库中，用于后续查询、展示和审计重算。区块链负责保存日志摘要形式的存证记录，作为链下日志完整性的可信校验依据。其基本结构如图 3-1 所示。

图 3-1 链上链下混合存储模型

该设计首先能够降低链上存储成本。日志原文通常具有数量多、长度不固定、内容变化频繁等特点，如果将完整日志直接写入区块链，不仅会增加链上存储开销，也会降低系统处理效率。相比之下，哈希摘要长度固定，能够以较小的数据规模代表日志原文的完整性特征，更适合作为链上存证对象。其次，该设计能够降低敏感信息暴露风险。任务日志中可能包含路径、状态、错误信息或业务上下文，若直接上链，数据一旦公开将难以删除或修改。采用链下保存原文、链上保存摘要的方式，可以在保留可验证性的同时减少隐私泄露风险。

从审计可信性角度看，链上哈希存证为链下日志提供了独立校验依据。日志首次提交时，系统将原始日志计算得到的哈希写入链上；后续审计时，系统重新读取链下日志原文并再次计算哈希。如果链下日志未被篡改，则重算哈希应与数据库中保存的哈希以及链上存证哈希保持一致。若日志原文被修改，即使修改幅度较小，重新计算得到的哈希值也会发生变化，从而在比对过程中暴露异常。因此，该模型能够在不改变日志链下存储和查询方式的基础上，为日志完整性提供可追溯、可验证的证明。

此外，链上链下混合存储模型兼顾了系统效率和工程实现复杂度。SQLite 用于保存日志原文、审计记录、告警记录和 Agent 状态，便于系统进行快速查询和页面展示；LogRegistry 合约用于保存关键哈希存证，保证核心审计依据不完全依赖链下数据库。二者通过 taskId、log_id、log_hash 和 contract_address 等字段建立关联，使系统能够在日志采集、存储、存证和审计之间形成稳定的数据映射关系。由此可见，该模型既保留了传统数据库在数据管理方面的便利性，又利用区块链增强了日志审计结果的可信度，是本系统可信日志审计机制的基础。

本节关键信息摘要：

1. 传统中心化日志存储存在被篡改、删除或伪造后难以自证的问题。
2. 本系统采用链下保存日志原文、链上保存日志哈希摘要的混合存储模型。
3. 链上只保存哈希和必要元数据，可降低存储成本并减少敏感日志暴露风险。
4. 审计时通过重新计算链下日志哈希并与链上存证比对，判断日志完整性。
5. SQLite 提供查询和展示能力，LogRegistry 提供可信存证依据，二者共同支撑审计闭环。

## 3.1.2 日志采集、存证、审计、告警闭环流程

可信日志审计不仅需要解决日志数据如何存储的问题，还需要形成从日志产生到异常反馈的完整业务闭环。本系统围绕任务日志可信性验证目标，将日志采集、链下存储、链上存证、审计核验、异常告警和前端展示整合为一条连续流程，使日志在进入系统后能够被持续追踪，并在后续审计阶段具备可验证依据。

系统流程从日志文件开始。应用系统或任务执行过程产生新的日志内容后，Agent 日志采集模块负责读取本地日志文件中的新增部分。为避免重复采集，Agent 通过偏移量记录方式维护上次读取位置，仅采集追加产生的新日志内容。采集到的日志会被封装为标准数据结构，其中包含任务标识、日志来源、日志级别、采集时间和日志原文等信息。随后，Agent 将封装后的日志提交给 Server 后端服务。

Server 接收到日志后，首先将日志原文及其元数据写入 SQLite 数据库中的 logs 表，以便后续查询、展示和审计重算。完成链下入库后，Server 对日志原文执行 SHA-256 哈希计算，生成能够代表日志内容完整性的哈希摘要。该哈希摘要随后被传入 LogRegistry 智能合约的 storeLog 方法，与任务标识一同写入链上。链上写入完成后，系统会在 log_hash_records 表中保存对应的链上存证信息，包括日志哈希、合约地址、交易哈希、区块号以及链上状态。至此，系统完成了从日志采集到链上存证的前半段流程。

在审计阶段，用户或系统脚本可以触发单条日志审计或批量审计任务。Server 根据待审计日志的 log_id 读取 logs 表中的日志原文，并重新计算 actualHash。同时，系统从 log_hash_records 表中读取该日志提交时保存的 expectedHash 以及对应的 contract_address，再根据任务标识从 LogRegistry 合约中查询链上记录，获得 onChainHash。随后，系统对 actualHash、expectedHash 和 onChainHash 进行比对。当三者一致时，说明链下日志内容与原始存证记录保持一致，系统生成 passed 状态的审计记录；当重新计算的哈希与数据库或链上记录不一致时，说明日志可能被篡改，系统生成 failed 状态的审计记录。

当审计结果为 failed 时，系统进一步触发异常告警流程。告警记录写入 alerts 表，告警类型为 hash_mismatch，并与对应日志记录和审计记录建立关联。告警信息包括告警标题、描述、严重程度和处理状态，用于提示用户该日志存在完整性风险。前端 Web 模块通过后端接口获取日志列表、审计结果和告警信息，并在总览页、日志中心、审计管理和告警管理页面进行展示。这样，用户不仅能够查看日志是否已经完成存证，还能够观察审计通过、失败或待定等状态，并及时发现潜在篡改风险。

图 3-2 可信日志审计闭环流程

从整体上看，本系统形成了“采集—存储—存证—审计—告警—展示”的可信审计闭环。Agent 解决日志自动进入系统的问题，Server 负责链下持久化、哈希计算和业务编排，LogRegistry 提供链上可信存证能力，审计模块负责完整性核验，告警模块负责异常反馈，Web 前端负责结果呈现。各模块围绕日志哈希这一核心证据建立关联，使日志在采集后能够被追溯，在被修改后能够被识别，在发现异常后能够被提示。该闭环流程是后续日志哈希模型、智能合约设计和链上链下协同审计机制展开的基础。

本节关键信息摘要：

1. 系统形成了“采集—存储—存证—审计—告警—展示”的完整闭环。
2. Agent 负责增量采集日志，Server 负责入库、哈希计算和链上写入。
3. LogRegistry 保存日志哈希和任务标识，log_hash_records 保存链上交易与合约地址等信息。
4. 审计阶段通过 actualHash、expectedHash 和 onChainHash 的比对判断日志是否可信。
5. 审计失败时系统生成 hash_mismatch 告警，并通过前端展示异常结果。

## 3.2.1 日志标准化封装与任务标识设计

日志原文通常来源于不同应用、不同任务或不同运行环境，其格式、级别、时间和路径信息可能存在差异。如果系统直接对原始文本进行存储和审计，后续在查询、归类、上链和比对时会缺少统一的数据依据。因此，在日志进入可信审计流程之前，需要对日志进行标准化封装，使其具备稳定的数据结构和明确的业务归属关系。本系统在 Agent 采集和 Server 接收阶段，将日志内容封装为包含任务标识、来源信息、日志内容、日志级别和采集时间等字段的标准数据对象。

在本系统中，日志标准化封装主要包括 taskId、sourceType、sourcePath、logContent、logLevel 和 collectedAt 等字段。其中，taskId 用于表示日志所属的业务任务或审计对象，是连接链下日志、数据库记录和链上存证记录的关键字段。sourceType 用于描述日志来源类型，例如日志来自 Agent 采集或其他提交入口。sourcePath 用于记录日志文件路径或来源位置，便于后续定位日志产生环境。logContent 保存日志原文，是进行哈希计算和审计重算的基础。logLevel 用于表示日志级别，例如 INFO、WARN 或 ERROR，便于前端展示和筛选。collectedAt 用于记录日志采集时间，帮助系统分析日志产生和进入审计系统的时间关系。

表 3-1 日志标准化封装字段说明

上述字段中，taskId 是最核心的业务关联字段。在链下数据库中，logs 表通过 task_id 保存任务标识，log_hash_records 表也保存相同的 task_id，从而将日志原文记录与哈希存证记录对应起来。在链上合约中，LogRegistry 同样以 taskId 作为日志记录的重要字段，并通过任务标识建立从任务到链上记录编号的映射关系。这样，系统在审计阶段可以根据同一 taskId 查询某个任务下的全部链上存证记录，并进一步判断待审计日志是否存在对应的链上哈希。

任务标识还能够支持日志归集和审计回溯。在实际任务执行过程中，同一任务可能产生多条日志。如果每条日志缺少统一的任务标识，系统只能以单条日志为单位进行孤立处理，不利于任务维度的追踪和统计。通过 taskId，系统可以将同一任务下的日志、哈希记录、审计记录和告警信息关联起来，使前端能够按任务查看日志状态，也使后端能够在审计时定位对应的链上记录。对于多次部署或历史合约地址回溯场景，taskId 与 contract_address 等字段共同构成审计定位依据，有助于提高审计过程的准确性。

因此，日志标准化封装并不是简单的数据整理步骤，而是可信审计链路能够稳定运行的前提。通过统一字段结构，系统可以在日志采集、数据库存储、链上存证、审计比对和前端展示之间保持一致的数据语义，减少因日志格式差异导致的处理复杂度，为后续哈希生成和链上链下字段映射提供基础。

本节关键信息摘要：

1. 日志进入系统前需要进行标准化封装，以统一采集、存储、上链和审计过程中的数据结构。
2. 标准字段包括 taskId、sourceType、sourcePath、logContent、logLevel 和 collectedAt。
3. taskId 是连接链下日志、数据库存证记录和链上合约记录的关键业务标识。
4. 任务标识支持同一任务日志归集、链上查询和历史审计回溯。
5. 标准化封装为后续哈希计算和字段映射提供稳定基础。

## 3.2.2 SHA-256 日志摘要生成方法

日志完整性校验的核心在于判断日志内容在存储和审计过程中是否发生变化。哈希函数能够将任意长度的数据映射为固定长度的摘要值，当输入内容发生变化时，输出摘要也会随之改变。因此，哈希摘要常用于文件完整性校验、数据存证和审计比对等场景。本系统采用 SHA-256 算法对日志原文进行摘要计算，将日志内容转换为固定长度的十六进制哈希值，并以该哈希值作为链上存证和后续审计比对的核心依据。

在日志提交阶段，Server 接收到 Agent 上报的日志数据后，会读取其中的 logContent 或数据库字段 log_content，并以 UTF-8 编码方式输入 SHA-256 哈希函数。计算结果被转换为十六进制字符串，并添加 0x 前缀，以便与以太坊生态中常见的 bytes32 类型和十六进制表示方式保持一致。该哈希值随后被保存到 log_hash_records 表中，同时作为参数传入 LogRegistry.storeLog(taskId, logHash) 方法写入链上。由于链上仅保存哈希摘要而不保存日志原文，系统能够在减少链上数据量的同时保留日志完整性校验能力。

在审计阶段，系统再次读取 logs 表中的日志原文，并使用相同的 SHA-256 计算方式生成 actualHash。若日志内容自提交后未发生改变，则审计阶段重新计算得到的 actualHash 应与提交阶段保存的 expectedHash 一致，也应与链上查询得到的 onChainHash 保持一致。若链下日志原文被人为修改，即使只改变一个字符，重新计算得到的哈希值也会与原始哈希产生明显差异，从而在三方比对过程中被识别出来。

需要注意的是，哈希摘要本身并不负责保存日志语义，也不能直接说明日志内容是否真实发生过某个业务事件。它的作用是为某一时刻的日志内容生成唯一性较强的完整性标识。换言之，系统通过哈希值证明“当前链下日志是否与当时存证的日志内容一致”，而不是通过哈希值直接判断业务行为是否合法。因此，在本系统中，SHA-256 日志摘要主要承担完整性校验和链上存证索引作用，与 taskId、contract_address、audit_records 等字段共同支撑可信审计流程。

采用 SHA-256 进行日志摘要生成还能够提高系统实现的一致性。日志提交和审计重算都使用同一计算规则，避免了不同模块采用不同摘要格式导致的比对误差。只要日志原文编码、哈希算法和输出格式保持一致，系统就能够稳定地在数据库、链上合约和审计逻辑之间传递哈希值，为后续三方哈希比对提供可靠基础。

本节关键信息摘要：

1. SHA-256 用于将日志原文转换为固定长度哈希摘要，支撑完整性校验。
2. 系统在日志提交阶段对 logContent 或 log_content 计算 0x 开头的十六进制哈希值。
3. 审计阶段使用相同规则重新计算 actualHash，并与 expectedHash、onChainHash 比对。
4. 哈希摘要用于判断日志内容是否变化，不直接判断业务事件是否合法。
5. 统一的哈希生成规则是后续三方哈希比对的基础。

## 3.2.3 链上存证字段与链下记录映射关系

链上存证机制要发挥作用，必须与链下数据库记录建立明确的映射关系。若链上哈希记录无法准确对应到链下日志原文，审计阶段就难以判断某一条日志是否存在有效存证。因此，本系统在数据库表设计和智能合约设计中同时保留任务标识、日志哈希和合约地址等关键字段，用于建立 logs、log_hash_records 与 LogRegistry 链上记录之间的对应关系。

在链下数据库中，logs 表负责保存日志原文及其来源信息，是审计重算 actualHash 的数据来源。该表中的 id 字段是链下日志记录的唯一编号，task_id 表示日志所属任务，log_content 保存日志原文，source_type、source_path、log_level 和 collected_at 则用于描述日志来源、级别和采集时间。logs 表本身不直接保存链上交易信息，而是通过 id 与 log_hash_records 表中的 log_id 建立关联。

log_hash_records 表负责保存日志哈希及链上写入信息，是连接链下日志和链上存证的中间表。其中，log_id 对应 logs 表中的日志主键，说明该条哈希记录属于哪一条日志；task_id 与 logs 表中的 task_id 保持一致，用于任务维度查询；log_hash 保存提交阶段计算得到的日志哈希，也就是审计阶段的 expectedHash；contract_address 保存该哈希实际写入的 LogRegistry 合约地址；transaction_hash 记录链上写入交易；block_number 记录交易所在区块；on_chain_status 表示链上写入状态。通过这些字段，系统不仅能够知道某条日志的原始哈希，还能够追踪该哈希写入了哪个合约、对应哪笔交易以及写入是否成功。

在链上合约中，LogRegistry 的 LogRecord 结构体保存 taskId、logHash、createdAt 和 submitter。taskId 与链下 task_id 对应，用于按任务查询链上日志记录；logHash 与 log_hash_records.log_hash 对应，是日志完整性校验的核心值；createdAt 记录链上写入时的区块时间戳，可作为存证时间参考；submitter 记录执行写入操作的钱包地址，用于确认链上记录的提交来源。合约还通过 taskIdToRecordIds 映射维护任务标识与链上记录编号之间的关系，使后端在审计时能够根据 taskId 查询同一任务下的链上哈希记录。

表 3-1 链上链下字段映射关系

这种字段映射关系使审计流程具备可追溯性。审计某条日志时，系统先根据 log_id 找到 logs 表中的日志原文，再根据 log_id 查询最新的 log_hash_records 记录，获得 expectedHash 和 contract_address。随后，系统使用 contract_address 连接对应的 LogRegistry 合约，并根据 task_id 查询链上记录，判断链上是否存在与 expectedHash 匹配的 logHash。若链下重算得到的 actualHash 与 expectedHash 和链上 logHash 均一致，则说明该日志在链下保存期间未发生内容变化。

此外，contract_address 字段在历史审计场景中具有重要意义。本地链或测试环境中可能存在多次部署合约的情况，如果审计时只读取当前环境变量中的合约地址，可能无法正确查询旧日志对应的链上记录。通过在 log_hash_records 表中保存实际写入时的合约地址，系统可以在审计阶段回溯到对应历史合约，提高审计结果的准确性。因此，链上存证字段与链下记录映射不仅是数据关联设计，也是保证可信审计结果可复现的重要基础。

本节关键信息摘要：

1. logs 表保存日志原文，是审计阶段重新计算 actualHash 的来源。
2. log_hash_records 表保存 log_hash、contract_address、transaction_hash、block_number 和 on_chain_status 等链上写入信息。
3. LogRegistry 链上记录保存 taskId、logHash、createdAt 和 submitter。
4. log_id、task_id、log_hash 和 contract_address 共同建立链下日志与链上存证的映射关系。
5. contract_address 支持历史合约地址回溯，是提高审计准确性的重要字段。
