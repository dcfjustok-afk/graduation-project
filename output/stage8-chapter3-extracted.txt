3.1.1 链下日志存储与链上哈希存证模型
日志数据是信息系统运行过程中形成的重要证据材料，通常用于安全审计、故障排查、责任追溯和运行状态分析。在传统日志管理方式中，日志原文通常直接保存在服务器文件系统、关系型数据库或集中式日志平台中。这种中心化存储方式具有实现简单、查询方便、维护成本较低等优点，但在可信审计场景下也存在明显不足。一旦具备较高权限的内部人员、系统管理员或攻击者能够访问日志存储位置，就可能对日志内容进行修改、删除或伪造。由于日志数据和审计依据都依赖同一中心化存储环境，系统在事后很难证明日志是否保持原始状态，审计结果也缺少独立可信的证据支撑。
针对上述问题，本系统采用“链下保存日志原文、链上保存日志哈希摘要”的混合存储模型。该模型并不将完整日志内容直接写入区块链，而是在日志进入系统后，由后端服务对日志原文计算 SHA-256 哈希值，再将哈希摘要以及任务标识等必要元数据写入 LogRegistry 智能合约。日志原文仍保存在 SQLite 数据库中，用于后续查询、展示和审计重算。区块链负责保存日志摘要形式的存证记录，作为链下日志完整性的可信校验依据。其基本结构如图 3-1 所示。
图 3-1 链上链下混合存储模型
该设计首先能够降低链上存储成本。日志原文通常具有数量多、长度不固定、内容变化频繁等特点，如果将完整日志直接写入区块链，不仅会增加链上存储开销，也会降低系统处理效率。相比之下，哈希摘要长度固定，能够以较小的数据规模代表日志原文的完整性特征，更适合作为链上存证对象。其次，该设计能够降低敏感信息暴露风险。任务日志中可能包含路径、状态、错误信息或业务上下文，若直接上链，数据一旦公开将难以删除或修改。采用链下保存原文、链上保存摘要的方式，可以在保留可验证性的同时减少隐私泄露风险。
从审计可信性角度看，链上哈希存证为链下日志提供了独立校验依据。日志首次提交时，系统将原始日志计算得到的哈希写入链上；后续审计时，系统重新读取链下日志原文并再次计算哈希。如果链下日志未被篡改，则重算哈希应与数据库中保存的哈希以及链上存证哈希保持一致。若日志原文被修改，即使修改幅度较小，重新计算得到的哈希值也会发生变化，从而在比对过程中暴露异常。因此，该模型能够在不改变日志链下存储和查询方式的基础上，为日志完整性提供可追溯、可验证的证明。
此外，链上链下混合存储模型兼顾了系统效率和工程实现复杂度。SQLite 用于保存日志原文、审计记录、告警记录和 Agent 状态，便于系统进行快速查询和页面展示；LogRegistry 合约用于保存关键哈希存证，保证核心审计依据不完全依赖链下数据库。二者通过 taskId、log_id、log_hash 和 contract_address 等字段建立关联，使系统能够在日志采集、存储、存证和审计之间形成稳定的数据映射关系。由此可见，该模型既保留了传统数据库在数据管理方面的便利性，又利用区块链增强了日志审计结果的可信度，是本系统可信日志审计机制的基础。
本节关键信息摘要：
1. 传统中心化日志存储存在被篡改、删除或伪造后难以自证的问题。
2. 本系统采用链下保存日志原文、链上保存日志哈希摘要的混合存储模型。
3. 链上只保存哈希和必要元数据，可降低存储成本并减少敏感日志暴露风险。
4. 审计时通过重新计算链下日志哈希并与链上存证比对，判断日志完整性。
5. SQLite 提供查询和展示能力，LogRegistry 提供可信存证依据，二者共同支撑审计闭环。
3.1.2 日志采集、存证、审计、告警闭环流程
可信日志审计不仅需要解决日志数据如何存储的问题，还需要形成从日志产生到异常反馈的完整业务闭环。本系统围绕任务日志可信性验证目标，将日志采集、链下存储、链上存证、审计核验、异常告警和前端展示整合为一条连续流程，使日志在进入系统后能够被持续追踪，并在后续审计阶段具备可验证依据。
系统流程从日志文件开始。应用系统或任务执行过程产生新的日志内容后，Agent 日志采集模块负责读取本地日志文件中的新增部分。为避免重复采集，Agent 通过偏移量记录方式维护上次读取位置，仅采集追加产生的新日志内容。采集到的日志会被封装为标准数据结构，其中包含任务标识、日志来源、日志级别、采集时间和日志原文等信息。随后，Agent 将封装后的日志提交给 Server 后端服务。
Server 接收到日志后，首先将日志原文及其元数据写入 SQLite 数据库中的 logs 表，以便后续查询、展示和审计重算。完成链下入库后，Server 对日志原文执行 SHA-256 哈希计算，生成能够代表日志内容完整性的哈希摘要。该哈希摘要随后被传入 LogRegistry 智能合约的 storeLog 方法，与任务标识一同写入链上。链上写入完成后，系统会在 log_hash_records 表中保存对应的链上存证信息，包括日志哈希、合约地址、交易哈希、区块号以及链上状态。至此，系统完成了从日志采集到链上存证的前半段流程。
在审计阶段，用户或系统脚本可以触发单条日志审计或批量审计任务。Server 根据待审计日志的 log_id 读取 logs 表中的日志原文，并重新计算 actualHash。同时，系统从 log_hash_records 表中读取该日志提交时保存的 expectedHash 以及对应的 contract_address，再根据任务标识从 LogRegistry 合约中查询链上记录，获得 onChainHash。随后，系统对 actualHash、expectedHash 和 onChainHash 进行比对。当三者一致时，说明链下日志内容与原始存证记录保持一致，系统生成 passed 状态的审计记录；当重新计算的哈希与数据库或链上记录不一致时，说明日志可能被篡改，系统生成 failed 状态的审计记录。
当审计结果为 failed 时，系统进一步触发异常告警流程。告警记录写入 alerts 表，告警类型为 hash_mismatch，并与对应日志记录和审计记录建立关联。告警信息包括告警标题、描述、严重程度和处理状态，用于提示用户该日志存在完整性风险。前端 Web 模块通过后端接口获取日志列表、审计结果和告警信息，并在总览页、日志中心、审计管理和告警管理页面进行展示。这样，用户不仅能够查看日志是否已经完成存证，还能够观察审计通过、失败或待定等状态，并及时发现潜在篡改风险。
图 3-2 可信日志审计闭环流程
从整体上看，本系统形成了“采集—存储—存证—审计—告警—展示”的可信审计闭环。Agent 解决日志自动进入系统的问题，Server 负责链下持久化、哈希计算和业务编排，LogRegistry 提供链上可信存证能力，审计模块负责完整性核验，告警模块负责异常反馈，Web 前端负责结果呈现。各模块围绕日志哈希这一核心证据建立关联，使日志在采集后能够被追溯，在被修改后能够被识别，在发现异常后能够被提示。该闭环流程是后续日志哈希模型、智能合约设计和链上链下协同审计机制展开的基础。
本节关键信息摘要：
1. 系统形成了“采集—存储—存证—审计—告警—展示”的完整闭环。
2. Agent 负责增量采集日志，Server 负责入库、哈希计算和链上写入。
3. LogRegistry 保存日志哈希和任务标识，log_hash_records 保存链上交易与合约地址等信息。
4. 审计阶段通过 actualHash、expectedHash 和 onChainHash 的比对判断日志是否可信。
5. 审计失败时系统生成 hash_mismatch 告警，并通过前端展示异常结果。
3.2.1 日志标准化封装与任务标识设计
日志原文通常来源于不同应用、不同任务或不同运行环境，其格式、级别、时间和路径信息可能存在差异。如果系统直接对原始文本进行存储和审计，后续在查询、归类、上链和比对时会缺少统一的数据依据。因此，在日志进入可信审计流程之前，需要对日志进行标准化封装，使其具备稳定的数据结构和明确的业务归属关系。本系统在 Agent 采集和 Server 接收阶段，将日志内容封装为包含任务标识、来源信息、日志内容、日志级别和采集时间等字段的标准数据对象。
在本系统中，日志标准化封装主要包括 taskId、sourceType、sourcePath、logContent、logLevel 和 collectedAt 等字段。其中，taskId 用于表示日志所属的业务任务或审计对象，是连接链下日志、数据库记录和链上存证记录的关键字段。sourceType 用于描述日志来源类型，例如日志来自 Agent 采集或其他提交入口。sourcePath 用于记录日志文件路径或来源位置，便于后续定位日志产生环境。logContent 保存日志原文，是进行哈希计算和审计重算的基础。logLevel 用于表示日志级别，例如 INFO、WARN 或 ERROR，便于前端展示和筛选。collectedAt 用于记录日志采集时间，帮助系统分析日志产生和进入审计系统的时间关系。

上述字段中，taskId 是最核心的业务关联字段。在链下数据库中，logs 表通过 task_id 保存任务标识，log_hash_records 表也保存相同的 task_id，从而将日志原文记录与哈希存证记录对应起来。在链上合约中，LogRegistry 同样以 taskId 作为日志记录的重要字段，并通过任务标识建立从任务到链上记录编号的映射关系。这样，系统在审计阶段可以根据同一 taskId 查询某个任务下的全部链上存证记录，并进一步判断待审计日志是否存在对应的链上哈希。
任务标识还能够支持日志归集和审计回溯。在实际任务执行过程中，同一任务可能产生多条日志。如果每条日志缺少统一的任务标识，系统只能以单条日志为单位进行孤立处理，不利于任务维度的追踪和统计。通过 taskId，系统可以将同一任务下的日志、哈希记录、审计记录和告警信息关联起来，使前端能够按任务查看日志状态，也使后端能够在审计时定位对应的链上记录。对于多次部署或历史合约地址回溯场景，taskId 与 contract_address 等字段共同构成审计定位依据，有助于提高审计过程的准确性。
因此，日志标准化封装并不是简单的数据整理步骤，而是可信审计链路能够稳定运行的前提。通过统一字段结构，系统可以在日志采集、数据库存储、链上存证、审计比对和前端展示之间保持一致的数据语义，减少因日志格式差异导致的处理复杂度，为后续哈希生成和链上链下字段映射提供基础。
本节关键信息摘要：
1. 日志进入系统前需要进行标准化封装，以统一采集、存储、上链和审计过程中的数据结构。
2. 标准字段包括 taskId、sourceType、sourcePath、logContent、logLevel 和 collectedAt。
3. taskId 是连接链下日志、数据库存证记录和链上合约记录的关键业务标识。
4. 任务标识支持同一任务日志归集、链上查询和历史审计回溯。
5. 标准化封装为后续哈希计算和字段映射提供稳定基础。
3.2.2 SHA-256 日志摘要生成方法
日志完整性校验的核心在于判断日志内容在存储和审计过程中是否发生变化。哈希函数能够将任意长度的数据映射为固定长度的摘要值，当输入内容发生变化时，输出摘要也会随之改变。因此，哈希摘要常用于文件完整性校验、数据存证和审计比对等场景。本系统采用 SHA-256 算法对日志原文进行摘要计算，将日志内容转换为固定长度的十六进制哈希值，并以该哈希值作为链上存证和后续审计比对的核心依据。
在日志提交阶段，Server 接收到 Agent 上报的日志数据后，会读取其中的 logContent 或数据库字段 log_content，并以 UTF-8 编码方式输入 SHA-256 哈希函数。计算结果被转换为十六进制字符串，并添加 0x 前缀，以便与以太坊生态中常见的 bytes32 类型和十六进制表示方式保持一致。该哈希值随后被保存到 log_hash_records 表中，同时作为参数传入 LogRegistry.storeLog(taskId, logHash) 方法写入链上。由于链上仅保存哈希摘要而不保存日志原文，系统能够在减少链上数据量的同时保留日志完整性校验能力。
在审计阶段，系统再次读取 logs 表中的日志原文，并使用相同的 SHA-256 计算方式生成 actualHash。若日志内容自提交后未发生改变，则审计阶段重新计算得到的 actualHash 应与提交阶段保存的 expectedHash 一致，也应与链上查询得到的 onChainHash 保持一致。若链下日志原文被人为修改，即使只改变一个字符，重新计算得到的哈希值也会与原始哈希产生明显差异，从而在三方比对过程中被识别出来。
需要注意的是，哈希摘要本身并不负责保存日志语义，也不能直接说明日志内容是否真实发生过某个业务事件。它的作用是为某一时刻的日志内容生成唯一性较强的完整性标识。换言之，系统通过哈希值证明“当前链下日志是否与当时存证的日志内容一致”，而不是通过哈希值直接判断业务行为是否合法。因此，在本系统中，SHA-256 日志摘要主要承担完整性校验和链上存证索引作用，与 taskId、contract_address、audit_records 等字段共同支撑可信审计流程。
采用 SHA-256 进行日志摘要生成还能够提高系统实现的一致性。日志提交和审计重算都使用同一计算规则，避免了不同模块采用不同摘要格式导致的比对误差。只要日志原文编码、哈希算法和输出格式保持一致，系统就能够稳定地在数据库、链上合约和审计逻辑之间传递哈希值，为后续三方哈希比对提供可靠基础。
本节关键信息摘要：
1. SHA-256 用于将日志原文转换为固定长度哈希摘要，支撑完整性校验。
2. 系统在日志提交阶段对 logContent 或 log_content 计算 0x 开头的十六进制哈希值。
3. 审计阶段使用相同规则重新计算 actualHash，并与 expectedHash、onChainHash 比对。
4. 哈希摘要用于判断日志内容是否变化，不直接判断业务事件是否合法。
5. 统一的哈希生成规则是后续三方哈希比对的基础。
3.2.3 链上存证字段与链下记录映射关系
链上存证机制要发挥作用，必须与链下数据库记录建立明确的映射关系。若链上哈希记录无法准确对应到链下日志原文，审计阶段就难以判断某一条日志是否存在有效存证。因此，本系统在数据库表设计和智能合约设计中同时保留任务标识、日志哈希和合约地址等关键字段，用于建立 logs、log_hash_records 与 LogRegistry 链上记录之间的对应关系。
在链下数据库中，logs 表负责保存日志原文及其来源信息，是审计重算 actualHash 的数据来源。该表中的 id 字段是链下日志记录的唯一编号，task_id 表示日志所属任务，log_content 保存日志原文，source_type、source_path、log_level 和 collected_at 则用于描述日志来源、级别和采集时间。logs 表本身不直接保存链上交易信息，而是通过 id 与 log_hash_records 表中的 log_id 建立关联。
log_hash_records 表负责保存日志哈希及链上写入信息，是连接链下日志和链上存证的中间表。其中，log_id 对应 logs 表中的日志主键，说明该条哈希记录属于哪一条日志；task_id 与 logs 表中的 task_id 保持一致，用于任务维度查询；log_hash 保存提交阶段计算得到的日志哈希，也就是审计阶段的 expectedHash；contract_address 保存该哈希实际写入的 LogRegistry 合约地址；transaction_hash 记录链上写入交易；block_number 记录交易所在区块；on_chain_status 表示链上写入状态。通过这些字段，系统不仅能够知道某条日志的原始哈希，还能够追踪该哈希写入了哪个合约、对应哪笔交易以及写入是否成功。
在链上合约中，LogRegistry 的 LogRecord 结构体保存 taskId、logHash、createdAt 和 submitter。taskId 与链下 task_id 对应，用于按任务查询链上日志记录；logHash 与 log_hash_records.log_hash 对应，是日志完整性校验的核心值；createdAt 记录链上写入时的区块时间戳，可作为存证时间参考；submitter 记录执行写入操作的钱包地址，用于确认链上记录的提交来源。合约还通过 taskIdToRecordIds 映射维护任务标识与链上记录编号之间的关系，使后端在审计时能够根据 taskId 查询同一任务下的链上哈希记录。

这种字段映射关系使审计流程具备可追溯性。审计某条日志时，系统先根据 log_id 找到 logs 表中的日志原文，再根据 log_id 查询最新的 log_hash_records 记录，获得 expectedHash 和 contract_address。随后，系统使用 contract_address 连接对应的 LogRegistry 合约，并根据 task_id 查询链上记录，判断链上是否存在与 expectedHash 匹配的 logHash。若链下重算得到的 actualHash 与 expectedHash 和链上 logHash 均一致，则说明该日志在链下保存期间未发生内容变化。
此外，contract_address 字段在历史审计场景中具有重要意义。本地链或测试环境中可能存在多次部署合约的情况，如果审计时只读取当前环境变量中的合约地址，可能无法正确查询旧日志对应的链上记录。通过在 log_hash_records 表中保存实际写入时的合约地址，系统可以在审计阶段回溯到对应历史合约，提高审计结果的准确性。因此，链上存证字段与链下记录映射不仅是数据关联设计，也是保证可信审计结果可复现的重要基础。
本节关键信息摘要：
1. logs 表保存日志原文，是审计阶段重新计算 actualHash 的来源。
2. log_hash_records 表保存 log_hash、contract_address、transaction_hash、block_number 和 on_chain_status 等链上写入信息。
3. LogRegistry 链上记录保存 taskId、logHash、createdAt 和 submitter。
4. log_id、task_id、log_hash 和 contract_address 共同建立链下日志与链上存证的映射关系。
5. contract_address 支持历史合约地址回溯，是提高审计准确性的重要字段。
3.3.1 合约数据结构设计
LogRegistry 智能合约是本系统链上存证机制的核心组成部分，其主要作用是保存日志哈希及相关元数据，为后续审计提供可追溯的链上证据。由于区块链存储成本较高，并且链上数据一旦写入后不宜修改，本系统在合约数据结构设计时遵循“字段必要、结构清晰、便于查询”的原则，只保存与日志可信审计直接相关的信息，不将日志原文写入链上。合约中的核心数据结构为 LogRecord，该结构体用于描述单条日志的链上存证记录。
LogRecord 结构体主要包含 taskId、logHash、createdAt 和 submitter 四个字段。taskId 表示日志所属的业务任务标识，是链上记录与链下日志记录之间建立业务关联的关键字段。在系统运行过程中，同一任务可能对应多条日志记录，因此 taskId 不仅用于说明日志来源于哪个任务，也用于支持后续按任务维度查询链上存证。通过该字段，后端审计服务能够根据某一任务标识读取该任务下的链上日志哈希记录，并与链下数据库中的日志记录进行匹配。
logHash 字段用于保存日志原文经过 SHA-256 计算后得到的哈希摘要，是链上存证记录中最核心的字段。系统不在链上保存 logContent 原文，而是保存 logHash，用较小的数据量代表日志内容的完整性特征。后续审计时，系统会对链下保存的日志原文重新计算哈希，并将重算结果与链上 logHash 进行比对。如果日志内容在链下被修改，则重新计算得到的哈希值会与链上存证记录不一致，从而暴露篡改风险。
createdAt 字段用于记录日志哈希写入链上时的区块时间戳。该字段并不表示日志实际产生时间，而是表示该条存证记录被写入区块链的时间。它可以为后续审计提供时间参考，使系统能够说明某条日志哈希在何时完成链上存证。submitter 字段用于记录执行链上写入操作的钱包地址。在本系统中，日志哈希通常由后端服务账户写入链上，submitter 能够帮助确认该条存证记录的提交来源，并配合权限控制机制说明写入行为是否来自授权角色。
除 LogRecord 结构体外，LogRegistry 合约还通过 records 数组保存全部链上日志存证记录。每当 storeLog 方法成功写入一条日志哈希时，合约都会将新的 LogRecord 追加到 records 数组中，数组下标即可作为该条链上记录的 recordId。通过这种方式，合约能够支持基于记录编号的单条查询，后续可通过 getLog(recordId) 读取指定编号的链上记录。
为了支持任务维度的查询，合约还设计了 taskIdToRecordIds 映射。该映射以 taskId 为键，以 recordId 列表为值，用于记录某一任务下所有链上日志记录的编号。当一条日志哈希写入合约时，系统不仅会将 LogRecord 添加到 records 数组中，还会把对应 recordId 加入 taskIdToRecordIds[taskId]。这样，后端服务在审计某个任务时，可以先通过任务标识获得该任务下所有链上记录编号，再进一步读取对应的日志哈希。该设计避免了遍历全部 records 数组，提高了按任务查询链上存证记录的便利性。
总体而言，LogRegistry 的数据结构设计围绕日志可信审计需求展开。LogRecord 提供单条存证记录的基本信息，records 数组支持全局记录编号查询，taskIdToRecordIds 映射支持任务维度的链上记录定位。三者共同构成了系统链上存证的数据基础，为后续日志哈希写入、任务维度查询和三方哈希比对提供支撑。
本节关键信息摘要：
1. LogRegistry 合约只保存日志哈希和必要元数据，不保存日志原文。
2. LogRecord 包含 taskId、logHash、createdAt 和 submitter 四个核心字段。
3. records 数组用于保存全部链上存证记录，并通过 recordId 支持单条查询。
4. taskIdToRecordIds 映射用于建立任务标识与链上记录编号列表之间的关系。
5. 合约数据结构为后续任务维度查询和三方哈希比对提供链上数据基础。
3.3.2 基于 AccessControl 的写入权限控制
日志存证合约的可信性不仅取决于链上数据难以篡改，还取决于写入链上数据的主体是否可信。如果智能合约允许任意地址调用日志写入方法，攻击者或无关用户就可能向合约中写入伪造的 taskId 和 logHash，造成链上存证记录被污染。即使链上数据本身不可篡改，若写入入口没有权限约束，系统后续审计时也可能面对大量无效或恶意的存证记录，影响审计结果的可靠性。因此，LogRegistry 合约必须对日志哈希写入操作进行访问控制，确保只有被授权的账户能够执行存证写入。
本系统采用 OpenZeppelin 提供的 AccessControl 机制实现合约权限管理。AccessControl 是 Solidity 智能合约开发中常用的角色访问控制组件，能够通过角色标识区分不同权限主体，并提供角色授予、撤销和权限校验能力。相比在合约中自行维护布尔类型权限字段，AccessControl 具有结构清晰、复用性强、接口成熟等优点，适合在毕业设计原型系统中实现可解释、可验证的权限边界。
在 LogRegistry 合约中，LOGGER_ROLE 表示允许写入日志存证记录的角色。storeLog 方法被设计为只有具备 LOGGER_ROLE 的地址才能调用。该角色通常可以授予后端服务使用的钱包账户，由后端在接收日志、计算哈希后统一发起链上写入。这样，日志哈希上链行为由系统后端进行控制，避免任意外部地址直接向合约提交不可信数据。通过 LOGGER_ROLE，系统将链上写入入口限定在可信服务范围内，使链上记录更符合审计业务语义。
DEFAULT_ADMIN_ROLE 则用于管理角色授权。部署合约时，管理员地址获得 DEFAULT_ADMIN_ROLE，并具备授予或撤销 LOGGER_ROLE 的权限。该设计使系统能够区分“权限管理者”和“日志写入者”两类角色：管理员负责角色配置，日志写入账户负责执行实际存证操作。二者职责分离有助于提高合约权限模型的清晰性，也便于在论文中说明系统安全边界。
采用 AccessControl 还能够提高合约行为的可测试性。合约测试可以分别验证授权账户是否能够成功调用 storeLog，未授权账户是否会被拒绝，以及角色授予后权限是否生效。这种测试方式比自定义权限字段更加规范，也更便于与 OpenZeppelin 的成熟实现保持一致。同时，由于 AccessControl 在智能合约生态中应用广泛，其权限语义相对明确，能够降低自定义实现中出现权限绕过或逻辑遗漏的风险。
从系统整体角度看，基于 AccessControl 的权限控制是链上可信存证机制的重要组成部分。日志哈希写入链上后具有较强的不可篡改性，但只有写入来源可信，链上记录才具有审计价值。LOGGER_ROLE 限定了写入主体，DEFAULT_ADMIN_ROLE 管理角色授权，两者共同构成了 LogRegistry 的访问控制边界。通过该机制，系统能够在链上存证环节减少无效写入和恶意写入风险，为后续审计比对提供更可靠的链上数据来源。
本节关键信息摘要：
1. 日志存证合约不能允许任意地址写入，否则链上记录可能被恶意污染。
2. LogRegistry 使用 OpenZeppelin AccessControl 实现角色访问控制。
3. LOGGER_ROLE 用于限制日志哈希写入权限，通常授予后端服务账户。
4. DEFAULT_ADMIN_ROLE 用于管理角色授权，实现权限管理者与写入者职责分离。
5. AccessControl 提高了权限模型的清晰性、可测试性和安全边界可解释性。
3.3.3 日志哈希写入与任务维度查询方法
LogRegistry 合约在数据结构和权限控制的基础上，进一步提供日志哈希写入与任务维度查询方法，用于支撑链上存证和后续审计读取。合约方法设计围绕两个目标展开：一是能够安全地将日志哈希写入链上，形成不可轻易篡改的存证记录；二是能够根据任务标识查询相关链上记录，使后端审计服务能够定位待审计日志对应的链上哈希。
日志哈希写入主要通过 storeLog(taskId, logHash) 方法完成。该方法接收任务标识和日志哈希两个参数，并要求调用者具备 LOGGER_ROLE。写入前，合约需要对参数进行基本校验，确保 taskId 不为空，logHash 不为零值。这样的校验可以避免无效任务标识或空哈希被写入链上，减少无意义存证记录。参数校验通过后，合约以当前 records 数组长度作为新记录的 recordId，并将包含 taskId、logHash、createdAt 和 submitter 的 LogRecord 追加到 records 数组中。同时，合约会将该 recordId 加入 taskIdToRecordIds[taskId]，建立任务标识与链上记录编号之间的映射关系。
在完成写入后，合约触发 LogStored 事件。事件中包含 recordId、taskId、logHash、submitter 和 createdAt 等信息，用于记录链上写入行为。虽然本系统当前主要通过后端接口和数据库记录进行展示，但事件机制仍具有重要意义。它能够为后续扩展链上事件监听、前端链上记录展示或审计追踪提供基础，也使日志存证行为在链上具备更清晰的可观察性。
除写入方法外，LogRegistry 还提供多种查询方法。getLog(recordId) 用于根据记录编号读取单条链上存证记录，适合在已经知道 recordId 的情况下定位具体日志。getRecordIdsByTaskId(taskId) 用于返回某一任务标识下的全部记录编号，使后端能够先获取记录编号列表，再按需查询具体记录。getLogsByTaskId(taskId) 则直接返回某一任务下的完整 LogRecord 列表，便于后端审计服务一次性读取任务相关链上哈希。getTaskLogCount(taskId) 用于统计指定任务下的链上日志数量，getLogCount() 用于统计合约中全部存证记录数量。

在审计阶段，任务维度查询方法具有直接作用。后端服务会根据待审计日志的 task_id 连接对应 LogRegistry 合约，并调用 getLogsByTaskId(taskId) 获取该任务下的链上记录。随后，系统从返回结果中提取 logHash，并判断数据库中保存的 expectedHash 是否能够在链上记录中找到对应项。如果链上记录中存在匹配哈希，则说明该日志提交时确实完成了链上存证；若链上记录缺失或不匹配，则系统需要结合本地重算哈希进一步判断审计状态。
因此，storeLog 方法负责将日志哈希写入链上，查询方法负责在审计阶段提供链上证据读取能力，事件机制则增强链上写入过程的可追踪性。三者共同构成 LogRegistry 合约的核心操作接口，使系统能够围绕任务标识完成日志存证、查询和审计比对。
本节关键信息摘要：
1. storeLog(taskId, logHash) 是日志哈希写入链上的核心方法。
2. storeLog 需要校验 taskId 和 logHash，并要求调用者具备 LOGGER_ROLE。
3. 写入成功后，合约会追加 LogRecord，维护 taskIdToRecordIds 映射，并触发 LogStored 事件。
4. getLogsByTaskId 和 getRecordIdsByTaskId 支持任务维度查询，是审计阶段读取链上哈希的重要接口。
5. 合约写入、查询和事件机制共同支撑链上存证的可追溯性。
3.4.1 数据库哈希、链上哈希与重算哈希三方比对
链上存证的最终目的在于为日志完整性审计提供可信依据。单独保存日志原文或单独保存链上哈希都不足以完成完整审计，系统需要在审计阶段将链下数据库记录、链上存证记录和当前日志内容重新计算结果进行联合比对。本系统将该过程设计为数据库哈希、链上哈希与重算哈希的三方比对机制，通过 expectedHash、actualHash 和 onChainHash 三个值判断日志是否保持一致。
expectedHash 表示系统在日志提交阶段计算并保存的期望哈希，来源于 log_hash_records 表中的 log_hash 字段。当日志首次进入系统时，Server 对日志原文计算 SHA-256 哈希，并将该值写入 log_hash_records 表。因此，expectedHash 可以理解为系统在日志入库和上链时保存的原始摘要记录。它位于链下数据库中，便于后端快速读取和审计记录关联。
actualHash 表示审计阶段对当前日志原文重新计算得到的实际哈希。审计服务会根据待审计日志的 log_id 读取 logs 表中的 log_content，并使用与提交阶段相同的 SHA-256 规则生成 actualHash。该值反映的是审计发生时链下日志原文的当前状态。如果日志原文自提交后未被修改，actualHash 应当与 expectedHash 保持一致；如果日志内容被篡改、删除后重写或被伪造，则 actualHash 会与原始 expectedHash 不一致。
onChainHash 表示从 LogRegistry 合约中读取到的链上哈希记录。系统会根据 log_hash_records 中保存的 contract_address 连接对应合约，并根据 task_id 查询该任务下的链上记录，从中提取 logHash 字段。由于链上记录写入后难以被随意修改，onChainHash 在审计中承担独立可信证据的作用。它用于证明某条日志在提交时是否已经将对应哈希写入链上。
图 3-3 三方哈希比对流程
三方比对的基本逻辑是：当 expectedHash、actualHash 和 onChainHash 三者一致时，说明链下日志当前内容、数据库保存的原始哈希记录以及链上存证记录相互匹配，系统可以判定审计通过，生成 passed 状态的审计记录。当 actualHash 与 expectedHash 不一致时，说明当前日志原文与提交阶段保存的哈希不匹配，存在链下日志被修改的风险。如果此时链上记录仍能匹配 expectedHash，则更能说明当前链下日志已经偏离原始存证内容，系统应判定为 failed。当 expectedHash 存在但链上记录暂不可用或未匹配到对应哈希时，系统可根据实际情况标记为 pending 或 failed，以区分链上证据缺失与日志内容异常。
三方哈希比对机制的优势在于，它不是单纯依赖数据库自身进行校验，而是引入链上记录作为外部可信依据。即使链下 logs 表中的日志原文被篡改，只要 log_hash_records 或链上存证记录仍保留原始哈希，审计阶段就可以通过重新计算哈希发现异常。同时，如果链下数据库中的存证记录也出现不一致，链上 LogRegistry 中的记录仍可作为追溯依据。通过这种方式，系统在中心化存储之外增加了可信校验维度，提高了审计结果的可靠性。
本系统在生成审计结果时，会将 expectedHash、actualHash、审计状态和审计说明写入 audit_records 表，并在失败情况下生成异常告警。这使三方比对不仅停留在计算层面，还能转化为可查询、可展示、可追踪的审计结果。由此，数据库哈希、链上哈希与重算哈希三方比对构成了本系统可信日志审计机制的核心判定方法。
本节关键信息摘要：
1. 三方哈希比对包含 expectedHash、actualHash 和 onChainHash 三个值。
2. expectedHash 来源于 log_hash_records.log_hash，表示提交阶段保存的原始哈希。
3. actualHash 来源于审计阶段对 logs.log_content 的重新计算。
4. onChainHash 来源于 LogRegistry 合约查询结果，作为链上可信证据。
5. 三者一致时审计通过，不一致时系统判定异常并可生成告警。
3.4.2 历史合约地址回溯审计策略
在区块链应用系统中，合约地址是定位链上数据的重要依据。对于生产环境中长期稳定运行的合约而言，系统通常可以通过固定配置读取合约地址。但在毕业设计原型系统、本地 Hardhat 链环境或频繁部署测试场景中，合约地址可能随着部署过程发生变化。如果审计服务始终只读取当前环境变量中的最新合约地址，就可能无法正确查询历史日志对应的链上存证记录，从而影响审计结果的准确性。
本系统在实验和开发过程中考虑了这一问题，并采用基于历史合约地址的回溯审计策略。日志哈希每次写入链上后，后端不仅保存 log_hash 和 transaction_hash，还会在 log_hash_records 表中保存本次写入实际使用的 contract_address。该字段记录的是日志存证发生时对应的 LogRegistry 合约地址，而不是审计时系统当前配置的合约地址。审计阶段，系统优先读取该日志哈希记录中的 contract_address，并使用该地址创建链上读取客户端，查询对应历史合约中的存证记录。
这种设计能够解决多次部署带来的历史记录审计问题。例如，在本地 Hardhat 环境中，开发者可能重新启动节点或重新部署 LogRegistry 合约。此时，新的合约地址可能与旧日志写入时的地址不同。如果审计旧日志时只连接最新合约地址，系统可能无法查询到旧日志对应的 onChainHash，从而将原本已经完成存证的日志误判为链上记录缺失或审计待定。通过保存并使用 log_hash_records.contract_address，系统能够回到该日志实际写入时的合约地址进行查询，提高历史日志审计的可追溯性。
历史合约地址回溯策略还能够增强实验结果的可复现性。毕业设计系统通常需要多次执行部署、验证和性能测试，如果不同轮次实验使用了不同合约实例，而系统没有记录每条日志对应的合约地址，就难以解释旧数据审计结果为何发生变化。将 contract_address 与每条哈希记录绑定后，审计过程可以明确说明该日志写入了哪个合约，审计时又查询了哪个合约，从而减少因环境变化导致的误判。
从数据关系角度看，contract_address 是连接链下存证记录和链上合约实例的关键字段。task_id 能够定位任务维度的链上记录，log_hash 能够定位具体日志摘要，而 contract_address 则定位这些记录所在的合约实例。三者结合后，系统才能准确完成“哪条日志、属于哪个任务、写入哪个合约”的审计追溯过程。
需要说明的是，历史合约地址回溯并不改变链上存证本身的结构，而是在后端审计逻辑中增强链上读取策略。它属于工程实现层面的可靠性改进，主要用于解决多次部署、本地链重启和历史记录查询不一致等问题。通过该策略，系统能够更准确地处理不同部署时期产生的日志记录，提升可信审计流程的稳定性。
本节关键信息摘要：
1. 多次部署或本地 Hardhat 链重启可能导致当前合约地址与历史日志写入地址不同。
2. 如果审计时只读取当前环境变量中的合约地址，可能误判历史日志链上记录缺失。
3. 本系统在 log_hash_records.contract_address 中保存日志实际写入时的合约地址。
4. 审计阶段优先使用历史 contract_address 查询链上记录，提高可追溯性。
5. 历史合约地址回溯属于工程可靠性改进，有助于提升实验结果可信度。
3.4.3 合约代码存在性校验机制
区块链合约调用的前提是目标地址上确实部署了合约代码。在本地 Hardhat 链或测试环境中，节点重启、链状态重置或合约重新部署都可能导致原有合约地址不再包含有效字节码。如果系统仍然按照旧地址执行链上读写操作，就可能出现交易或查询过程表面执行，但实际并未与预期的 LogRegistry 合约交互的情况。对于可信日志审计系统而言，这类问题会影响链上存证和审计结果的真实性，因此需要在链上读写前增加合约代码存在性校验。
本系统采用 provider.getCode(address) 对目标合约地址进行校验。该方法可以读取指定地址上的链上字节码。如果返回结果为空或仅为 0x，则说明该地址当前没有部署合约代码，不能作为有效的 LogRegistry 合约地址使用。此时，系统应停止后续链上写入或查询，并给出明确错误提示，而不是继续执行可能产生误导结果的操作。通过这种方式，系统能够在链上交互开始前发现合约地址失效问题。
合约代码存在性校验首先用于日志哈希写入阶段。Server 在调用 LogRegistry.storeLog(taskId, logHash) 之前，会检查当前配置的合约地址是否存在字节码。如果合约地址无效，系统不会将该次写入误认为成功，而是记录链上写入失败状态。这样可以避免出现“数据库中已有哈希记录，但实际链上没有对应合约调用”的情况，保证 log_hash_records 中的 on_chain_status 更符合真实链上状态。
该机制同样适用于审计阶段。审计服务在根据 contract_address 创建链上读取客户端后，需要确认目标地址仍存在合约代码。如果目标地址不存在字节码，则说明当前链环境无法提供该条记录的链上证据，系统应将链上记录不可用作为审计状态判断的重要依据。相比直接吞掉异常或返回空结果，合约代码存在性校验能够更清楚地区分“链上确实没有对应哈希”和“目标合约地址当前不可用”这两类情况。
在实验环境中，该机制尤其重要。本地 Hardhat 链重启后，原有合约部署状态可能消失，但环境变量或数据库中仍可能保留旧合约地址。如果缺少代码存在性校验，系统可能在错误地址上执行查询，导致审计结果不稳定或难以解释。通过在链上读写前校验目标地址字节码，系统能够及时发现环境状态与数据库记录之间的不一致，从而提高实验过程的可复现性和审计结论的可信度。
从系统健壮性角度看，合约代码存在性校验是对链上交互边界条件的补充处理。它不改变日志哈希存证和三方比对的基本逻辑，但能够避免由于合约地址失效造成的误判。结合历史合约地址回溯策略，系统既能够定位日志实际写入的合约地址，又能够验证该地址在当前链环境中是否仍然有效，从而使链上链下协同审计更加稳健。
本节关键信息摘要：
1. 本地链重启或合约重新部署可能导致历史合约地址不再存在字节码。
2. 若不校验合约代码，系统可能在无效地址上执行链上读写，造成误判。
3. 本系统通过 provider.getCode(address) 检查目标地址是否存在合约代码。
4. 该机制同时用于日志哈希写入阶段和审计阶段。
5. 合约代码存在性校验能够提高实验可信性和系统健壮性。
3.5.1 审计状态判定规则
在可信日志审计过程中，系统需要将哈希比对结果转化为明确的审计状态，以便后端记录、前端展示和后续告警处理。本系统围绕数据库哈希、链上哈希与重算哈希三方比对结果，设计了 passed、failed 和 pending 三类审计状态。其中，passed 表示日志完整性校验通过，failed 表示日志存在篡改风险或存证记录不一致，pending 表示当前证据不完整或链上记录暂不可用，需要等待后续补充核验。
审计状态判定首先依赖 expectedHash、actualHash 和 onChainHash 三个值。expectedHash 来源于 log_hash_records 表中的 log_hash 字段，代表日志提交阶段保存的原始哈希。actualHash 来源于审计阶段对 logs 表中 log_content 字段重新计算得到的哈希，代表当前链下日志内容的实际状态。onChainHash 来源于 LogRegistry 合约查询结果，代表链上存证记录中的日志哈希。三者分别对应数据库记录、当前日志内容和链上存证证据，是审计判定的核心依据。
当 expectedHash、actualHash 与 onChainHash 三者完整存在且内容一致时，系统将审计状态判定为 passed。该状态说明链下日志当前内容与数据库中保存的原始哈希一致，同时也能在链上存证记录中找到匹配哈希。此时，日志从提交、存证到审计重算的完整链路能够相互印证，系统可以认为该条日志在链下保存期间未发生内容篡改。审计通过后，系统会在 audit_records 表中写入 passed 状态，并可将 logs 表中对应日志状态更新为 audit_passed，供前端展示和统计使用。
当 actualHash 与 expectedHash 不一致时，系统通常将审计状态判定为 failed。该情况说明审计阶段重新计算得到的日志哈希与日志提交阶段保存的哈希不一致，表示链下日志原文可能已经被修改。即使链上记录仍然存在且与 expectedHash 匹配，也只能说明原始日志曾经完成存证，而当前链下日志已经偏离原始内容。因此，该情况应被视为篡改风险，并触发后续异常告警流程。若 expectedHash 与链上记录也不匹配，则说明链下数据库记录、当前日志内容或链上存证之间存在更复杂的不一致，同样应判定为 failed，以提示用户进行人工复核。
pending 状态主要用于处理证据不完整或链上记录暂不可用的情况。例如，数据库中存在 expectedHash，且 actualHash 与 expectedHash 一致，但由于链上服务暂时不可访问、合约地址不可用或链上记录尚未匹配到对应哈希，系统无法确认该日志是否具备完整链上存证。此时，日志内容本身未表现出被篡改迹象，但链上证据不足，系统可将审计状态标记为 pending。pending 并不表示审计失败，而是表示当前审计结论尚不完整，需要在链上记录恢复或补充后再次确认。
表 3-3 审计状态判定规则
审计状态判定规则的设计需要兼顾准确性和可解释性。passed 状态强调三方证据一致，failed 状态强调哈希不一致或存在篡改风险，pending 状态则用于区分链上证据缺失与日志内容异常。通过这种分类，系统能够避免将所有链上不可用情况简单归为失败，也能够在日志内容确实发生变化时及时给出风险提示。最终，审计状态将与 audit_message 一同写入 audit_records 表，为前端展示和后续追踪提供依据。
本节关键信息摘要：
1. 审计状态分为 passed、failed 和 pending 三类。
2. passed 表示 expectedHash、actualHash 和 onChainHash 三方一致，日志完整性校验通过。
3. failed 表示重算哈希与数据库或链上存证不一致，日志存在篡改风险。
4. pending 表示日志内容暂未发现异常，但链上证据缺失或不可用，审计结论尚不完整。
5. 审计状态和审计说明会写入 audit_records 表，供前端展示和后续追踪使用。
3.5.2 哈希不一致告警生成流程
审计状态判定完成后，系统需要将发现的异常转化为可追踪、可展示的告警记录。单纯生成 failed 审计结果只能说明某次审计未通过，但如果缺少告警机制，用户仍需要主动检查审计列表才能发现风险。为提高异常发现效率，本系统在审计结果为 failed 时自动生成 hash_mismatch 类型告警，将日志完整性异常从审计结果进一步转化为告警事件，形成从检测到提示的闭环流程。
哈希不一致告警的生成入口位于审计执行流程。当系统完成 expectedHash、actualHash 和 onChainHash 的比对后，如果判定结果为 failed，后端服务会先创建一条审计记录，将 audit_status、expected_hash、actual_hash 和 audit_message 等信息写入 audit_records 表。随后，系统根据该审计记录生成对应的告警数据，并写入 alerts 表。这样，审计记录负责保存本次校验的技术结果，告警记录负责向用户表达该异常的风险含义，二者通过关联字段建立联系。
在 alerts 表中，alert_type 用于标识告警类型。本系统当前使用 hash_mismatch 表示哈希不一致告警，说明该告警由日志哈希校验失败触发。severity 表示告警严重程度，哈希不一致通常意味着日志内容可能被篡改，因此可设置为较高风险级别。related_log_id 用于关联出现异常的日志记录，related_audit_id 用于关联触发该告警的审计记录。通过这两个字段，用户可以从告警追溯到具体日志，也可以从告警查看对应审计过程和哈希比对结果。
告警标题和描述用于提高前端展示的可读性。标题通常概括风险对象，例如提示某一任务存在篡改风险；描述则进一步说明该日志的重新计算哈希与存证记录不一致，需要进行复核。相比只展示 failed 状态，标题和描述能够帮助用户快速理解异常原因，降低使用者阅读底层哈希字段的成本。status 字段用于表示告警处理状态，默认可设置为 open，表示该告警尚未处理。后续若系统扩展告警处置功能，可以根据处理过程将状态更新为 resolved 或其他状态。
哈希不一致告警生成流程体现了本系统从审计检测到风险提示的闭环。系统并不是在发现哈希不一致后仅返回接口结果，而是将异常持久化为告警记录，使前端告警管理页面能够持续展示该风险。即使用户没有立即查看审计详情，也可以通过告警列表发现存在异常的日志记录。与此同时，告警与日志、审计记录之间的关联关系保证了异常事件可以被追溯，便于后续人工复核或进一步处理。
从系统设计角度看，告警机制增强了可信日志审计系统的主动性和可用性。三方哈希比对负责发现问题，审计记录负责保存技术证据，告警记录负责提示风险并支持后续跟踪。三者结合后，系统能够将底层哈希不一致问题转化为面向用户的异常事件，从而提高日志审计结果的实际应用价值。
本节关键信息摘要：
1. 当审计状态为 failed 时，系统会自动生成 hash_mismatch 类型告警。
2. audit_records 保存审计技术结果，alerts 保存面向用户的异常风险提示。
3. related_log_id 和 related_audit_id 分别关联异常日志和触发告警的审计记录。
4. 告警标题、描述、严重程度和状态字段有助于前端展示和后续追踪。
5. 告警机制将哈希不一致检测结果转化为可持续管理的风险事件。
3.6 本章小结
本章围绕基于区块链的可信日志存证与审计机制展开，重点说明了系统核心技术方案。首先，本章提出链下保存日志原文、链上保存日志哈希的混合存储模型，通过 SQLite 保留日志查询和展示能力，通过 LogRegistry 智能合约保存哈希摘要和任务标识，从而兼顾存储效率、隐私保护和审计可信性。随后，本章说明了日志采集、存证、审计、告警和前端展示构成的完整闭环流程，明确了各模块在可信日志审计链路中的作用。
在数据模型方面，本章介绍了日志标准化封装、任务标识设计、SHA-256 日志摘要生成方法，以及链上存证字段与链下记录之间的映射关系。通过 taskId、log_id、log_hash 和 contract_address 等字段，系统能够将链下日志原文、数据库存证记录和链上合约记录关联起来，为后续审计比对提供稳定的数据基础。
在智能合约与审计机制方面，本章围绕 LogRegistry 合约的数据结构、AccessControl 权限控制、日志哈希写入和任务维度查询方法进行了说明，并进一步分析了数据库哈希、链上哈希与重算哈希的三方比对机制。针对本地链重启和多次部署可能带来的审计误判问题，本章还说明了历史合约地址回溯审计策略和合约代码存在性校验机制。最后，本章介绍了审计状态判定规则和哈希不一致告警生成流程，使系统能够在发现日志完整性异常后生成审计失败记录和异常告警。
综上，本章完成了系统核心可信审计机制的设计说明，为后续系统需求分析、总体架构设计以及具体工程实现提供了技术基础。
本节关键信息摘要：
1. 本章重点说明了链下日志存储与链上哈希存证结合的可信审计模型。
2. LogRegistry 合约、LOGGER_ROLE 权限控制和任务维度查询构成链上存证基础。
3. 三方哈希比对是判断日志是否被篡改的核心方法。
4. 历史合约地址回溯和合约代码存在性校验增强了审计过程的可靠性。
5. 审计状态判定与异常告警机制共同形成从检测到提示的闭环。
