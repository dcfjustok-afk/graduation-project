## 5.1 系统开发环境与工程结构

本系统以毕业设计原型实现和论文实验验证为目标，采用前后端分离、链上链下协同和多模块统一管理的工程组织方式。为便于同时管理前端页面、后端服务、日志采集 Agent、智能合约和公共类型，本项目采用 Monorepo 结构，将不同子系统放置在同一仓库中进行统一维护。该组织方式能够减少多仓库之间版本不一致的问题，也便于在实验和答辩过程中通过统一脚本完成构建、验证和演示。

系统工程主要由 apps、packages、tests、scripts、storage 和 doc 等目录组成。其中，apps 目录用于存放可独立运行的应用模块，包括 apps/web、apps/server 和 apps/agent。apps/web 是前端审计系统，基于 React、TypeScript 和 Ant Design 实现，主要负责系统总览、日志中心、审计管理和告警管理等页面展示。apps/server 是后端服务模块，基于 Node.js、Express 和 TypeScript 实现，负责接收日志、写入 SQLite、计算日志哈希、调用智能合约、执行审计和生成告警。apps/agent 是日志采集模块，用于读取本地日志文件新增内容，并将日志提交给后端服务。

packages 目录用于存放可被多个模块复用或独立维护的公共工程。其中，packages/contracts 是智能合约工程，基于 Hardhat、Solidity 和 OpenZeppelin 实现 LogRegistry 合约，并提供合约部署和测试能力。packages/shared 用于沉淀前后端和 Agent 可复用的类型定义、数据结构和公共协议，减少不同模块之间字段不一致的问题。通过将合约工程和共享类型独立出来，系统能够在保持模块边界清晰的同时，提高整体工程的一致性。

tests/performance 目录用于保存性能测试脚本，包括日志批量提交实验和批量审计实验。scripts 目录用于存放仓库级验证脚本，便于统一执行合约测试、后端验证、Agent 验证和前端构建验证。storage/sqlite 目录用于保存 SQLite 数据文件和相关说明，支撑链下日志、哈希记录、审计记录、告警记录和 Agent 状态的持久化。doc 目录用于保存论文目录、技术说明、实验报告、答辩材料和写作 SOP 等文档资料，为论文撰写和答辩准备提供支撑。

从技术栈角度看，系统前端采用 React 和 Ant Design 实现页面交互和可视化展示，后端采用 Express 提供 REST API，链下数据存储采用 SQLite，链上存证采用 Hardhat 本地链和 Solidity 智能合约实现，后端通过 Ethers 与 LogRegistry 合约交互。该技术组合既能够覆盖完整的软件系统开发流程，又能够突出区块链可信存证在日志审计中的作用。

总体而言，Monorepo 工程结构使本系统能够在一个仓库内统一管理多个子模块，便于开发、测试、实验和论文说明。前端、后端、Agent、合约和共享类型之间职责相对独立，又通过统一接口和数据结构相互协作，为后续系统实现和实验验证奠定了工程基础。

本节关键信息摘要：

1. 系统采用 Monorepo 结构统一管理前端、后端、Agent、智能合约和共享类型。
2. apps/web、apps/server 和 apps/agent 分别对应前端展示、后端服务和日志采集。
3. packages/contracts 负责 LogRegistry 合约开发，packages/shared 负责共享类型和公共协议。
4. tests/performance 和 scripts 目录支撑性能实验与脚本化验证。
5. 工程结构有助于提升系统可维护性、实验可复现性和论文说明清晰度。

## 5.2 日志采集 Agent 实现

日志采集 Agent 是系统实现自动化日志接入的关键模块。传统日志审计若依赖人工导入日志，容易出现遗漏、重复和时效性不足等问题。为使任务日志能够持续进入可信审计流程，本系统设计了独立的 Agent 模块，用于读取本地日志文件新增内容，并将标准化日志数据提交给后端服务。Agent 模块主要围绕日志读取、增量采集、偏移量持久化、失败重试和状态同步等功能展开，其中 logAgent 负责组织 Agent 主流程，协调 fileReader、logCollector、retryQueue 和 offsetStore 等功能单元共同完成采集与上报。

### 5.2.1 增量读取与偏移量持久化实现

增量读取是 Agent 模块的基础能力。日志文件通常会随着系统运行不断追加内容，如果每次采集都从文件开头读取，不仅会造成重复提交，也会增加不必要的处理开销。因此，Agent 需要记录每个日志文件上一次读取到的位置，并在下一次采集时从该偏移量继续读取新增内容。本系统通过 fileReader 和 offsetStore 等功能实现增量采集与偏移量持久化。

fileReader 负责根据指定文件路径和偏移量读取新增日志内容。当 Agent 启动或定时执行采集任务时，系统首先从 offsetStore 中读取上次保存的 lastOffset，再将该偏移量传入文件读取逻辑。fileReader 根据文件当前长度和 lastOffset 判断是否存在新增内容；若文件长度大于偏移量，则读取新增部分并按日志行进行处理；若文件没有新增内容，则本轮采集不产生提交数据。该方式能够避免重复读取历史日志，使 Agent 更适合持续运行场景。

logCollector 负责组织日志采集流程。它在 fileReader 读取新增内容后，将日志行封装为后端可接收的数据结构。封装内容通常包括 taskId、sourceType、sourcePath、logContent、logLevel 和 collectedAt 等字段。其中，taskId 用于标识日志所属任务，sourcePath 用于说明日志来源文件，logContent 是实际提交的日志内容，collectedAt 用于记录采集时间。通过标准化封装，Agent 输出的数据能够与后端日志入库、哈希计算和链上存证流程保持一致。

偏移量持久化用于保证 Agent 重启后仍能继续从正确位置读取日志。如果 Agent 只在内存中保存偏移量，一旦进程退出或系统重启，下一次运行时可能重新读取整个文件，造成重复提交。offsetStore 将读取位置保存到本地状态文件中，使 Agent 在重新启动后能够恢复上次采集进度。当日志提交成功后，Agent 会更新对应文件的 lastOffset，确保后续采集从新的位置继续读取。

在实现效果上，增量读取与偏移量持久化共同保证了日志采集过程的连续性和准确性。fileReader 解决“从哪里读”的问题，logCollector 解决“如何组织提交数据”的问题，offsetStore 解决“采集进度如何保存”的问题。三者配合后，Agent 能够以较低侵入方式接入本地日志文件，为后端可信存证和审计流程提供稳定输入。

本节关键信息摘要：

1. Agent 通过偏移量机制只读取日志文件新增内容，避免重复采集。
2. fileReader 根据文件路径和 lastOffset 读取新增日志数据。
3. logCollector 将日志行封装为包含 taskId、sourcePath、logContent 等字段的提交数据。
4. offsetStore 将读取偏移量持久化，支持 Agent 重启后继续采集。
5. 增量读取和偏移量持久化为后续日志入库和链上存证提供稳定输入。

### 5.2.2 失败重试与状态同步实现

在实际运行过程中，Agent 向后端提交日志时可能遇到网络异常、后端服务暂时不可用或接口调用失败等情况。如果失败后直接丢弃日志，将破坏日志采集链路的完整性；如果无限制地立即重试，又可能在后端不可用时造成额外压力。因此，本系统在 Agent 模块中设计了失败重试机制和状态同步机制，以提高日志采集过程的可靠性和可观察性。

失败重试主要由 retryQueue 负责。当 Agent 提交日志失败时，系统不会立即丢弃该日志，而是将待提交数据加入重试队列。重试队列保存待发送日志、失败次数和下一次重试时间等信息，使 Agent 能够在后续轮询过程中继续尝试提交。为了避免频繁请求不可用服务，重试过程可以采用逐步延长间隔的策略，使系统在保证数据不丢失的同时降低异常期间的请求压力。

retryQueue 的持久化同样重要。如果待重试数据只保存在内存中，Agent 重启后未发送日志将丢失。通过将重试队列写入本地文件，Agent 可以在重新启动后恢复未提交任务，并继续向后端发送。该设计提高了日志采集过程的容错能力，使系统在短暂异常后仍能尽量保持日志提交完整性。

状态同步用于向后端报告 Agent 当前运行情况。Agent 在运行过程中会定期将 agentName、sourcePath、lastOffset、lastHeartbeatAt、lastSyncAt、status 和 errorMessage 等信息提交给后端，由后端保存到 agent_states 表中。通过该表，系统可以了解 Agent 是否在线、当前读取到哪个位置、最近一次同步时间以及是否存在错误信息。前端总览页面也可以基于这些状态展示采集端运行情况。

失败重试与状态同步分别解决日志提交可靠性和采集过程可观察性问题。前者保证在后端暂时不可用时日志不会轻易丢失，后者使系统能够掌握 Agent 的运行状态。二者结合后，Agent 不仅能够完成基本日志读取，还能够在异常场景下保持较好的恢复能力，并为后端和前端提供运行状态依据。这些能力为系统形成稳定的“采集—存储—存证—审计”链路提供了基础。

本节关键信息摘要：

1. retryQueue 用于保存提交失败的日志数据，避免异常时直接丢失。
2. 重试队列可持久化保存，支持 Agent 重启后恢复未发送数据。
3. 状态同步会将 Agent 名称、日志路径、偏移量、心跳时间和错误信息提交给后端。
4. agent_states 表用于保存采集端运行状态，便于前端展示和后续排查。
5. 失败重试和状态同步提升了日志采集链路的可靠性和可观察性。
