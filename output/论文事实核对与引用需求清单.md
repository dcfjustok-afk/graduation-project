## 二、论文题目和研究对象

论文题目：`基于区块链的可信任务日志审计系统设计与实现`。

研究对象是“任务日志”的可信审计系统，不是通用区块链平台、完整 SIEM 系统、日志语义异常检测系统、生产级区块链审计平台或多用户权限管理平台。

论文研究的问题是：传统中心化日志保存方式下，日志原文、哈希记录和审计结果可能处于同一管理域内，一旦数据库或管理权限被滥用，日志被修改、删除或伪造后缺少独立可信依据。本文采用“链下保存日志原文、链上保存日志哈希摘要”的方式，为日志完整性审计提供可追溯的外部参照。

## 三、系统真实目标

系统目标是构建一个可运行、可演示、可实验验证的可信任务日志审计原型，打通以下闭环：

1. Agent 从本地日志文件增量采集新增日志。
2. Server 接收日志并写入 SQLite。
3. Server 对日志正文计算 SHA-256 哈希。
4. Server 调用 `LogRegistry` 合约写入日志哈希摘要。
5. 审计服务重新计算日志哈希，并与数据库哈希、链上哈希进行比对。
6. 审计失败时写入 `audit_records` 并生成 `hash_mismatch` 告警。
7. Web 前端展示总览、日志、审计和告警数据。

系统目标不包括：

- 公开链、测试网或联盟链生产部署；
- 链上保存日志原文；
- 多租户、多用户登录或完整 RBAC 业务权限系统；
- 日志语义识别、攻击模式识别或机器学习异常检测；
- 数字签名体系、端到端加密存储或 Merkle Tree 批量证明；
- 合约批量写入、分页查询、删除或修改链上记录。

## 四、系统真实链路

系统真实链路如下：

```text
本地日志文件
  -> apps/agent 按 lastOffset 增量读取新增行
  -> Agent 维护 pendingQueue 与 offset 状态
  -> Agent 调用 POST /api/logs
  -> Server 校验请求体并写入 SQLite logs 表
  -> Server 计算 log_content 的 SHA-256 哈希
  -> Server 使用 Ethers 连接本地 Hardhat 链
  -> Server 先执行 provider.getCode(address) 校验合约代码存在
  -> Server 调用 LogRegistry.storeLog(taskId, logHash)
  -> Server 写入 log_hash_records
  -> 用户或脚本触发 POST /api/audits/run 或 POST /api/audits/:logId/run
  -> Server 读取 logs.log_content 并重新计算 actualHash
  -> Server 读取 log_hash_records.log_hash 作为 expectedHash
  -> Server 使用 log_hash_records.contract_address 回溯历史合约地址
  -> Server 调用 LogRegistry.getLogsByTaskId(taskId) 查询 onChainHash
  -> Server 进行 expectedHash / actualHash / onChainHash 比对
  -> passed / failed / pending 写入 audit_records
  -> failed 时写入 alerts 表中的 hash_mismatch 告警
  -> Web 前端通过 REST API 展示统计、列表、审计和告警
```

需要精确表述的细节：

- Agent 是“轮询 + 文件偏移量读取”，不是 `fs.watch` 或 `chokidar`。
- 链上只保存哈希摘要和必要元数据，不保存日志原文。
- 后端写链前会通过 `provider.getCode(address)` 校验合约地址是否存在字节码。
- 审计时优先使用 `log_hash_records.contract_address`，不是只使用当前 `.env` 中的最新合约地址。
- 批量审计当前是逐条顺序执行，不是并发审计队列。

## 七、智能合约真实能力

合约文件：`packages/contracts/contracts/LogRegistry.sol`  
合约名称：`LogRegistry`  
继承：OpenZeppelin `AccessControl`

角色：

- `DEFAULT_ADMIN_ROLE`：默认管理员角色；
- `LOGGER_ROLE`：允许写入日志存证记录的角色。

链上结构：

```solidity
struct LogRecord {
    string taskId;
    bytes32 logHash;
    uint256 createdAt;
    address submitter;
}
```

方法：

| 方法 | 真实能力 |
| --- | --- |
| `storeLog(string taskId, bytes32 logHash)` | 仅 `LOGGER_ROLE` 可调用；校验 `taskId` 非空、`logHash` 非零；写入记录并触发事件。 |
| `getLog(uint256 recordId)` | 按记录编号查询单条链上存证记录。 |
| `getRecordIdsByTaskId(string taskId)` | 按任务标识查询链上记录编号数组。 |
| `getLogsByTaskId(string taskId)` | 按任务标识查询完整链上记录数组。 |
| `getTaskLogCount(string taskId)` | 查询指定任务的链上日志数量。 |
| `getLogCount()` | 查询链上日志存证总数。 |

事件：

- `LogStored(recordId, taskId, logHash, submitter, createdAt)`

合约不具备：

- 不保存日志原文；
- 不保存交易哈希、区块号和合约地址，这些由后端写入 SQLite；
- 不实现日志删除、修改、分页查询或批量写入；
- 不执行审计判定，审计判定由后端完成；
- 不实现完整业务用户权限系统。

## 九、审计机制

审计逻辑文件：`apps/server/src/services/auditExecutionService.ts`。

三类核心哈希：

- `expectedHash`：来自 `log_hash_records.log_hash`，表示日志提交阶段保存的哈希；
- `actualHash`：审计阶段对当前 `logs.log_content` 重新计算得到的哈希；
- `onChainHash`：通过 `LogRegistry.getLogsByTaskId(taskId)` 从链上查询得到的哈希，代码中优先判断链上列表是否包含 `expectedHash`。

判定规则：

| 场景 | 结果 |
| --- | --- |
| `expectedHash` 存在、链上匹配该哈希、且 `actualHash == expectedHash` | `passed` |
| `expectedHash` 存在、链上匹配该哈希、但 `actualHash != expectedHash` | `failed`，生成 `hash_mismatch` |
| `expectedHash` 存在、链上未匹配或暂不可用、但 `actualHash == expectedHash` | `pending` |
| `expectedHash` 存在、链上未匹配或暂不可用、且 `actualHash != expectedHash` | `failed`，生成 `hash_mismatch` |
| `expectedHash` 不存在 | `pending` |

需要谨慎表达：

- “三方哈希比对”是本文对审计机制的工程概括；
- `pending` 表示证据不完整，不等于通过；
- 系统识别的是“存证后链下日志内容是否被修改”，不能证明日志最初业务语义绝对真实。
